# sql/upgrade —— 存量库增量脚本

这个目录放的是**给已经存在的数据库打的补丁**，与上一层 [`../crm.sql`](../crm.sql)
是两种完全不同的东西，**别混用**：

| | `../crm.sql` | 本目录（`sql/upgrade/*.sql`） |
| :--- | :--- | :--- |
| 用途 | **全量初始化**：建 49 张表 + 全部种子数据 | **增量升级**：给已有库补列 / 补表 / 补菜单 |
| 什么时候跑 | **只有全新的空库** | 只有**存量库**（已经跑过旧版 crm.sql 的） |
| 对已有库执行 | ☠️ **清库**（含 49 条 `DROP TABLE`） | 正常，就是干这个的 |
| 对新库执行 | 正常 | 报 1060 / 1091 / 1062，**忽略即可** |

> **本质原因**：`../crm.sql` 是「结果」—— 任何一个脚本的改动都已经折叠进它的建表语句和
> 种子数据里了。所以这些增量脚本**不是「还没合并的碎片」**，它们存在的唯一理由是
> 让**存量库**能追平 `crm.sql`。不要再往 `crm.sql` 里追加它们的内容，
> 那会让全新库跑出 `Duplicate column` / 主键重复。

## ⚠️ 三个必须先知道的前提

1. **dev 和 prod 是同一个库**（`YOUR_SERVER_IP:3306/crm`）。
   在这里执行的任何 SQL，改的都是生产数据。
2. **多数脚本不是「重复执行安全」的**。重跑一般会报
   `1060 Duplicate column` / `1091 Can't DROP` / `1062 Duplicate entry` ——
   这些报错**通常意味着早就跑过了**，不代表脚本坏了。
   每个脚本头部都写了它自己的重跑行为和校验方法。
3. **执行前先核对状态，不要凭印象**。判断某个脚本跑过没有的方法见
   《[docs/09-生产部署.md](../../docs/09-生产部署.md)》7.1 节 ——
   那份文档里有完整的**脚本清单与执行状态**，是本目录唯一的台账。

## 命名约定

```
alter-<日期>-<主题>.sql    表结构 / 菜单 / 授权变更
seed-<日期>-<主题>.sql     演示或回填数据（不是表结构）
```

日期是**脚本编写日期**，不是「应该执行的时间」。文件名里的主题要能一眼看出动了哪张表。

## 新增脚本时

1. 文件头写清楚四件事：**背景（为什么需要）**、**什么时候跑**、
   **重跑会怎样**（含可忽略的错误码）、**怎么验证跑成功了**。
2. 在《docs/09-生产部署.md》7.1 的表格里**加一行**，状态填 `☐ 待确认`。
   —— 漏加这一步，接手的人就不知道有这个脚本，等于没写。
3. 同步更新 `../crm.sql`：把这些改动折叠进它的建表语句 / 种子数据。
   否则新库与原库会漂移。
