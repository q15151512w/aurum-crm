## 一、通用约定

### 1.1 统一响应格式

```json
{
  "code": 0,
  "message": "操作成功",
  "data": { },
  "success": true
}
```

| 字段 | 说明 |
| :--- | :--- |
| `code` | **0 表示成功**，非 0 为业务错误码 |
| `message` | 提示信息，非 0 时可直接展示给用户 |
| `data` | 业务数据，无数据时为 `null` |
| `success` | `code == 0` 的便捷布尔值 |

### 1.2 HTTP 状态码约定 ⚠️

| 场景 | HTTP 状态 | body.code |
| :--- | :--- | :--- |
| 成功 | 200 | 0 |
| 业务规则拒绝 | 200 | 业务错误码 |
| 未登录 / Token 失效 | 200 | 401 |
| 权限不足 | 200 | 403 |
| 参数校验失败 | 200 | 400 |
| **未预期的服务端异常** | **500** | 500 |

> **前端拦截器必须同时处理这两条路径**，不能只判断 HTTP 状态码。实现见 `aurum-crm-ui/src/utils/request.js`。

### 1.3 认证

除白名单外，所有接口都需要携带 Token：

```http
Authorization: Bearer <token>
```

白名单路径：`/auth/login`、`/auth/login/email`、`/auth/email/**`、`/auth/register`、`/auth/password/forgot`、`/auth/captcha`、`/health`、`/doc.html`、`/actuator/**`

> ⚠️ 白名单只列**确实不需要登录**的接口。别图省事写成 `/auth/**` ——
> 那会把 `/auth/me`、`/auth/logout`、`/auth/profile`、`PUT /auth/password` 一起放开，
> 它们要读登录态，被跳过后会抛异常并以 **HTTP 500** 返回，与真实原因完全脱节。
> 同理 `/auth/password/forgot` 在白名单里，而 `PUT /auth/password`（已登录改密）**绝不能**加进来。

### 1.4 分页

**请求参数**（继承 `PageParam`）：

| 参数 | 类型 | 默认 | 说明 |
| :--- | :--- | :--- | :--- |
| `pageNo` | Integer | 1 | 页码，从 1 开始 |
| `pageSize` | Integer | 10 | 每页条数，**上限 500** |

**响应结构**：

```json
{
  "code": 0,
  "data": {
    "list": [],
    "total": 1024,
    "pageNo": 1,
    "pageSize": 10
  }
}
```

### 1.5 错误码分段

| 区间 | 模块 | 示例 |
| :--- | :--- | :--- |
| 0 | 成功 | |
| 400–599 | 通用 | 401 未登录、403 无权限、400 参数错误、500 服务端错误 |
| 1000–1999 | 系统 | 1002 账号或密码错误、1102 角色名已存在 |
| 2000–2999 | 客户 | 2002 线索已转化、2103 客户已被他人领取 |
| 3000–3999 | 财务 | 3102 发票已开具 |
| 4000–4999 | 审批流 | 4005 审批任务已处理 |
| 4900+ | 并发 | 4902 资源已被他人操作 |
| 5000–5999 | **AI 小助手** | 5001 AI 服务暂时不可用、5006 未配置模型 |

**认证模块用到的具体错误码**（1000–1099 段）：

| 码 | 含义 | 触发场景 |
| :--- | :--- | :--- |
| 1002 | 账号或密码错误 | 2.1 密码登录 |
| 1003 | 原密码错误 | 2.7 修改密码 |
| 1004 | 验证码发送过于频繁 | 2.2，同一邮箱 60 秒内重复请求 |
| 1005 | 账号已存在 | 2.4 注册，`username` 重复 |
| 1006 | 验证码错误或已过期 | 2.3 / 2.4 / 2.5 校验**邮箱** `emailCode` 失败 |
| 1009 | 验证码邮件发送失败 | 2.2，SMTP 连不上 / 授权码错 / 被 163 限流（**会退还 60 秒限流**）|
| 1010 | 该邮箱已被注册 | 2.4 注册时 `email` 重复 |
| 1007 | **账号未启用** | 登录时 `status != 1`。见下方说明 |
| 1008 | 验证码错误或已过期，请重新计算 | 2.1 密码登录的**算术验证码**答错或过期（见 2.9）|
| 1104 | 角色标识已存在 | 3.2 新增/修改角色，`role_key` 重复 |
| 1105 | 不能把自己设为直属上级 | 3.1 设置直属上级 |
| 1106 | 请先为该人员分配角色 | 3.1 激活时该账号没有任何角色（见下方说明）|
| 1107 | 角色组不存在 | 3.2 删除角色组 |
| 1108 | 角色组名称已存在 | 3.2 新增角色组 |

**角色相关（1101–1103）**：1101 角色不存在 / 1102 角色名称已存在 / 1103 该角色下还有用户，无法删除。

> **1006 与 1008 是两种不同的验证码**，分号编码而不是共用一个 —— 共用的话日志里
> 分不清用户是「邮箱验证码填错」还是「算术题答错」，排障时要多绕一圈。

> **1007 的提示文案要分情况**，前端直接展示 `message` 即可：
> - `status = 2` 且**未分配角色** → 「账号待管理员分配角色后启用」（**注册后的默认状态**）
> - `status = 2` 且已分配角色 → 「账号已被禁用，请联系管理员」
> - `status = 3` → 「该账号已离职」

**字典模块用到的具体错误码**（1300–1399 段）：

| 码 | 含义 | 触发场景 |
| :--- | :--- | :--- |
| 1301 | 字典类型已存在 | 新增类型时 `type`（编码）重复 |
| 1302 | 字典类型不存在 | 修改/删除/新增字典项时，目标类型不存在 |
| 1303 | 字典项不存在 | 修改/删除字典项时该 id 不存在 |
| 1304 | 该字典类型下已存在相同的键值 | 同类型下 `value` 重复。⚠️ **应用层校验**，表上没有唯一键 |
| 1305 | 该字典类型下还有字典项，无法删除 | 删除类型前先删掉它下面的字典项，或改为「停用」 |

**AI 小助手用到的具体错误码**（5000–5999 段）：

| 码 | 含义 | 触发场景 |
| :--- | :--- | :--- |
| 5001 | AI 服务暂时不可用 | 上游连接失败 / 返回 5xx / 响应无法解析 |
| 5002 | AI 服务响应超时 | 与上游的连接或读取超时 |
| 5003 | 不支持的工具调用 | 上游请求了未注册的工具名（正常不会出现）|
| 5004 | AI 查询步骤过多 | 工具调用轮数达到上限（默认 3 轮）|
| 5005 | 提问内容过长 | 单次提问超出 `ai.max-prompt-chars`（默认 4000 字）|
| 5006 | AI 小助手未启用 | 未配置 `ai.providers.*.api-key`，或 `ai.enabled=false` |

> **流式接口的错误码出现在两个不同位置**，前端必须分别处理：
> 权限（403）、参数校验（400）、5005、5006 都发生在**响应流开始之前**，返回的是普通 JSON；
> 而 5001 / 5002 发生在对话过程中 —— 那时 HTTP 状态码已锁定 200，只能通过 SSE 的
> `error` 事件传出。详见**第十三节**。

### 1.6 数据权限说明 ⚠️

**所有查询接口的返回数据都会被数据权限自动过滤**，前端无需传任何参数：

| 角色 | 能看到的数据 |
| :--- | :--- |
| 销售专员 | 自己负责的 + **全部公海数据** |
| 销售总监 | 本部门及以下 + 全部公海数据 |
| 财务 / 管理员 | 全部数据 |

详见《04-权限设计文档.md》第三节。前端只负责展示，**不要试图用参数绕过**（后端会忽略）。

### 1.7 字段权限说明

部分敏感字段会**按角色脱敏或置空**，前端需做兜底展示：

| 字段 | 非授权角色看到的效果 |
| :--- | :--- |
| `crm_product.costPrice` | `null` |
| `crm_customer.phone` / `crm_contact.phone` | `138****8888` |
| `fin_payment.amount` | `null` |

> 前端应对 `null` 做友好展示（如显示 `--`），而不是报错或显示 `undefined`。

### 1.8 字段口径约定 ⭐

**新增接口或字段前必读。** 这套约定是在 BUG-002（前后端字段口径不一致导致的 500 与大面积空列）修复过程中固定下来的，详见《07-测试BUG记录》。

#### 三条规则

| # | 规则 | 判断标准 | 落地方式 |
| :--- | :--- | :--- | :--- |
| 1 | **数据字典字段传码值** | 取值存在 `sys_dict_data` 表里 | 请求/响应都是 `TINYINT`；前端用 `dictOptions()` / `useDictMap()` 从 `/system/dict-data/batch` 取数（见 `composables/useDictOptions.js`），列表用 `#cell-xxx` slot 映射标签 |
| 2 | **状态机枚举字段传中文标签** | 取值写死在 Java 枚举里 | 后端在 Convert 里用 `labelOf()` 转换；前端表单与列表都用中文，不做映射 |
| 3 | **对外字段名跟前端走** | — | 请求方向用 DDL 字段名；响应方向由 VO 补前端要的别名与派生字段 |

#### 规则 1 的例子（数据字典）

| 字段 | 字典 | 接口取值 |
| :--- | :--- | :--- |
| `crm_customer.source` / `crm_lead.source` | `crm_source` | 1 官网 / 2 电话 / … / 5 广告 / 7 其他 |
| `crm_customer.industry` / `crm_lead.industry` | `crm_industry` | 1 制造业 / 2 互联网 / … / 8 其他 |
| `crm_customer.level` / `crm_lead.level` | `crm_customer_level` | 1 重要 / 2 普通 / 3 非优先 |
| `crm_customer.deal_status` | `crm_deal_status` | 1 未成交 / 2 已成交 |
| `crm_contract.contract_type` | `crm_contract_type` | 1 销售合同 / 2 框架合同 / 3 补充协议 |

权威取值以 `sql/crm.sql` 的 `sys_dict_data` 为准。

#### 规则 2 的例子（状态机枚举）

| 字段 | 枚举类 | 对外标签 |
| :--- | :--- | :--- |
| `crm_opportunity.stage` | `OpportunityStage` | 初步接洽 / 需求确认 / 方案报价 / 商务谈判 / 赢单 / 输单 |
| `crm_quotation.status` | `QuotationStatus` | 草稿 / 已发出 / … |
| `crm_contract.audit_status` | `ContractAuditStatus` | 未提交 / 审核中 / 审核通过 / 审核拒绝 |
| `crm_contract.status` | `ContractStatus` | 草稿 / 已生效 / 已作废 / 已到期 |

> ⚠️ `crm_contract` 有**两个**状态列，别搞混：`audit_status` 是审核态，`status` 是履约状态。前者曾长期被前端挂在 `status` 这个名字下。

#### 规则 3 的落地要求

**每个列表的响应 VO 必须提供 `id`** —— 前端 `useTable` / `ProList` 用 `row.id` 做行键与详情跳转，缺了**不报错**，只是悄悄跳到 `/undefined`。

跨表派生字段（`customerName` / `ownerName` / `creator` / `quotationNo` 等）一律由 Service **批量**补齐，不要放在 Convert 里逐行查库（会 N+1）。

拼接类派生字段同理：`region`（`province`+`city`+`district`）由后端 `RegionText.join()` 生成后下发，前端在展示与回填两个方向都直接用。

#### 请求体解析失败的约定

字段类型不匹配（如把字典字段发成中文）会抛 `HttpMessageNotReadableException`。`GlobalExceptionHandler` 已单独兜这一类，返回 **400 + 指明「哪个字段、什么值、期望什么类型」**。

> 看到 `500「服务器内部错误」` 而不是 400，说明是**未预期的服务端异常**，不是参数问题 —— 别在请求体上瞎试。

### 1.9 导出与下载 ⭐

> 所有「导出」接口都走同一套约定，不是直接返回文件流。理解它才能理解前端下载弹窗的行为。

**保存形式与位置** —— 后端做两件事：

1. **序列化**：把查询结果写成 **Excel（xlsx）** 文件字节，与客户模块同一套
   `ExcelKit.write` 样式（`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`）。
2. **上传 OSS**：字节写入阿里云 OSS，对象 key 规则
   `crm/export/{yyyy}/{MM}/{uuid}.xlsx`（例 `crm/export/2026/09/3f2a9....xlsx`）。

接口响应体是 `CommonResult<String>`，`data` 字段就是**公网下载 URL**（`https://<bucket>.<endpoint>/crm/export/...`）。文件本体在 OSS 上，**不在本地磁盘**。

> 后端另有 `GET /xxx/export-xml`（SpreadsheetML `.xml`）端点，为历史兼容保留；前端导出按钮已统一走 `/export` 出 **xlsx**，不再使用 XML。

**下载形式** —— 前端拿到 URL 后，用户点「下载文件」时**经后端流式转发**下载：

- 前端调 `GET /system/export/download?url=<导出URL>&filename=<文件名>`（`responseType:'blob'`），
  后端把该 URL 反解成对象 key、打开 OSS 流转发，并用 `Content-Disposition` 写明**中文文件名**；
- 为什么不能直接 `<a href=OSS_URL download>` 或 fetch OSS URL：OSS 是跨域地址，浏览器对跨域的
  `download` 属性不生效（退回用 URL 末尾 uuid 当文件名），直接 fetch 又受 OSS CORS 限制 —— 同源转发是唯一可控文件名的做法；
- 落盘文件名 = 「当前页导出名」+ `.xlsx`：顶级菜单（`scope=all`）为 `页面名 + 导出`（如「客户导出」），
  子菜单胶囊为胶囊 label（如「我的关注客户」「我负责的合同」）。统一由 `utils/exportName.js` 的 `exportNameOf` 计算。

**前端交互**（统一收在 `components/ExportDownloadDialog.vue`）：导出成功后弹「导出成功」，
只有「下载文件」按钮触发下载；右上角 X 或「稍后再说」只关闭弹窗、不下载。
点「下载文件」触发下载后弹窗随即关闭，并向上 emit，父页面弹 `下载完成`。
⚠️ 早先用 `ElMessageBox.alert` 的 `callback` 会在**所有**关闭动作里触发，导致点关闭也下载 —— 已修掉。

## 二、认证模块 `/auth`

| 方法 | 路径 | 说明 | 认证 |
| :--- | :--- | :--- | :---: |
| GET | `/auth/captcha` | 获取算术验证码（密码登录前置，见 2.9） | ❌ |
| POST | `/auth/login` | 密码登录（需带算术验证码，见 2.9） | ❌ |
| POST | `/auth/email/code` | 发送邮箱验证码（60 秒限流） | ❌ |
| POST | `/auth/login/email` | 邮箱验证码登录 | ❌ |
| POST | `/auth/register` | 注册账号 | ❌ |
| POST | `/auth/password/forgot` | 忘记密码 | ❌ |
| GET | `/auth/me` | 获取当前用户信息 + 权限 + 菜单 | ✅ |
| PUT | `/auth/profile` | **修改个人资料**（顶栏「个人资料」）🆕 | ✅ |
| POST | `/auth/logout` | 退出登录 | ✅ |
| PUT | `/auth/password` | 修改密码 | ✅ |

### 2.1 登录

```http
POST /auth/login
Content-Type: application/json

{ "username": "admin", "password": "123456", "captchaKey": "9f2c...", "captchaCode": "7" }
```

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `username` | String | 是 | 登录账号 |
| `password` | String | 是 | 密码 |
| `captchaKey` | String | 见下 | 验证码标识，来自 2.9 |
| `captchaCode` | String | 见下 | 算术题的**计算结果**（数字字符串，可能是 `0`）|

> `captchaKey` / `captchaCode` 的**是否必填取决于验证码开关**（2.9）：
> 开关开启时必须传，关闭时不用传（传了也会被忽略）。
> 因为「必填」是运行时决定的，后端**没有**用 `@NotBlank` 做静态校验 ——
> 否则开关一关，前端不传这两个字段就会被参数校验拦成 `400`，
> 把一个「可关闭的功能」变成「关不掉的功能」。校验在 Service 里按开关判断，失败返回 `1008`。

**响应**：

```json
{
  "code": 0,
  "data": { "token": "b5f2a1c8-...", "expiresIn": 86400 }
}
```

> **校验顺序**：验证码 → 账号密码 → 账号状态。
> 验证码必须排在**验密码之前** —— 密码用的是 BCrypt（strength=10），
> 单次比对要烧 50~100ms CPU（这是故意设计得慢的）。验证码若放在密码之后，
> 攻击者每次请求都能逼服务器算一次 BCrypt，登录接口就成了 CPU 放大器。

**登录前必须校验 `sys_user.status`**（三种非正常态都要挡，不能只看密码对不对）：

| status | 含义 | 结果 |
| :--- | :--- | :--- |
| 1 | 正常 | ✅ 放行 |
| 2 | 禁用 | ❌ 返回 `1007`。**注册出来的账号就是这个状态**（见 2.4）|
| 3 | 离职 | ❌ 返回 `1007` |

> ⚠️ **别把「密码对」当成「能登录」**。刚注册的账号密码是对的，但 `status = 2`，
> 必须挡住 —— 否则「管理员分配角色后才启用」这条约束就形同虚设。
> 邮箱验证码登录（2.3）同样要校验。

### 2.2 发送邮箱验证码

```http
POST /auth/email/code
Content-Type: application/json

{ "email": "zhangsan@qq.com" }
```

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `email` | String | 是 | 邮箱地址，最长 128 字符 |

**响应**：`{ "code": 0, "data": null }`

**规则**：

- **60 秒限流**：同一邮箱 60 秒内重复请求返回 `1004 验证码发送过于频繁`。
  ⚠️ 邮箱按**小写归一化**后计限流 —— `A@x.com` 与 `a@x.com` 是同一个邮箱，
  不归一化的话换个大小写就能绕过。
- **验证码有效期 5 分钟**，验证通过后立即失效（不能重复使用）。
  一次性由 Redis Lua 脚本保证（比对与删除在同一段脚本里原子执行），
  杜绝「两个请求同时验同一个码」的双花。
- **不区分场景** —— 登录 / 注册 / 找回密码共用同一套验证码邮件。
  > 早先前端带过一个 `scene` 参数想区分三种模板，经确认没必要：多一个维度，
  > 后端就要多维护三套一模一样的模板配置。
- 邮箱不存在时**也返回成功**（不泄露「该邮箱是否注册过」）——
  究竟是「注册新号」还是「登录/找回」，由后续的 2.3 / 2.4 / 2.5 各自校验时报错。
  > ⚠️ 这一点很关键：注册接口（2.4）**会**明确告诉用户「该邮箱已被注册」，
  > 那是它必须做的；但**发码接口绝不能**做同样的判断，否则它就成了邮箱枚举器。
- **发信失败返回 `1009`，且会退还 60 秒限流** —— 用户没收到邮件时可以立刻重试，
  不会被白锁一分钟。超时 5 秒快速失败，不会把请求线程挂住。

**邮件内容**：主题「【AurumCRM】邮箱验证码」，正文含 6 位验证码，注明 5 分钟内有效、仅可使用一次。
发件人固定为配置的 163 邮箱（`spring.mail.username`）。

### 2.3 邮箱验证码登录

```http
POST /auth/login/email
Content-Type: application/json

{ "email": "zhangsan@qq.com", "emailCode": "123456" }
```

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `email` | String | 是 | 注册时预留的邮箱 |
| `emailCode` | String | 是 | 6 位验证码 |

**响应**：与 2.1 密码登录**完全一致**（`{ token, expiresIn }`），后续走同一套鉴权。

> 该邮箱在 `sys_user` 里查不到时返回 `1001 用户不存在`。
> 唯一性由 `uk_email (email, is_active)` 索引保证，正常不会命中多个账号。

### 2.4 注册账号

```http
POST /auth/register
Content-Type: application/json

{ "username": "zhangsan", "email": "zhangsan@qq.com", "emailCode": "123456", "password": "abc12345" }
```

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `username` | String | 是 | 登录账号，2–32 位，**全局唯一**，重复返回 `1005 账号已存在` |
| `email` | String | 是 | 邮箱，**全局唯一**，重复返回 `1010 该邮箱已被注册`；**必须通过 2.2 的验证码校验** |
| `emailCode` | String | 是 | 6 位验证码 |
| `password` | String | 是 | 6–20 位，服务端 BCrypt 加密后存 `sys_user.password` |

**响应**：`{ "code": 0, "data": null }`（**不自动登录**，前端引导用户回登录页）

> **邮箱是必填项**：注册流程走「先发邮箱验证码、再带 `emailCode` 提交」，
> 邮箱是这条链路的必要输入，同时也是之后登录 / 找回密码的凭据。
>
> **手机号不再参与注册**（原先是必填 + 短信验证）。`sys_user.phone` 仍在，
> 但只作为用户资料字段，由管理员在「人员管理」里维护。
>
> **校验顺序**：先查账号重复 → 再查邮箱重复 → 最后验码。
> 两次查重都排在验码之前，是因为验证码一次性 —— 先验码再报「已存在」等于白白烧掉用户收到的那封信。

#### 新注册用户的初始状态 ⚠️

**注册 = 投递申请，不是开通账号。** 落地时按这个来：

| 字段 | 初始值 | 说明 |
| :--- | :--- | :--- |
| `status` | **2（禁用）** | **关键**。注册后不能登录，见下 |
| `dept_id` | 空（或配置的默认部门）| 由管理员在分配角色时一并确定 |
| `superior_id` | 空 | 同上 |
| `sys_user_role` | **不写入任何行** | 角色由公司定，不能让注册者自选 |

**放行为两步，缺一不可**：

```
1. 管理员在「人员管理」里找到该账号（筛选「已禁用」）
2. 编辑 → 选角色（可同时补部门/直属上级）→ 保存，再点「激活」
```

**为什么要这样**：企业里的人是**先入职、角色已定**，才有账号。
自助注册只解决「申请」这一环，身份和权限必须由公司来定。
若注册后直接给默认角色，等于**任何人都能自己开账号进系统看客户数据** —— 那是权限漏洞。

**两个约束**：

- 注册后 `status = 2`，**登录会被 1007 挡下**（见 2.1）。别只校验密码。
- **激活一个没有任何角色的账号应当被拒绝**，提示「请先为该人员分配角色」。
  这样「有账号必有角色」就成了一条硬约束，而不是靠约定。
  > 补充在 `PUT /system/user/{id}/status` 上，见 3.1。

### 2.5 忘记密码

```http
POST /auth/password/forgot
Content-Type: application/json

{ "email": "zhangsan@qq.com", "emailCode": "123456", "newPassword": "abc12345" }
```

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `email` | String | 是 | 注册时预留的邮箱 |

### 2.9 算术验证码 🆕

```http
GET /auth/captcha
```

无请求参数。**未登录即可调用**（在白名单里）——登录页要先把题目显示出来，用户才可能算。

**响应**：

```json
{
  "code": 0,
  "data": {
    "enabled": true,
    "captchaKey": "9f2c8a1b4e6d4f0a9c3b2d5e7f8a1b2c",
    "captchaQuestion": "42 ÷ 6 = ?"
  }
}
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `enabled` | Boolean | 验证码开关是否开启。**前端必须先看这个字段** |
| `captchaKey` | String | 验证码标识。登录时原样带回 `POST /auth/login` 的 `captchaKey` |
| `captchaQuestion` | String | 题目文本，**纯文本直接显示**，不含任何标记语言 |

> ⚠️ **开关关闭时响应是 `{"enabled": false}`，`captchaKey` / `captchaQuestion` 会整个字段消失**
> （不是 `null`）—— 全局 Jackson 配了 `default-property-inclusion: non_null`。
> 所以前端只能靠 `enabled` 判断，不能靠 `captchaQuestion === null` 判断。

**规则**：

| 规则 | 取值 |
| :--- | :--- |
| 题型 | 四则运算（`+` `-` `×` `÷`）随机出 |
| 运算数 | **0 ~ 9**（含两端）|
| 除法 | **只出能整除的**。题面构造为 `(a×d) ÷ d = ?`，两个因数 `a`、`d` 都在 0~9 内，答案必然是整数 `a`；**除数恒 ≥ 1**（运算数虽含 0，但除数单独取 1~9，不会除以零）|
| 减法的被减数 | ≥ 减数，**不出负数** |
| 答案范围 | 0 ~ 81（`10 × 10` 不可达，因运算数上限是 9），**可能是 0**（如 `5 - 5 = ?`、`0 + 0 = ?`），前端校验要允许 |
| 除法被除数 | **允许超过 9**（最大 9×9 = 81）。它是两个因数相乘的产物，用户不需要填它，题面出现 `72 ÷ 9 = ?` 属正常 |
| 有效期 | 5 分钟 |
| 重试 | **一道题只能答一次** —— 答错也会立即作废，必须重新取题 |
| 作用范围 | **只用于密码登录（2.1）**。邮箱验证码登录、注册、忘记密码都不需要它 |

> ⚠️ 运算数含 0，因此会不时出现「6 × 0 = ?」「0 + 3 = ?」这类一眼出答案的送分题。
> 这是有意接受的 —— 见下方「安全局限」：题目本就明文下发，
> 防护强度靠的是**一次性消费**和**把校验挡在 BCrypt 之前**，不指望题目难度。
> 要收紧只需把 `AuthConstants.CAPTCHA_MIN` 改成 1。

> **为什么答错也作废**：算术题的答案空间很小（加减乘除的结果大致落在 0~100）。
> 若能对同一道题反复试，几轮就能蒙对，等于没有防护。
> 代价是用户算错一次就要换题 —— 所以前端在**登录失败时会自动刷新题目**，用户不会卡住。

### ⚠️ 安全局限（必须知道）

**题目是明文下发给前端的**，形如 `{"captchaQuestion": "3 + 5 = ?"}`。
一个会解析 JSON、能做四则运算的脚本可以**立刻算出答案并自动提交**，无需任何识别成本。

对比图形验证码：图形码至少要过一道 OCR 或图像处理，成本高得多。

所以算术题**挡得住的是「不解析页面、只会盲目重放账号密码」的最朴素脚本**，
不等于图形验证码的强度，**不要把它当作对等的防护**。

这是有意的取舍：换来了极好的用户体验（不用辨认扭曲字符）、零 AWT 依赖、
以及不消耗画图的 CPU。若将来需要更强防护，把本节的实现换回图形验证码即可 ——
接口形状（`captchaKey` + `captchaCode` + 一次性消费 + 开关）完全不用动，只换 `captchaQuestion` 的生成方式。

**开关**：`application.yml` 的 `aurum.auth.captcha.enabled`，默认 `true`。

```yaml
aurum:
  auth:
    captcha:
      enabled: true    # false 时 /auth/captcha 返回 enabled=false，登录不再校验
```

> 本地调试、演示、写集成测试时可以关掉，免得每次都真的算一遍。
> 关闭后前端会隐藏整个验证码输入行，登录接口不传 `captchaKey` / `captchaCode` 也正常放行。

**三态与两个展示字段的映射**（⚠️ 优先级固定，否则同时选中时结果不确定）：

```
入参合成：workStatus=="离职" → 3 ；否则 accountStatus=="已禁用" → 2 ；否则 → 1
出参拆开：status=1 → 在职 / 已激活      status=2 → 在职 / 已禁用      status=3 → 离职 / 已激活
```

> ⚠️ 传了**无法识别**的中文取值（如 `gender="外星人"`）后端会返回 **400**，不会静默写成默认值 ——
> 静默兜底会悄悄写错数据而前端看不出来。

**`PUT /system/user/{id}/status` 的额外校验** ⚠️：

| 目标状态 | 校验 |
| :--- | :--- |
| 1 激活 | **该用户必须已有至少一个角色**，否则拒绝并提示「请先为该人员分配角色」（错误码 `1106`）|
| 2 禁用 / 3 离职 | 无额外校验 |

> 这条校验是「有账号必有角色」的兜底。没有它，注册出来的账号可以被直接激活，
> 变成一个登录进去什么都看不到的「幽灵账号」。

**重置密码的响应** ⚠️：`POST /system/user/{id}/reset-password` 请求体为空对象 `{}`，
**新密码由后端生成并在响应里返回**（`{ "password": "xxxx" }`），前端需当场弹给管理员看 ——
库里只存 BCrypt 哈希，之后谁也再查不出来。同时会把该用户的所有会话踢下线。

**本期实现状态**：上表中前 9 个接口、`export`、`export-xml`、`import-template` **已实现**；
`import` **未实现**。

> ⚠️ 导出统一是「数据序列化 → 上传 OSS → 返回公网下载 URL」的模式（不是直接返回文件流）：
> - `export` 产出 **xlsx**（`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`）

| :--- | :--- | :--- | :--- |

```json
  "data": { "attachmentId": 1001, "fileName": "合同扫描件.pdf", "fileSize": 204800, "url": "/system/file/1001" }

```

**关联流程**（三步，注意第 1 步不传业务信息）：

```
1. 用户选文件 → POST /system/file/upload → 拿到 attachmentId
2. 单据保存时，把 attachmentId 追加进该业务记录的 attachment_ids
      · 新建单据：随 POST /{资源} 的请求体一起提交 attachmentIds
      · 已有单据：走业务自身的更新接口，如 PUT /crm/customer/{id}
3. 详情页渲染：读业务记录的 attachmentIds，逐个取附件信息
```

**哪些业务表带 `attachment_ids`**：`crm_customer`、`crm_contract`、`fin_invoice`
（客户详情「附件」Tab / 合同详情「附件」Tab / 财务开票回填）。
其它表需要时按同样方式加列。

> ⚠️ 早先 `sys_attachment.biz_type` / `biz_id` 是 `NOT NULL`，意味着**上传时就必须知道挂在哪张单据上**；
> 但实际交互是「先在弹窗里选文件、点保存时单据才落库」，那一刻单据 ID 还不存在。
> 因此把关联改到业务表的 `attachment_ids` 上，`sys_attachment` 的这两个字段**改为可空、仅作冗余**。
>
> 同理，`POST /finance/invoice/{id}/issue` 请求体里的 `attachmentIds` 语义是
> **「把这些附件挂到本发票上」**（即写进 `fin_invoice.attachment_ids`），不是新建附件 ——
> 上传在上一步已经做完了。

### 3.8 日志 🆕

对应原型「系统管理 → 登陆日志 / 操作日志」两页（注意原型写的是「登**陆**」）。
**两个都是纯查询接口，没有任何写入接口** —— 日志由后端自动记录，这是审计的基本要求。

| 方法 | 路径 | 权限点 | 说明 |
| :--- | :--- | :--- | :--- |
| GET | `/system/login-log` | `system:loginLog:list` | 登录日志分页列表 |
| GET | `/system/login-log/export` | `system:loginLog:export` | 导出登录日志 Excel（xlsx，上传 OSS 返回 URL）|
| GET | `/system/login-log/export-xml` | `system:loginLog:export` | 导出登录日志 XML/SpreadsheetML（.xml，上传 OSS 返回 URL）|
| GET | `/system/operation-log` | `system:operationLog:list` | 操作日志分页列表 |

> **菜单是隐藏的**：操作日志那条菜单（menu 77）`visible = 0`，由「登陆日志」页切 Tab 进入 ——
> 但接口权限点照常校验，不是靠隐藏菜单来保护的。

**通用请求参数**（两个接口一致，与其它列表页共用 `ProList` 组件）：

| 参数 | 类型 | 说明 |
| :--- | :--- | :--- |
| `pageNo` / `pageSize` | Integer | 分页，上限 500（见 1.4）|
| `keyword` | String | 模糊搜索。空串 = 不筛 |

- 登录日志的 `keyword` 匹配 **登陆人 / 工号 / IP**
- 操作日志的 `keyword` 匹配 **操作人 / 模块**

> 前端还会恒定带上 `scope=all` 与 `_t` 时间戳 —— 后端未声明这两个参数，
> Spring 会静默忽略，正好就是「未知参数不筛」。

**分页响应**：`{ list: [...], total: N }`，两个接口都按时间倒序（`时间 DESC, log_id DESC`）。
⚠️ 二级排序不是可有可无的：只按时间排，同一秒内的多条记录在不同次查询里顺序可能不同，翻页会串行。

#### 3.8.1 `/system/login-log` 登录日志

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `userName` | String | 登陆人（真实姓名）。**跨表取 `sys_user.real_name`**；登录失败且账号不存在时为空 |
| `username` | String | 工号（登陆账号）。⚠️ 邮箱验证码登录时入参只有邮箱，此列为空 |
| `phone` | String | 手机号码，**已脱敏**成 `138****8880`。跨表取 `sys_user.phone` |
| `loginTime` | DateTime | 登陆时间 |
| `ip` / `browser` / `os` | String | IP / 浏览器（含版本，如 `Chrome 120`）/ 操作系统 |
| `duration` | Number | **登陆时长（小时，1 位小数）**。`logout_time` 为空时该字段不下发（见下）|

> ⚠️ **`duration` 大量为空是常态，不是 bug。** 只有用户**主动点「退出登录」**才会回填
> `logout_time`；以下情况都不会，那些记录的时长永远算不出来：
> 直接关浏览器 / 关标签页、会话到期、以及 `forgotPassword` / `changePassword` 走的
> `StpUtil.kickout`（强制下线）。前端留空展示即可。
>
> ⚠️ **登录地点（`location`）恒为空**：需要 IP 归属地服务，项目没有接入。
> 表里有这一列只是为了将来要接时不用改表。

**写入时机**（无需前端参与）：

| 时机 | 说明 |
| :--- | :--- |
| 登录成功 | 写一条 `status=1`，并把 `log_id` 存进 Sa-Token Session，供登出时回填 `logout_time` |
| 登录失败 | 写一条 `status=0`。密码登录失败时 `user_id` 为 **null**（账号可能不存在）|
| 退出登录 | 用 Session 里的 `log_id` 回填 `logout_time` |

> ⚠️ **失败记录的 `msg` 有意统一。** 密码登录刻意让「用户不存在」与「密码错误」返回
> **同一个错误码 1002**（防账号枚举，见 2.1 的说明）。失败日志的 `msg` 因此对这两种情况
> **强制写成同一句话**「账号或密码错误」—— 否则这个日志页就成了现成的账号枚举工具。
> 新增失败分支时务必保持这个口径。

#### 3.8.2 `/system/operation-log` 操作日志

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `userName` | String | 操作人（表列 `oper_name`）|
| `module` | String | 模块（表列 `title`）。取 Controller 上的 Swagger `@Tag(name)` |
| `action` | String | **操作类型，已转中文标签**：新增 / 修改 / 删除 / 导出 / 查询 / 导入 / 其他 |
| `method` | String | 方法名（`类名.方法()`）|
| `params` | String | 请求参数 JSON，**已脱敏**（密码等字段是 `****`）|
| `ip` | String | IP地址 |
| `costMs` | Number | 耗时（毫秒）|
| `status` | String | **已转中文**「成功」/「失败」|
| `operateTime` | DateTime | 操作时间 |

> ⚠️ `status` **必须是中文**：前端 `#cell-status` 插槽靠 `value === '成功'` 判断标签颜色，
> 下发数字会让整列渲染成表示失败的红色。同理 `action` 转中文是按 1.8 的
> 「状态机枚举由后端转标签」口径处理的。

**自动记录的范围**：`controller` 包下**全部 POST / PUT / DELETE 方法**（20 个 Controller、72 个写接口），
由 `OperationLogAspect` 按 HTTP 动词切点自动覆盖 —— **不需要逐个方法加注解，漏标也不会漏记**。

**逐字化的标签**由 `@Log` 注解覆盖，用于自动推导不准的地方，例如：

```java
// POST 但语义是「审核」，不是「新增」
@Log(title = "合同", businessType = OperationBusinessType.UPDATE)
@PostMapping("/{id}/audit")
public CommonResult<Boolean> audit(@PathVariable Long id) { ... }
```

**三条安全约束**（改切面时必须守住）：

1. **参数必须脱敏**。`password` / `oldPassword` / `newPassword` / `emailCode` / `captchaCode`
   会被替换成 `****`（字段名比较忽略大小写）。**新增含凭证的字段时记得回来补白名单** ——
   漏一个就是把明文密码写进日志表。
2. **不记返回值**。成功时不写 `json_result`（体积 + 泄露风险）；失败时只写 `error_msg`。
3. **记日志失败不影响业务**。整个记录过程包在 try/catch 里，写不进去只打 warn。

> **已知的存储取舍**：文件上传接口的参数只记「文件名 + 大小」，不记内容；
> 参数 JSON 截断到 2000 字符。
>
> 另注：查询接口（GET）**不记录** —— 那是刻意的，否则每次刷新列表都会产生一条日志。

> 以 Knife4j 文档页 `http://localhost:8080/doc.html` 为准。

**`scope` 取数口径**（列表页顶部筛选胶囊，与角色数据权限是**交集** ——
只能在权限允许的范围内继续收窄，不能靠它越权）：

| 取值 | 胶囊 | 追加的条件 |
| :--- | :--- | :--- |
| `all` | 全部线索 | 不额外收窄（默认） |
| `mine` | 我负责的线索 | `owner_user_id = 当前用户` |
| `subordinate` | 下属负责的线索 | `owner_user_id IN (沿 sys_user.superior_id 逐级向下的全部下属，不含自己)` |
| `starred` | 我关注的线索 | `lead_id IN (当前用户在 crm_star 里关注过的线索)` |

未登记的 `scope` 取值返回 `400`，**不是**静默当作 `all` —— 前端加了胶囊而后端漏配时，
静默返回未过滤的数据会让人以为功能正常。

> `mine` / `subordinate` 无匹配时、`starred` 未关注任何线索时，返回**空分页**
> 而不是报错（筛选条件失效不该中断查询）。

**关注接口**：`POST` 关注、`DELETE` 取消关注，都是幂等的（重复关注 / 取消未关注的都不报错）。
刻意不做成单个 toggle 接口 —— toggle 在双击或重试下会把状态翻回去，让界面与库里相反。
两接口均返回 `CommonResult<Boolean>` 的 `true`；线索不存在时返回 `2001`。

**响应字段约定**：线索列表 / 详情的响应除 `leadId` / `leadName` 外，**还会带一份别名**
`id` / `name`（值相同）。前端的通用列表组件是全站复用的，它按 `row.id` 做行键
（详情跳转、勾选后的批量操作载荷都读它）、第一列的列 prop 固定为 `name`；
缺了别名，详情会跳到 `/crm/lead/undefined`、批量操作会发出 `undefined`。
`starred` 表示当前登录人是否已关注该线索。

> **`/{id}/star` 是 POST + DELETE 一对，不是 toggle** —— 刻意做成幂等的：
> 重复关注、取消一个没关注过的都不报错。toggle 语义在「连续点两下」或「多端同时点」时
> 结果取决于到达顺序，会翻错。线索侧（4.1）同一套设计。
> 响应体的 `starred` 字段在列表/详情里回填当前登录人的关注态。

> ⚠️ **权限是双层校验，两层失败的返回不同**：
> - **第一层 · 操作权限（接口级）**：缺权限返回 **403** + 「没有该操作权限：xxx」
>   （如 `sales` 角色没有 `crm:customer:delete`，调删除就 403）
> - **第二层 · 数据权限（行级）**：权限够了但**这条数据不在你的可见范围**，
>   返回的是 **2101「客户不存在」而不是 403** —— 有意不区分「不存在」和「看不到」，
>   避免变成 ID 探测器。列表接口不会报错，只是查不到那些行。
>
> 权限标识的权威来源是 `sys_menu.perms`（`sql/crm.sql`）。超管角色（`admin`）的
> permissions 被合成为 `*:*:*`，并由 `SaTokenConfig#overridePermissionMatching()`
> **显式**放行全部权限点。
>
> ⚠️ **别把 `*:*:*` 当成 Sa-Token 内建的「匹配一切」语法。** 它只是普通通配模式，
> 模式里的 `:` 是字面量，默认只能命中**三段式**权限码（`crm:lead:list`），
> 命中不了两段式的 `dashboard:view`。少了上面那处覆写，超管就会在
> **首页看板**上被 403 —— 而其余模块全部正常，极难定位（详见 `07-测试BUG记录.md` BUG-003）。
> 新增权限点请一律用三段式。
>
> 实现状态（2026-09-15 更新）：`CustomerController` 已实现

**报价单编号**

服务端生成，**请求体不接受该字段**（`QuotationConvert` 里显式忽略 `quotationNo`）：
保存时调编号引擎 `BusinessNumberService#next("QUOTE")`，按 `sys_numbering_rule` 的 `QUOTE` 规则出号 ——
`BJ` + `yyyyMMdd` + 4 位流水、**按日重置**，例 **`BJ202401010001`**。

> ⚠️ 内置 code（`LEAD` / `CUSTOMER` / `OPP` / `QUOTE` / `CONTRACT` / `PAYMENT` / `INVOICE`）的
> **前缀 / 日期格式 / 位数 / 重置周期是锁定**的：生成侧（`BusinessNumberServiceImpl.FIXED`）与
> 编号定义页（`NumberingRuleServiceImpl.enforceFixed`）两处都强制，**改 `sys_numbering_rule.prefix` 不生效**。
> 只有 `enabled`（启停）、`current_seq` / `current_period`（当前流水与周期）是运行时可变的。
>
> 编号的 CAS 更新与主单插入在同一个事务：落库失败时流水一起回滚，不会白占号。

**关联客户与商机的一致性校验** ⭐

`customer_id`（必填）与 `opportunity_id`（可空）都是逻辑外键。新增与修改**都会**校验：
商机若传了，它必须存在，且**与报价单是同一个客户**。

| 情况 | 结果 |
| :--- | :--- |
| 不传 `opportunityId`（直接给客户报价） | ✅ 允许 |
| `opportunityId` 指向的商机不存在 / 不在数据范围内 | ❌ `2201 商机不存在` |
| 商机所属客户 ≠ 请求里的 `customerId` | ❌ `2253 报价单的客户与所选商机不一致…` |

> 客户不一致刻意**拒绝而不是静默改写彼此**：改客户会连带改变数据权限与统计口径
> （与合同侧的 `2304` / `ContractRelationSupport` 同一取舍）。
> 前端 `views/crm/quotation/index.vue` 选中商机时会把客户对齐成商机的客户并置为只读，
> 所以正常操作撞不到 `2253`；这一关拦的是非 UI 调用与历史脏数据。

**报价单状态（对外只有 3 个标签，库里是 5 个码值）**

| 库值 | DDL 注释 | 对外标签 | 谁能写它 |
| :--- | :--- | :--- | :--- |
| 0 | 草稿 | 报价中 | —（历史数据，可读不再产生） |
| 1 | 已发出 | 报价中 | 新增报价单时 |
| 2 | 已接受 | **已生成合同** | `POST /crm/quotation/{id}/convert-contract` |
| 3 | 已拒绝 | 已失效 | —（历史数据，可读不再产生） |
| 4 | 已作废 | 已失效 | `POST /crm/quotation/{id}/void` |

> **状态只能由动作驱动，不能手改**：更新接口里的 `status` 只做「标签是否变化」的比对，
> 与当前库值的归并标签相同就不写库（防止一张 `0 草稿` 的单子被编辑一次就静默升级成 `1 已发出`）。
> 前端的表单里状态是**只读展示**。

**报价单选择器带产品明细**（`GET /crm/quotation/simple-list`）

每行在 `id / name / quotationNo / customerName` 之外**还带**：

| 字段 | 用途 |
| :--- | :--- |
| `products` | 与详情接口同一结构（含跨表补好的 `unitName`），没有明细时是**空数组**不是 `null` |
| `opportunityId` / `opportunityName` | 合同表单选中报价单后要把**商机一起对齐**成它上面的商机；只给 id 会让表单上的名称停在旧值 |
| `customerId` | 同上，客户也要对齐 |

**可选收窄参数**（都可空，不传即不过滤，与改动前行为一致）：

| 参数 | 含义 |
| :--- | :--- |
| `opportunityId` | 只列该商机的报价单 —— 合同表单选了商机时传它 |
| `customerId` | 只列该客户的报价单 —— 合同表单没选商机时按客户传 |

合同表单的「报价单编号」选择器靠这些做回显与过滤 —— 选中一张报价单后，前端把 `products`
**整份**填进合同的产品明细，并把商机/客户对齐（`crm-ui` 的
`views/crm/contract/form-config.js`）。只给 `id / name / quotationNo` 的话，选完报价单
产品的位置会一直空着，而接口是 200、界面也不报错，很难从后端日志上看出来。

> ⚠️ 代价是选择器响应不再「精简」：一页 10 条报价单会带上各自最多 200 行明细
> （`ItemSupport.MAX_ITEMS`）。真成为问题时，再改回让前端选中后单独调一次
> `GET /crm/quotation/{id}`（详情返回的就是同一份 `products`）。

**报价单转合同**（`POST /crm/quotation/{id}/convert-contract`）

```json
{ "code": 0, "data": 3001 }
```

`data` 是**新生成的合同 ID**。行为：

1. 按报价明细生成一份**合同草稿**（编号由 `CONTRACT` 编号规则生成，明细金额按《02-建表文档》3.6 重算，
   `amount = Σ 明细`，`auditStatus = 0 待提审` / `status = 0 草稿`）；
2. **报价单状态转为「已生成合同」**（库值 `2`）；
3. 合同上的 `quotation_id` 指回报价单 —— 列表的「关联合同」列就是按它反查的（1:N，只显示最新一份）。

| 情况 | 结果 |
| :--- | :--- |
| 报价中（0/1）、已生成合同（2） | ✅ 允许。**重复转换是允许的**：一个报价单可以出多份合同 |
| 已失效（3/4） | ❌ `2252 当前报价单状态不允许该操作` |
| 报价单没有产品明细 | ❌ `2252`（合同明细不允许为空，不能造一张空合同） |
| 报价单不存在 / 不在数据范围内 | ❌ `2251 报价单不存在` |

**作废**（`POST /crm/quotation/{id}/void`）→ `{ "code": 0, "data": true }`

状态落到库值 `4 已作废`（对外「已失效」）。**只有「报价中」可以作废**：
已生成合同的单子已经有下游合同，应当先去处理合同；已失效是终态。两者都返回 `2252`。

> **金额口径**：合同保存时后端根据明细重算 `amount`；提交审核时再次校验
> `amount == Σ contract_item.amount`，不一致直接拒绝（错误码 `2302`）。
> 计算口径见《02-建表文档.md》3.6 节：**先逐行四舍五入，再汇总**。

**关联字段（客户 / 商机 / 报价单）的一致性校验** ⭐

`crm_contract` 上这三列都是逻辑外键：`customer_id` NOT NULL，`opportunity_id` / `quotation_id`
**可空**（可以直接挂在客户上、也可以从商机或报价单来）。新增与修改**都会**过这一关，
口径集中在后端 `support/ContractRelationSupport`：

| 情况 | 结果 |
| :--- | :--- |
| 三个都为空（客户直签合同） | ✅ 允许 |
| `quotationId` 指向的报价单不存在 / 不在数据范围内 | ❌ `2251 报价单不存在` |
| `opportunityId` 指向的商机不存在 / 不在数据范围内 | ❌ `2201 商机不存在` |
| 报价单 / 商机所属客户 ≠ 合同的 `customerId` | ❌ `2304 合同的客户与所选商机 / 报价单不一致…` |
| 报价单挂了商机，但请求里的 `opportunityId` 与它不同 | ✅ 保存时**以报价单为准**对齐 `opportunity_id` |
| 报价单没挂商机，请求里另有 `opportunityId` | ✅ **保留**请求里的商机（不会抹成 null） |

> 客户不一致刻意**拒绝而不是静默改写**：改客户会连带改变数据权限（谁还能看见这张合同）
> 与统计口径。报错文案已提示怎么改（重选一次报价单即自动对齐）。
> 前端 `views/crm/contract/form-config.js` 的联动规则与本表逐条对应（选商机带出客户、
> 选报价单对齐商机与客户），正常情况下用户不会撞到 `2304`。

**审批进度** ⭐ `GET /crm/contract/{id}/approval`

合同审核期间 `auditStatus` **一直是「审核中」**（`CONTRACT_AUDIT` 是两级流：部门主管 → 财务，
只有最后一个节点通过才会变成「审核通过」）。所以列表上的「审核中」**答不出「现在该谁审」** ——
这个接口把审批实例与任务翻译成可读的流程。权限与详情一致（`crm:contract:list`），不新增权限点。

```json
{
  "code": 0,
  "data": {
    "contractId": "2099451961604145152",
    "contractNo": "HT20260914000002",
    "contractName": "aaa",
    "auditStatus": "审核中",
    "flowName": "合同审核流",
    "instanceId": "2099479714317479936",
    "instanceStatus": "审批中",
    "applyUserName": "赵财务",
    "applyTime": "2026-09-14 20:45:45",
    "currentNodeOrder": 2,
    "currentNodeName": "财务审批",
    "pendingApproverNames": ["赵财务", "陈会计"],
    "nodes": [
      {
        "nodeId": "1", "nodeOrder": 1, "nodeName": "部门主管审批",
        "approveType": "或签", "approverType": "发起人直属上级",
        "progress": "已通过", "pendingApproverNames": [], "predictedApproverNames": [],
        "tasks": [{
          "taskId": "2099479714820796416", "approverId": "1", "approverName": "超级管理员",
          "taskStatus": "已办", "approveResult": "通过", "comment": "",
          "handleTime": "2026-09-14 20:46:29", "createTime": "2026-09-14 20:45:45"

      },
      {
        "nodeId": "2", "nodeOrder": 2, "nodeName": "财务审批",

          { "taskId": "2099479899978346496", "approverId": "5", "approverName": "赵财务",

```

> 上面这条是**停在第二个节点（最后一步）**的样子，所以没有 `next*` 字段。若合同还停在第一个节点，
> 同一份响应会多出 `"nextNodeOrder": 2, "nextNodeName": "财务审批",
> "nextApproverNames": ["赵财务","陈会计"]`，并且 `nodes[1].predictedApproverNames` 也是这两个人。

字段口径：

| 字段 | 取值 | 说明 |
| :--- | :--- | :--- |
| `auditStatus` | 未提交 / 审核中 / 审核通过 / 审核拒绝 | 合同审核态，取自 `crm_contract.audit_status`，与列表、详情**完全一致**（`ContractAuditStatus`） |
| `instanceStatus` | 审批中 / 已通过 / 已驳回 / 已撤销 | 审批**实例**状态（`sys_approval_instance.status`）；无实例时为 `null` |
| `currentNodeName` / `pendingApproverNames` | 如「财务审批」/ `["赵财务","陈会计"]` | **「现在该谁审」的答案**；非「审批中」时 `currentNodeName` 为 `null`、列表为空 |
| `nextNodeName` / `nextApproverNames` | 如「财务审批」/ `["赵财务","陈会计"]` | **「下一步到谁」**：当前节点之后**第一个**节点的名称与**预计**审批人；已是最后一步、或流程未进行/已结束时为空（`non_null` 下不出现） |
| `nodes[].predictedApproverNames` | 姓名数组 | **预计审批人**：只在该节点 `progress = 未开始` 时有值，与 `pendingApproverNames`（真实待办人）**不要混用** |
| `nodes[].progress` | 未开始 / 待审批 / 已通过 / 已驳回 / 已跳过 | 把该节点全部任务**归并**后的一句话（`ApprovalNodeProgress`）；或签节点「1 人已办 + N 人已跳过」= **已通过** |
| `nodes[].approveType` | 或签 / 会签 / 依次 | 节点审批方式 |
| `nodes[].approverType` | 指定用户 / 指定角色 / 部门主管 / 发起人直属上级 / 发起人本人 | 节点审批人来源 |
| `tasks[].taskStatus` | 待办 / 已办 / 已跳过 | 任务级状态（`DictLabels`）；「已跳过」= 或签节点被别人处理掉了 |
| `tasks[].approveResult` | 通过 / 驳回 / 撤销；未处理为 `null` | 审批结果 |

其余约定：

1. **没有审批实例也会返回东西**：草稿（未提交）或演示数据遗留时，`nodes` 用**当前启用的模板**渲染，
   全部「未开始」——至少能看出这条合同要走几步；`flowName` 取模板名。
2. **`abnormalHint`**：数据不一致时给出人话说明，正常为 `null`。三种情形：
   ① 合同「审核中」但**没有审批实例**（演示库 `HT20260003` 就是这种：任何审批动作都会返回
   `4003 审批实例不存在`，需重新提交审核）；② 实例已结束但合同仍「审核中」；
   ③ 实例进行中但合同审核态不是「审核中」。**接口只报事实，不做任何自愈写库。**
3. **只展示最近一个实例**：同一合同驳回后重新提交会新建实例（历史实例保留），本接口只回最新那条。
4. **节点以模板现状为准**：模板被改过（节点删了/改名了）时，仍停留在旧节点的实例用任务上的
   `node_name` 快照补出那一步，不会出现「当前节点：财务审批」但列表里没有这一步的错乱。
5. `pendingApproverNames` 依赖跨表查 `sys_user` 姓名；账号取不到姓名时该名字会被略过，
   **权威身份看同节点的 `tasks[].approverId`**。
6. **预计审批人是怎么算出来的**：与真实解析（`resolveApprovers`）**同一套规则** ——
   指定用户取 `approver_value`、指定角色取 `sys_user_role` 的成员、部门主管与发起人直属上级
   都取**发起人的直属上级**、发起人本人即发起人。所以它是**预计**：组织架构、角色成员、
   流程配置变了都会不同，**不要当成承诺**。解析不出人时给空数组 —— 那意味着**配置有问题**
   （角色下没成员 / 发起人没有直属上级），真走到那一步会因「审批节点没有解析出审批人」失败。
7. **只预测「还没到达」的节点**（`nodeOrder > currentNodeOrder`），因此当前节点的待办人
   永远看 `pendingApproverNames`。
8. 响应遵循全局 `non_null`：值为 `null` 的字段不会出现在 JSON 里，前端请按「字段可能不存在」写。

> **`/crm/contract/audit-list`（待审核列表）** 每一行额外回填（只在待审核视图回填，
> 主列表与导出没有）：
>
> | 字段 | 含义 |
> | :--- | :--- |
> | `currentNodeName` / `pendingApproverNames` | 当前环节与它的待办人 —— 「现在该谁审」 |
> | `nextNodeName` / `nextApproverNames` | 下一步的节点与**预计**审批人 —— 「下一步到谁」 |
> | `applyUserName` / `applyTime` | **提交人 / 提交时间**（审批实例的发起人与发起时间）—— ⚠️ 不是 `creator` / `createTime`（建单人、建单时间），单据可以甲建乙提交 |
>
> 让审批人在列表上就能看到「当前：财务审批 · 待 赵财务、陈会计」「下一步：财务审批 · 预计 赵财务、陈会计」。
> 该接口的过滤条件本身没变（仍是 `audit_status=1`）。前端页面：合同审核页的这两列 +
> 「审批进度」弹窗、合同详情页的「审批进度」Tab（共用 `views/crm/contract/ApprovalProgress.vue`）。

#### 一票多回款

发票是**一张票合并多笔回款**：`fin_invoice_payment` 是回款明细的唯一事实来源，
`fin_invoice.payment_id` 只是「主回款」（取首条明细），仅供展示与索引。

金额口径全部是**含税**，与 `fin_payment.amount` 一致。服务端按发票级税率
**逐行取不含税、四舍五入后再汇总**，税额取残差，以保证
`total_amount = amount + tax_amount` 精确成立（见《02-建表文档.md》）。

**新增/修改请求体**：

```json
{
  "invoiceType": 1,
  "taxRate": 6.00,
  "applyDate": "2026-09-14",
  "remark": "合并两笔回款",
  "items": [
    { "paymentId": 2, "writeOffAmount": 50000.00 },
    { "paymentId": 5, "writeOffAmount": 12000.00 }
  ],
  "invoiceTitle": "上海鸿远物流有限公司",
  "taxNo": "91310115MA1KXXXX3C",
  "bankName": "中国工商银行上海浦东支行",
  "bankAccount": "6222021234567890123",
  "invoiceAddr": "上海市浦东新区世纪大道 200 号",
  "invoicePhone": "021-58880001",
  "attachmentIds": [1001]
}
```

> ⚠️ 请求体里**没有 `customerId`，也没有任何金额汇总字段**：客户由所选回款推导
> （明细必须同客户），`amount` / `taxAmount` / `totalAmount` 由服务端按明细算。
> 让前端同时传客户和回款、或传金额，只会制造「两者不一致」的新失败模式。

> ⚠️ 后六个字段是**客户开票信息的快照**：选中客户时从客户默认开票信息带出、
> 允许用户改动，落库后即与客户档案解耦 —— 客户日后改了抬头，历史发票不会跟着变。

**校验与错误码**（`create` / `update` 同一套规则）：

| 错误码 | 触发条件 |
| :--- | :--- |
| `3103` | `items` 为空 |
| `3104` | 回款不存在 / 已删除 / 非「审核通过 + 已确认」 |
| `3105` | 所选回款不属于同一客户 |
| `3106` | 累计开票金额超过该回款可开余额（消息含回款编号与剩余可开额） |
| `3107` | 单行 `writeOffAmount <= 0` |
| `3108` | 同一笔回款在同一张票里出现多次 |
| `3109` | `taxRate` 不在 `[0, 100]` |

> ⚠️ 「累计」是**跨发票**的：同一笔回款可被多张发票分摊，但合计不得超过回款金额。
> 已作废发票（`status = 2`）的明细保留作审计轨迹，但不计入占用，故作废后额度自动释放。

> `invoiceInfo` 为 `null` 表示该客户尚未维护开票信息，前端应把六个字段留空让用户手填。
> `payments` 只含 `remainingAmount > 0` 的回款，且**受数据权限约束** ——
> 不能给同事负责的回款开票。权限码为 `fin:invoice:create` 或 `fin:invoice:update`（OR）。

**开票请求体**：

```json
{
  "invoiceNo": "04512345",
  "issueDate": "2026-09-12",
  "attachmentIds": [1001, 1002]
}
```

> ⚠️ 《02-建表文档.md》特别强调：**申请编号 `applyNo` 与实际发票号 `invoiceNo` 是两个字段**。
> 申请时只有 `applyNo`，财务开票后才回填 `invoiceNo`。

**财务拒绝**（`POST /finance/invoice/{id}/reject`）—— 与开票是同一环节的两个出口，
权限码同为 `fin:invoice:issue`（不新增菜单行，两个按钮都长在「财务开票」待办页上）。

```json
{ "comment": "抬头与营业执照不一致，请核对后重新提交" }
```

前置条件与开票对称：只有「已通过 + 待开票」的单子可被拒绝，落在 `auditStatus = 3 已驳回`、
`status` 保持 `0`。驳回后单子回到申请人手里，`PUT` 可编辑、`submit` 可重新提审 —— 闭环成立。

| 情况 | 结果 |
| :--- | :--- |
| `auditStatus /= 2` 或 `status /= 0` | ❌ `400 该发票当前不可拒绝` |
| `comment` 为空 | ❌ `400 拒绝时必须填写拒绝原因`（`@NotBlank` 已拦，服务端再兜一次）|

> ⚠️ **`comment` 只校验、不落库**：`fin_invoice` 没有审核意见列，与回款审核
> （`PaymentServiceImpl#audit`）现状一致。要真正留存需先给 `fin_invoice` 加列，届时回款那边
> 也该一起补 —— 不要只在这一个点上做对，那会让两处语义不对称。
>
> ⚠️ **拒绝不释放回款额度**：`fin_invoice_payment` 明细刻意保留，被占用的开票额度继续占着。
> 若退回即释放，申请人返工期间同一笔回款会被别人再开一张票，两张票合计超开。
> 要释放额度请走删除发票（`DELETE /finance/invoice/{id}`）。

> 2. **通知 / 公告**（`notice_type=2/3`）：管理员在「公告/通知管理」发布写入（复用 `sys_notice`）。
> 3. **任务提醒**（`notice_type=4`）：由**定时任务**生成 —— 每天凌晨 03:05（`NoticeReminderJob`）
>    扫描 `crm_customer.next_contact_time < 今天` 且 `deal_status=未成交` 且 `owner_user_id` 非空的客户，
>    为每个归属人生成一条「客户待回访」任务提醒（`receiver_id=归属人`，幂等：同一客户只生成一次）。
>
> 前端首页的「消息」区块因此同时展示审批 + 待办（待回访）提醒两类；
> 点单条消息若带 `link` 则跳详情，无 `link` 的纯提醒（如待回访）只展示不可跳。

### 9.8 `/dashboard/trend` 业绩趋势

**请求参数**

## 十、通用选择器接口约定 ⭐

原型里的「选择客户 / 选择商机 / 选择报价单 / 选择角色人员 / 负责人」**本质是同一个组件**，
后端也统一为一套接口模式：

```
GET /{模块}/{资源}/simple-list
```

| 参数 | 说明 |
| :--- | :--- |
| `pageNo` / `pageSize` | 分页 |
| `keyword` | 关键字搜索 |
| 其他过滤条件 | 因资源而异 |

**返回精简字段**（只返回选择器需要的，避免传输大对象）：

```json
{
  "code": 0,
  "data": {
    "list": [
      { "id": 100, "name": "北京星辰科技", "extra": "张三 / 138****8888" }
    ],
    "total": 50
  }
}
```

**⚠️ 强烈建议：不要用 `extra` 拼接字符串，直接返回结构化字段。**

原因：`extra` 的格式由各资源的业务决定，用 ` / ` 拼成一串之后，
**调用方只能按位置硬解析**，一旦某个资源改了字段顺序或某字段为空（变成 `null` 还是空串？），
前端就会错位。而且产品选择器需要 4 个字段，用字符串表达已经很勉强了。

**推荐形态**（示例为产品，其余资源按需给）：

```json
{
  "code": 0,
  "data": {
    "list": [
      { "id": 100, "name": "CRM 标准版",
        "unitId": 3, "unitName": "套",
        "salePrice": 29800.00, "costPrice": 8000.00, "taxRate": 6.00 }
    ],
    "total": 50
  }
}
```

> 产品这几项是**必须**的：前端「明细行编辑器」（报价单/合同/商机的产品明细）选了产品之后
> 要自动带出单位、售价、成本价，只给 `{id, name}` 是带不出来的。
> ⚠️ `salePrice` 对应 DDL 里的 `crm_product.price`（不是 `sale_price`），`costPrice` 是 `cost_price`。
> `costPrice` 受字段权限保护（非授权角色返回 `null`），前端要能显示成 `--`。

**覆盖的选择器**（前端 `constants/selectorRegistry.js` 实际共 12 类）：

## 十三、AI 小助手 `/ai`

> 后端配置见 `crm-server/src/main/resources/application-dev.yml` 的 `ai:` 块。
> **未配置 api-key 时接口返回 5006**，前端据此隐藏入口 —— 缺配置不影响其余功能，
> 这也是它和 OSS 配置（缺了直接启动失败）的不同之处。

### 13.1 `/ai/chat/stream` 流式对话

| 项 | 内容 |
| :--- | :--- |
| 方法 | `POST` |
| 路径 | `/ai/chat/stream` |
| 权限 | `ai:chat:use` |
| 请求头 | `Content-Type: application/json`（**不要加 `Accept`**，原因见本节末尾）|
| 响应 | `text/event-stream`（**不套 `CommonResult`**；返回类型是 void，响应体由后端直接写）|

**请求体**

```json
{
  "sessionId": null,
  "content": "我现在有多少待处理的线索？"
}
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `sessionId` | string \| null | 会话ID。**首次对话传 `null`**，服务端会新建并通过 `meta` 事件把新 ID 回传；传了已过期/不存在的 ID 同样会新建，**不报错** |
| `content` | string | 本轮提问，最长 4000 字 |

> **会话历史存在服务端 Redis，前端不上传历史。**
> 这比早先「前端把完整上下文传上来」的做法好两处：上下文**不可伪造**
> （以前客户端能塞任意 assistant 消息、甚至伪造 `system` 角色去顶掉系统提示词），
> 且请求体恒定大小、不随对话变长而膨胀。
>
> **存储形态**：`ai:chat:msg:{userId}:{sessionId}`（消息 List）+ `ai:chat:index:{userId}`
> （会话摘要 Hash），**7 天闲置过期**、单会话最多保留 50 条。
> 键前缀绑死当前登录用户 —— 传别人的 sessionId 只会查到自己名下的空键，
> 拿不到别人的对话。三个参数都在 `ai:` 配置块里（`session-ttl-days` / `session-max-messages`）。

**SSE 帧协议** ⚠️

帧与帧之间以**两个 LF（`\n\n`）**分隔，每帧形如（注意 `data:` 后是一行 JSON，再跟一个空行）：

```
event: delta
data: {"content":"客户"}

```

| event | data | 说明 |
| :--- | :--- | :--- |
| `meta` | `{"model":"deepseek-chat","sessionId":"a1b2…"}` | 开场。**`sessionId` 必须采纳** —— 首次提问、或手里的 ID 已过期时，服务端会在这里告知本轮实际用的会话；漏掉它，下一轮就又变成新会话了 |
| `delta` | `{"content":"…"}` | 正文**增量**（不是全量，前端要自己拼接）|
| `tool` | `{"name":"search_customers","status":"running"}` | 工具调用开始 / 结束，`status` 为 `running` 或 `done` |
| `done` | `{"finishReason":null,"usage":{"promptTokens":…,"completionTokens":…,"totalTokens":…}}` | 正常结束 |
| `error` | `{"code":5001,"message":"…"}` | 流中途失败 |
| `ping` | `{}` | 心跳。静默期（首 token 前、工具执行中）每 15 秒补一个，防止连接被中间设备掐断 |

**SSE 帧协议** ⚠️

帧与帧之间以**两个 LF（`\n\n`）**分隔，每帧形如（注意 `data:` 后是一行 JSON，再跟一个空行）：

```
event: delta
data: {"content":"客户"}

```

| event | data | 说明 |
| :--- | :--- | :--- |
| `meta` | `{"model":"deepseek-chat"}` | 开场，告知本次使用的模型 |
| `delta` | `{"content":"…"}` | 正文**增量**（不是全量，前端要自己拼接）|
| `tool` | `{"name":"search_customers","status":"running"}` | 工具调用开始 / 结束，`status` 为 `running` 或 `done` |
| `done` | `{"finishReason":null,"usage":{"promptTokens":…,"completionTokens":…,"totalTokens":…}}` | 正常结束 |
| `error` | `{"code":5001,"message":"…"}` | 流中途失败 |
| `ping` | `{}` | 心跳。静默期（首 token 前、工具执行中）每 15 秒补一个，防止连接被中间设备掐断 |

**错误返回的位置** ⚠️

见 **1.5 节**末尾的说明：权限 / 参数 / 5005 / 5006 是**流开始前**的普通 JSON，
5001 / 5002 只能走 `event: error`。客户端必须同时处理这两种形态。

写客户端时有两个**实测踩到过**的坑，务必注意：

1. **不要发送 `Accept: text/event-stream`。**
   `Accept` 作用于该请求的**所有**响应，包括错误响应。一旦它只允许
   `text/event-stream`，`GlobalExceptionHandler` 就无法把 `CommonResult` 渲染出来，
   结果是 **HTTP 500 + 空响应体**（连 `content-type` 都没有），
   调用方只能看到「500」，完全看不出真实原因（明明是 403 权限不足）。
   实测：带该头 → 403 变成 500 空响应；去掉 → 正常拿到 403 JSON。
   SSE 本身不要求请求方声明 `Accept`，省略即可。

2. **不要只看 HTTP 状态码判断成败。**
   本项目对业务错误沿用统一约定：**HTTP 状态码仍是 200**，真正的错误在 JSON body 的
   `code` 字段里（如 `{"code":403,"message":"没有该操作权限：ai:chat:use"}`）。
   所以客户端应当**按 `Content-Type` 分流**：是 `text/event-stream` 才走 SSE 解析，
   否则当作普通 JSON 错误处理。
   只判断 `res.ok`（或只看状态码）的话，错误响应会被当成正常的 SSE 流去读 ——
   里面一帧都没有，所有回调都不触发：用户点发送后**什么都没发生**，
   既没有回答也没有报错，比直接报错还难排查。

### 13.2 会话管理

三个普通 JSON 接口（走 `CommonResult` 包装），都需要 `ai:chat:use` 权限。

| 方法 | 路径 | 说明 |
| :--- | :--- | :--- |
| GET | `/ai/sessions` | 我的会话列表，按最后活跃时间倒序 |
| GET | `/ai/sessions/{id}/messages` | 某个会话的全部消息（时间正序）|
| DELETE | `/ai/sessions/{id}` | 删除会话（消息与索引一起删）|

> ⚠️ **方法那一格不要加反引号**，写成 `| GET |` 而不是 `` | `GET` | `` ——
> `gen:api-status` 用严格的正则 `^\|\s*(GET|POST|…)\s*\|` 抽表格行，加了反引号
> 整行会被跳过，于是接口总数少算、还会误报「文档里没有」。
> （`check:api` 用的是宽松的子串匹配，发现不了这个错误 —— 两个脚本要一起跑。）

> 路径里的 `{id}` 是**会话ID（sessionId）**。本文档统一用 `{id}` 作占位符（与
> `/crm/lead/{id}` 一致）—— `npm run check:api` 会把前端的 `{xxx}` 归一成 `{id}`
> 后与文档做**字面匹配**，写成 `{sessionId}` 会被判成「文档里查不到」。

**`GET /ai/sessions` 响应**

```json
{
  "code": 0,
  "data": [
    {
      "sessionId": "a1b2c3d4e5f6",
      "title": "我现在有多少待处理的线索？",
      "lastActive": 1768000000000,
      "messageCount": 6
    }
  ]
}
```

列表**不返回消息正文** —— 会话多了以后那是几 MB 的无用载荷，列表只需要标题和时间。
`title` 由首轮提问截断而来（前 30 字）。

> 刻意不做「让模型生成标题」：那会多一次调用（多花钱、多一次失败可能），
> 而绝大多数情况下用户第一句话本身就足够认出这是哪次对话。

**`GET /ai/sessions/{id}/messages` 响应**

```json
{
  "code": 0,
  "data": [
    { "role": "user", "content": "…", "tools": null, "ts": 1768000000000 },
    { "role": "assistant", "content": "…", "tools": ["search_leads"], "ts": 1768000001000 }
  ]
}
```

只存用户看得见的 `user` / `assistant` 两类消息；`tools` 是这一轮用过的工具名，
用于刷新后重新渲染「查询线索」这类小胶囊，与实时对话时的观感保持一致。

> **越权与「不存在」都返回空**：传别人的 `sessionId` 不会报错，返回**空列表**
> （删除同理，静默无操作）。有意不返回 404/403 —— 那等于给出
> 「这个 ID 存在但你没权限」这种可用于探测的反馈。

### 13.3 可用的工具

模型通过 function calling 调用下表工具。**全部只读**，且**全部走现有 Service** ——
因此行级数据权限（`DataPermissionInnerInterceptor`）自动生效：
销售专员问「所有客户」，拿到的只是他权限范围内的那些。

#### ⚠️ 工具按登录人的权限点过滤（2026-09-15 新增）

`AiToolRegistry.specs()` **只把当前登录用户有权限的工具发给模型** —— 没权限的工具，
模型根本不知道它存在，也就不会去调。过滤走
`SaTokenConfig#overridePermissionMatching()` 覆写过的权限匹配，所以：
超管的 `*:*:*` 自动拿到全部；角色被授予 `crm:lead:*` 这类部分通配时同样生效。

- 权限点取自工具声明的 `permission()`，值都是 `sys_menu.perms` 里现成的码，见下表
- `AiToolRegistry.execute()` 会**再校验一次**（纵深防御）：模型幻觉出一个它「记得」的
  无权工具名时，照样拒绝，不会因为名字在册就放行
- **函数权限与行级权限是交集**：既要用户有功能权限，查出来的行也仍受数据权限限制
- ⚠️ 两个日志工具和 `search_users` 查的表**不在数据权限白名单里**，行级过滤对它们不生效
  —— `permission()` 是唯一闸门，而这两个权限码在种子里**只授给了超管**

> ⚠️ `get_dict_data` 比 HTTP 接口**更严**：`GET /system/dict-data/batch` 对所有登录用户开放
> （前端下拉要用），而 AI 工具要 `system:dict:list`（种子里仅超管）。这是刻意的 ——
> 「AI 能问出系统里有哪些字典项」和「前端能渲染下拉」是两回事。

工具返回统一信封（**详情类工具也套同一层**，只有一行）：

```json
{ "total": 137, "returned": 5, "truncated": false, "rows": [ { "…": "…" } ] }
```

- `total` 是符合条件的**总数**，`rows` 只是当前页（单次最多 10 行、最多第 5 页）
- `truncated=true` 表示结果超出体积上限被截断，此时 `hint` 会说明该怎么办
- **工具执行失败不会中断对话**：错误会作为工具结果回灌给模型，让它自行纠正
- 金额类字段对无权限角色为空（沿用首页看板的字段权限规则），非空即为有权限
