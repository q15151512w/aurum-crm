## 一、项目一句话

**AurumCRM 是一套基于 LTC（Leads to Cash）全流程的企业级客户关系管理系统**，
覆盖「线索 → 客户 → 商机 → 报价 → 合同 → 回款 → 发票」完整销售链路，
并在其上叠加了**自研审批流引擎**、**DAO 层数据权限**与**AI 智能助手**三项自研能力。

## 二、业务范围与核心链路

**主链路**

```
营销活动 → 线索 →（分配 / 领取）→ 归属流转
                                    ↓ 超期未跟进
                                  线索池 →（领取）→ 线索
                                    ↓ 转化
                                  客户 → 联系人 / 跟进记录 / 商机 / 工单
                                    ↓
                                  商机 →（阶段变更）→ 报价单
                                    ↓
                                  合同 →（提交审核）→ 【审批引擎】→（通过）→ 生效
                                    ↓
                                  发票 / 回款 → 核销

客户 →（超期未跟进）→ 公海 →（领取）→ 客户
```

**两条资源回收支线**：线索进**线索池**、客户进**公海**，均支持管理员「分配」与员工「领取」两种再分配方式。

**两条审核线**：合同审核、财务审核（回款审核 / 开票）。

**核心状态机**

| 单据 | 状态字段 | 流转 |
|---|---|---|
| 报价单 | `status` 5 值 → 对外 3 标签 | 草稿/已发出→报价中；已接受→**已生成合同**；已拒绝/已作废→已失效 |
| 合同 | **两个正交字段** | `audit_status`：待提审→审批中→(全节点通过)已通过 / (任一驳回)已驳回<br>`status`：草稿→已生效 / 已作废 / 已到期 |
| 发票 | `status` + `audit_status` | 待开票→(财务开票回填 `invoice_no`)→已开票→已作废 |
| 回款 | `status` + `audit_status` | 待确认→(审核通过)→已确认→已作废 |

> **合同的 `audit_status` 与 `status` 刻意不合并** —— 审批状态与单据生命周期是两个正交维度，
> 合并会立刻产生「已作废但审批中」这类非法状态。

## 四、三大核心技术点 ★

### 1. 数据权限在 DAO 层单点拦截，而非各 Service 手写

**问题**：5 种数据范围（全部 / 自定义 / 本部门 / 本部门及以下 / 仅本人）如果要每个查询手写，
**漏一个就是一个越权漏洞**，而且无法集中测试。

**方案**：MyBatis `InnerInterceptor` + ThreadLocal 上下文，在 DAO 层统一注入。

```
统一条件模板：AND (owner_user_id IS NULL OR <data_scope 条件>)
```

**精巧之处**：对**没有公海概念**的表（合同/回款/发票），`owner_user_id` 是 `NOT NULL`，
`IS NULL` 分支恒为 false，条件自动退化为纯 scope 判断 ——
**两类表共用一套逻辑，不需要写两套代码**。

**拦截器链顺序有硬约束**（顺序错了会出静默 bug）：

```
分页 → 数据权限 → 防全表更新 → 乐观锁
```

- 分页必须**早于**数据权限，否则 `count` 不计入数据权限、总数虚高
- 乐观锁必须**最后**，因为它只改 `SET` 部分
- 「本部门及以下」用 `sys_dept.ancestors` 前缀匹配（`ancestors LIKE '0,1,3,%'`），避免递归查树

### 2. 自研 4 张表审批流引擎，替代 Flowable（30+ 张表）

**三层模型**：模板（`sys_approval_flow`）→ 实例（`sys_approval_instance`）→ 任务（`sys_approval_task`）。

**收益**：新增审批业务**无需建表**，只需在 `sys_approval_flow` 配一条模板。

**支持**：或签 / 会签 / 依次三种审批方式；节点顺序可配置；驳回后重新提交创建**新实例**，历史实例保留。

**踩过的硬坑（并发竞态）**：
`submit` / `audit` 是 check-then-act，`updateById` 无 CAS，且 **DDL 上没有唯一约束兜底**
（`idx_biz` 是普通索引而非 UNIQUE）→ 最坏情况**审批节点永久卡死，只能改库**。

**修复范式**：条件 UPDATE + 判断影响行数，**先抢占、再建副作用**。
并沉淀为团队规范：**状态机流转一律不用 `updateById`**。配套新增 `ContractServiceImplTest`（还原实现即失败）。

### 3. 权限码三段式 —— 一个「静默失效」陷阱

**现象**：18 个角色中**权限最高的超管是唯一进不去首页看板的**，8 个看板接口全部 403。

**根因**：`*:*:*` **不是 Sa-Token 的内建语法**，只是一个普通通配模式，而模式里的 `:`
是**字面量**，默认只能命中**三段式**权限码 —— 命中不了两段式的 `dashboard:view`。

**为什么难查**：只影响看板，其余 38 个权限点全部正常，极易误判成「菜单没配」。

**解法**：`SaTokenConfig#overridePermissionMatching()` 显式覆写，提供「等价于全部权限」的语义。
**并确立约定：权限码一律写成三段式 `模块:资源:操作`。**

## 五、数据库设计要点

**49 张表，9 个分组**

| 分组 | 数量 |
|---|---|
| 系统基础与权限 `sys_*` | 19 |
| 审批流引擎 | 4 |
| AI 能力 | 1 |
| 线索与客户 | 8 |
| 产品 / 商机 / 报价 | 7 |
| 合同与财务 | 5 |
| 销售过程 / 营销 / 售后 | 4 |
| 通用能力（关注收藏） | 1 |

**关键设计决策**

1. **雪花 ID 主键**（`BIGINT UNSIGNED`，应用层生成）—— 不用自增，避免暴露业务量、利于将来分库分表
2. **逻辑删除与唯一约束的冲突用「生成列」化解**
   `is_active GENERATED ALWAYS AS (IF(del_flag=0,1,NULL)) VIRTUAL` + `UNIQUE(业务键, is_active)`
   —— 利用「MySQL 唯一索引中 NULL 不冲突」实现**删除后编号可复用**
3. **全库不建物理外键**（逻辑外键）—— 避免锁竞争、级联风险、与逻辑删除冲突
4. **五个强制审计字段**；`update_time` **统一应用层写入**，DDL 不声明 `ON UPDATE CURRENT_TIMESTAMP`
   （后者在值未变化时不更新，与业务预期不符）
5. **禁用 `TINYINT(1)`** —— 会被 ORM 映射成 boolean，导致 `audit_status=2/3` 丢失信息
6. **公海状态单一真相**：只保留 `owner_user_id`（NULL = 在公海），**删除 `pool_status` 字段**，从结构上消除非法状态
7. **金额口径定稿**：`unit_price` 为含税单价，**先逐行四舍五入再汇总**（否则明细与合计差几分钱）；`合同金额 == Σ 明细`，服务端强校验
8. **名称搜索**用 `FULLTEXT ... WITH PARSER ngram`；数据权限表**必须同时建 `idx_owner` 与 `idx_dept`**

## 六、权限设计（四层正交）

```
① 菜单权限   能进入哪些页面
② 操作权限   能点击哪些按钮     （Sa-Token @SaCheckPermission，全项目 68 处注解）
③ 数据权限   能查询到哪些数据行  （MyBatis 拦截器，DAO 层单点强制）
④ 字段权限   能看到行里的哪些字段
```

**核心原则：数据权限 ≠ 功能权限。**
财务能「看到」全部客户数据，但菜单上只能进回款 / 发票 / 客户三个页面。

**4 个角色**

| 角色 | `role_key` | 数据范围 |
|---|---|---|
| 超级管理员 | `admin` | 全部 |
| 销售总监 | `sales_director` | 本部门及以下 |
| 销售专员 | `sales` | 仅本人 |
| 财务 | `finance` | 全部（靠菜单收紧） |

**超管是特例：权限被「替换」而非「并集」** —— `permissions` 不是从 `sys_role_menu` 汇总，
而是整体替换成 `["*:*:*"]`，菜单树取全量。

## 七、AI 智能助手

**形态**：SSE 流式对话（`POST /ai/chat/stream`），DeepSeek Function Calling。

**工具从 9 个扩展到 25 个**：CRM 业务 10 个 / 产品目录 2 个 / 财务 2 个 / 首页看板 2 个 / 系统设置 9 个。

**三个设计要点**

1. **按登录人权限点过滤工具**：`specs()` 只把当前用户有权限的工具发给模型；
   `execute()` **再校验一次做纵深防御**
2. **权限匹配复用而非重写**：直接复用 `SaTokenConfig` 覆写过的 `SaStrategy.instance.hasElement`
   —— 超管 `*:*:*` 与 `crm:lead:*` 部分通配语义**自动继承，没有第二份实现**
3. **函数权限与行级权限取交集**：所有工具**只读**且**全部走现有 Service**，
   因此行级数据权限自动生效

**边界诚实标注**：两个日志工具 + `search_users` 查的表不在数据权限白名单，
行级过滤对它们不生效，`permission()` 是唯一闸门。

**质量**：新增 `AiToolRegistryTest`（14 个断言）锁住过滤行为 —— **AI 工具链此前零测试**。

| 案例 | 内容 |
|---|---|
| BUG-003 | 权限最高的超管是唯一进不去看板的人（见第四节 3） |
| BUG-012 | 客户列表整页公海客户时 500 —— 空 Map 上 `Map.of().get(null)` 先 `requireNonNull` 抛 NPE。**同类模式在八处修过、第九处又漏** |

**三条「元结论」★ 答辩有料**

1. **「构建通过 + 自检脚本全绿」与「功能正确」无关**
   BUG-012~016 五条缺陷**全部存在于编译通过、三个自检脚本全过的代码里**。
   自检覆盖的是「结构一致性」（字段名、路由、import），**覆盖不到「语义正确」**（空 Map 的 NPE、并发竞态、权限码归属）。
2. **文档比代码更容易腐烂，而且烂得更隐蔽**
   BUG-010 曾**谎报已修复**（从未为真）；「公海领取并发控制是裸的」是**反向错误**（代码那处反而写对了）。
   → 由此确立纪律：**查完成度请用命令，不要抄文档清单**。
3. **同类缺陷会成片出现** —— 修一处时顺手 grep 同类模式，收益极高。

**自检体系**：`check:api`（199/199 通过）· `check:static`（12 项）· `check:mock`（78 项断言）

**部署踩坑（真实案例）**

- **`flock` 锁被子进程继承 → 服务再也停不掉**：`nohup java ... &` 拉起的 JVM 默认继承父进程 fd，
  而 flock 的锁绑定在「打开文件描述」上被父子共享 → 应用活着锁就永不释放，
  **而 stop 也走这条路，等于再也停不掉服务**。修复：`nohup ... 2>&1 9>&- &`
- **PID 回绕约 25 分钟一轮**（`kernel.pid_max` 32768 + 云监控 fork 频繁）→
  用 `/proc/<pid>/cmdline` 校验进程身份挡误杀，**这是每天都会发生的事，不是理论风险**
- **防火墙与云安全组是完全独立的两套规则**，只配一层会出现「端口显示已开放，但就是连不上，且任何地方都不报错」

## 十、答辩 Q&A 预案

**Q1：为什么不用 Spring Security，而用 Sa-Token？**
我们的需求只有三件事：登录、权限校验、会话管理。Sa-Token 这三件事**每一行代码都能讲清楚**；
Spring Security 的过滤器链在排查问题时反而增加理解成本。这是一个**「够用且可解释」优先于「功能更全」**的选择。

**Q2：为什么自研审批流，不用 Flowable / Activiti？**
我们的审批场景只有**线性审批**（部门主管 → 财务），不需要并行网关、子流程、边界事件。
Flowable 需要 30+ 张表，我们的三层模型只用 **4 张表**，且**每一张表的设计意图都能说清楚**。
收益是新增审批业务无需建表。

**Q3：为什么不用微服务？**
当前规模不需要，而且**微服务的运维代价（服务发现、链路追踪、分布式事务）我们没有对应的收益来覆盖**。
单体 + Maven 分模块已经做到结构清晰、依赖严格单向。

**Q4：数据权限为什么放 DAO 层而不是 Service 层？**
Service 层手写靠自觉，**漏一个就是越权漏洞**，而且无法集中写单测。
放 DAO 层用拦截器，新增接口**自动生效**，且能集中测试。

**Q5：为什么不用物理外键？**
四个原因：锁竞争、级联删除风险、与逻辑删除冲突、阻碍将来分库分表。
我们用逻辑外键 + 命名规范（`<被引用表>_id`）+ 类型强制一致来保证完整性。

**Q6：前端为什么不用 TypeScript？**
时间预算下，把精力投给后端的三个核心技术点（数据权限、审批引擎、AI 工具链）收益更高。
这是一个**明确的取舍**，不是遗漏。

**Q7：这个系统最大的技术难点是什么？**
并发下的状态机正确性。合同审批是 `check-then-act`，`updateById` 无 CAS、
DDL 上也没有唯一约束兜底，最坏情况会让审批节点**永久卡死**。
我们最终的修复范式是「条件 UPDATE + 判影响行数、**先抢占再建副作用**」，
并把它固化成规范：**状态机流转一律不用 `updateById`**。

**Q8：项目目前有什么不足？**
诚实地说有三个：
① **审批流模块 `crm-module-bpm` 仍是空模块**，合同审批的状态机目前写在 `ContractServiceImpl` 里，
   尚未抽到独立的引擎模块；
② **字段权限只有设计没有落地** —— 设计是注解 + Jackson 序列化过滤，
   实际落地处用的是按角色硬编码白名单，**目前存在两套并存的思路**；
③ **公海回收、合同到期扫描等定时任务尚未实现**。

**Q9：你们怎么保证代码质量？**
先说一个反直觉的发现：**构建通过 + 自检脚本全绿，与功能正确无关**。
我们的 BUG-012~016 五条缺陷全部存在于编译通过、三个自检脚本全过的代码里 ——
自检覆盖的是结构一致性，覆盖不到语义正确。
所以我们的做法是：**关键路径补回归单测**（如审批并发、AI 工具过滤），
并且确立纪律「**查完成度用命令，不要抄文档**」，因为我们的文档曾经谎报过修复状态。

**Q10：如果数据量涨到很大怎么办？**
我们做过评估：当前慢查询 0 条，整个库 3.4 MB，完全驻留在 InnoDB buffer pool 中，读操作无磁盘 I/O。
主从读写分离在当前规模下**收益为负** —— 跨公网从库的网络往返比内存读慢几个数量级，
同时还会引入写后读一致性风险。
因此判断**现阶段不应引入**，保留该方案作为数据量增长后的演进路径。
真正需要时，优先做**索引优化与缓存**，而不是先上读写分离。
