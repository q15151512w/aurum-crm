### 2.2 持久层

| 组件 | 版本 | 作用 |
| :--- | :--- | :--- |
| **MyBatis-Plus** | 3.5.7 | ORM 框架 |
| **MySQL Connector/J** | Boot BOM 管理 | MySQL JDBC 驱动 |
| **Druid** | 1.2.23 | 数据库连接池 + 慢 SQL 监控 |

> ⚠️ Spring Boot 3 必须使用 **`mybatis-plus-spring-boot3-starter`**，
> 普通的 `mybatis-plus-boot-starter` 不兼容。

**MyBatis-Plus 在本项目中承担的核心职责**

| 能力 | 实现方式 | 用途 |
| :--- | :--- | :--- |
| 审计字段自动填充 | `MetaObjectHandler` | `create_time` / `create_by` / `update_time` / `update_by` 自动写入 |
| 逻辑删除 | `@TableLogic` | `DELETE` 自动转为 `UPDATE del_flag = 1`；`SELECT` 自动追加 `del_flag = 0` |
| 分页 | `PaginationInnerInterceptor` | 统一分页，单页上限 500 条防拖库 |
| 防全表更新 | `BlockAttackInnerInterceptor` | 拦截不带 `WHERE` 的 `UPDATE` / `DELETE` |
| 乐观锁 | `OptimisticLockerInnerInterceptor` | 并发场景（领取客户/线索） |
| **数据权限** | 自定义 `InnerInterceptor` | **项目核心技术点**，见 2.5 |

**拦截器链顺序（关键）**

```
分页 → 数据权限 → 防全表更新 → 乐观锁
```

顺序不可随意调整：

- 分页必须早于数据权限，否则 `count` 查询被重复改写，总数与列表对不上
- 乐观锁必须在最后，它只改 `SET` 部分，要在所有 `WHERE` 改写完成之后执行

### 2.3 认证与安全

| 组件 | 版本 | 作用 |
| :--- | :--- | :--- |
| **Sa-Token** | 1.39.0 | 认证鉴权框架 |
| **sa-token-redis-jackson** | 1.39.0 | 会话存储到 Redis（支持多实例、会话续期） |
| **spring-security-crypto** | 6.3.4 | **仅引入 BCrypt 密码加密工具类** |
| **commons-pool2** | Boot BOM | Redis 连接池 |

**Sa-Token 提供的核心能力**

- 登录态管理：`StpUtil.login()` / `checkLogin()` / `logout()`
- 权限注解：`@SaCheckPermission("crm:customer:list")`
- 角色注解：`@SaCheckRole("sales")`
- 会话管理：多端登录、强制下线、账号封禁
- 全局异常：`NotLoginException` / `NotPermissionException` / `DisableServiceException`

**密码存储**：BCrypt（自带随机盐 + 可调计算强度），而非 MD5/SHA。
强度设为 10（2¹⁰ 次迭代），单次加密约 50~100ms。

> 这三个是项目的技术含量所在，实现细节见《02-建表文档.md》

### 3.5 前后端接口约定

后端统一响应格式：

```json
{ "code": 0, "message": "操作成功", "data": { } }
```

`utils/request.js` 的拦截逻辑（**必须严格遵守**）：

| 情况 | 处理 |
| :--- | :--- |
| `code === 0` | 返回 `data`，业务代码直接用 |
| `code === 401` | 清除 token，跳转登录页 |
| `code === 403` | `ElMessage.error('没有该操作权限')` |
| `code === 400` | 展示后端返回的校验提示 |
| 其他非 0 | `ElMessage.error(message)` |
| **HTTP 500** | ⚠️ 单独分支——这是唯一不走 `code` 约定的情况，提示「服务器繁忙」 |

> ⚠️ **HTTP 状态码约定**：业务与认证错误统一返回 **HTTP 200 + body 中的 `code`**；
> 只有**未预期的服务端异常**才返回 HTTP 500。前端拦截器需要同时处理这两条路径。

## 五、技术选型决策记录

> 答辩常被问「为什么用 A 不用 B」，此节用于回答。

### 5.1 为什么不用 Spring Security？

| 维度 | Sa-Token | Spring Security |
| :--- | :--- | :--- |
| 核心 API | `StpUtil` 十几个方法 | 过滤器链 + 配置类，概念多 |
| 学习成本 | 低 | 高 |
| 代码可读性 | 业务代码里一眼能看懂 | 大量逻辑藏在配置里 |
| 适用场景 | 中小型项目、快速开发 | 复杂安全需求（OAuth2、SAML） |

**结论**：本项目只需「登录 + 权限校验 + 会话管理」，Sa-Token 足够且**每一行都能讲清楚**。

### 5.2 为什么不用 Flowable / Activiti？

| 维度 | 自研三层模型 | Flowable |
| :--- | :--- | :--- |
| 核心表数量 | **4 张** | 30+ 张 |
| 概念模型 | 模板 → 实例 → 任务 | BPMN 2.0（网关、事件、边界事件…） |
| 学习成本 | 低 | 高 |
| 灵活性 | 线性审批够用 | 支持复杂流程编排 |
| 可解释性 | 每张表都能说清设计意图 | 大部分表说不清作用 |

**结论**：业务只需「提交 → 一级审批 → 二级审批」的线性流程，
自研 4 张表即可满足，且**新增审批业务无需建表**。

### 5.3 为什么不用微服务？

| 维度 | 单体多模块 | 微服务 |
| :--- | :--- | :--- |
| 部署复杂度 | 一个 jar | Nacos + Gateway + 多个服务 |
| 调试成本 | 直接断点 | 跨进程追踪 |
| 事务一致性 | 本地事务 | 需要 Seata 等分布式事务方案 |
| 运维成本 | 低 | 高 |
| 适用规模 | 中小型系统 | 大规模、多团队 |

**结论**：本项目规模不需要微服务。单体 + Maven 分模块已经做到「结构清晰」，
且不用付微服务的运维代价。

### 5.4 为什么不用物理外键？

见《02-建表文档.md》1.6 节，核心原因：

| 原因 | 说明 |
| :--- | :--- |
| 锁竞争 | 物理外键写入时对父表加锁，高并发易死锁 |
| 级联风险 | `ON DELETE CASCADE` 配错可能连带清空多张表 |
| 与逻辑删除冲突 | 本库用 `del_flag` 逻辑删除，父行并不真正消失 |
| 阻碍扩展 | 物理外键无法跨库，未来拆分是硬阻塞 |

**代价**：完整性责任转移到应用层，必须靠纪律兜底（插入校验 + 删除检查 + 定期巡检）。

### 5.5 为什么前端不用 TypeScript？

TypeScript 的优势是类型安全与 IDE 提示，但需要额外编写类型声明，
在项目周期有限的情况下，**把时间留给后端三个核心技术点收益更高**。

若后续扩展，可逐步迁移：Vite 对 JS/TS 混用支持良好。

## 六、版本管理约定

### 6.1 后端

所有第三方版本**集中声明在根 POM 的 `<dependencyManagement>`**，
各模块引依赖**不写 `<version>`**：

```xml
<properties>
    <spring.boot.version>3.3.5</spring.boot.version>
    <mybatis.plus.version>3.5.7</mybatis.plus.version>
    <sa.token.version>1.39.0</sa.token.version>
    <redisson.version>3.32.0</redisson.version>
    <knife4j.version>4.5.0</knife4j.version>
    <hutool.version>5.8.32</hutool.version>
    <mapstruct.version>1.6.2</mapstruct.version>
    <lombok.version>1.18.38</lombok.version>
</properties>
```

**好处**：升级只改一处；杜绝各模块版本漂移。

### 6.2 前端

依赖版本由 `package.json` 锁定，配合 `package-lock.json` 保证团队一致。
建议在 `package.json` 中使用 `~`（仅补丁版本）而非 `^`，避免次版本引入破坏性变更。

## 七、已知问题与解决方案

> 以下均为项目搭建过程中**实际踩到过的坑**，记录备查。

| # | 现象 | 原因 | 解决方案 |
| :--- | :--- | :--- | :--- |
| 1 | `ERR AUTH <password> called without any password configured` | Redis 未设密码，但配置里写了 `password:`（空值）。空值被 Spring 绑定成**空字符串**，Redisson 拿它发 AUTH 命令 | **整行删掉**，不要留空值 |
| 2 | `Unsupported character encoding 'utf8mb4'` | JDBC URL 的 `characterEncoding` 需填 **Java 字符集名**，不是 MySQL 的字符集名 | 改为 `characterEncoding=UTF-8`，Connector/J 8.x 自动映射到 utf8mb4 |
| 3 | 未登录接口返回 **500** 而非 401 | `NotLoginException` 被 `GlobalExceptionHandler` 的 `Exception` 兜底分支吞掉 | 新增 `SecurityExceptionHandler` 并标 `@Order(HIGHEST_PRECEDENCE)` 抢先处理 |
| 4 | Maven 报 `dependencies ... version is missing` | 版本管理只写在子模块，未对全项目生效 | 版本统一放根 POM 的 `<dependencyManagement>` |
| 5 | Maven 报 `dependencies of type=pom and with scope=import form a cycle` | 独立 BOM 模块的 `<parent>` 指向根 POM，根 POM 又 `import` 它 | BOM 合并进根 POM，取消独立模块 |
| 6 | 找不到 `mybatis-plus-jsqlparser:3.5.7` | 该独立包是 **3.5.9** 才拆出来的 | 3.5.7 中它打包在 `extension` 内，无需单独引入 |
| 7 | `MapStruct` 生成的实现类为空 | 注解处理器顺序错误 | `annotationProcessorPaths` 中 **Lombok 必须在 MapStruct 之前** |
| 8 | `spring-boot-maven-plugin` 用的是 **4.1.0**，而应用是 3.3.5 | 本项目用 `spring-boot-dependencies`（**BOM**）而非 `spring-boot-starter-parent`。BOM 只管**依赖**版本，**不管插件**版本，不写 `<version>` 时 Maven 会挑仓库里最新的插件 | 在 `crm-server/pom.xml` 中显式指定 `<version>${spring.boot.version}</version>` |
| 9 | 主键插入为 `null` 导致 SQL 报错 | `mybatis-plus.global-config.db-config.id-type` 设为 `input` 表示「主键由外部提供，ORM 不生成」，漏写 `setXxxId()` 就会插入 null | 改为 `ASSIGN_ID`（MyBatis-Plus 内置雪花算法，零代码） |
| 10 | 插入后「**内存对象里的时间 ≠ 数据库读回的时间**」，导致单元测试莫名失败 | 建表脚本用 `DATETIME`（**秒精度**，无小数位），而 `LocalDateTime.now()` 带纳秒。MySQL 按列精度截断，写进去 `18:31:43.123456789`、读回来 `18:31:43`，两者永不相等 | `DefaultDBFieldHandler` 统一 `LocalDateTime.now().truncatedTo(ChronoUnit.SECONDS)`。**若需要毫秒精度**，应把 DDL 审计字段改为 `DATETIME(3)` 并同步改成 `truncatedTo(MILLIS)`——两边粒度必须一致 |
| 11 | 编译报 `java.lang.ExceptionInInitializerError` / `com.sun.tools.javac.code.TypeTag :: UNKNOWN` | **Lombok 版本太旧，读不懂新版 JDK 的 javac 内部结构**。Lombok 是注解处理器，要往编译器 AST 里插 getter/setter，必须读取 javac 内部类 `com.sun.tools.javac.code.TypeTag`。该结构随 JDK 大版本变化，Lombok 1.18.34 只支持到 JDK 22 左右 | **升级 Lombok 到 1.18.38**（`pom.xml` 一行）：`<lombok.version>1.18.38</lombok.version>` |

> **第 11 条的实测数据**（本机装了 17 / 21 / 25 三个 JDK，逐版本 × 逐 Lombok 版本验证）：
>
> | Lombok | JDK 17 | JDK 21 | JDK 25 |
> | :--- | :---: | :---: | :---: |
> | 1.18.34 | ✅ | ✅ | ❌ `TypeTag :: UNKNOWN` |
> | **1.18.38** | ✅ | ✅ | ✅ |
>
> **结论**：升级 Lombok 后**三套 JDK 全部可用**，比「把 IDE 的 JDK 锁死在 17」更稳——团队成员装了不同 JDK 也不会出问题。
>
> **排查经验**：这个报错的表现是「**命令行能跑、IDE 编译不过**」（或反过来），因为两边可能用不同的 JDK。
> **先用 `java -version` 和 `mvn -version` 对比两边的 JDK**，比读代码快得多。
>
> **另一个信号**：如果本项目报错、但同机器上别的项目正常，去比对它们的 `lombok.version` —— 本项目当时用的是 1.18.34，而 `qk-parent` 用的是 1.18.38。

## 八、开发环境配置要点

> 多 JDK 环境下，**命令行**与 **IDE** 必须使用同一个 JDK，否则会出现「一边能跑一边报错」。

### 8.1 本机环境（参考）

| 项 | 路径 |
| :--- | :--- |
| JAVA_HOME | `D:\JAVA\jdk-17.0.19` |
| MAVEN_HOME | `D:\JAVA\apache-maven-3.9.4` |
| 其他已装 JDK | `jdk-21.0.6`、`jdk-25.0.2`（**本项目不用**） |

### 8.2 IDEA 需要统一的四处 JDK 设置

| 位置 | 设为 |
| :--- | :--- |
| `Project Structure → Project → SDK` | 17 |
| `Project Structure → Project → Language level` | 17 |
| `Project Structure → Modules → 各模块 → Module SDK` | 17（或 Project SDK） |
| `Settings → Build Tools → Maven → Runner → JRE` | 17（或 Use Project JDK） |

另需确认 `Settings → Build Tools → Compiler → Java Compiler → Target bytecode version` 为 **17**。

改完执行 `File → Invalidate Caches / Restart`，并在 Maven 面板点刷新重新导入。

### 8.3 IDEA 的 Maven 也要指向本地安装

| 位置 | 设为 |
| :--- | :--- |
| `Settings → Build Tools → Maven → Maven home path` | `D:\JAVA\apache-maven-3.9.4` |
| `Settings → Build Tools → Maven → User settings file` | `D:\JAVA\apache-maven-3.9.4\conf\settings.xml` |

默认值是 `Bundled (Maven 3)`，即 IDEA 自带的 Maven，与命令行行为可能不一致（镜像配置、依赖解析结果都会不同）。
