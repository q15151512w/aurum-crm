## 三、`env` 文件怎么同步（重要）

**要同步，但不能照抄。** 第二台的 `env` = 第一台的 `env` 改两行。

| 变量 | 第一台 | 第二台 |
|---|---|---|
| `DB_HOST` | 不填（回落 `127.0.0.1`） | **必填 `YOUR_SERVER_IP`**（第一台的公网 IP，见第零节决策） |
| `REDIS_HOST` | 不填（回落 `127.0.0.1`） | **必填**：同上，两行必须是**同一台机器** |
| `SERVER_PORT` / `HEALTH_URL` | `8080` / `http://127.0.0.1:8080/...` | **不变**（健康检查探的是本机） |
| 其余全部（凭证 / OSS / 邮件 / AI / `JAVA_OPTS`） | — | **原样照抄** |

> ⚠️ 在 Linux 上时 `DB_HOST` / `REDIS_HOST` 就不再回落到回环了 ——
> 第二台的 `127.0.0.1` 是它自己，那儿没有数据库。

### 三个坑

1. **不要手工重打一遍。** 十几项凭证手抄极易漏项，而症状是启动时报
   `Could not resolve placeholder`，或者更糟 —— 静默连到了错的库。
   **先 `scp` 过去，再改那两行。**

   > ⚠️⚠️ **更不要用 `deploy/env.example`**。它是**模板**，值全是
   > `<改成真实密码>` 这种占位符。直接 `cp` 成 env 去启动的后果很误导：
   > `service.sh` 的必填校验只查「变量空不空」，而 `<...>` 是**非空**的，
   > 于是校验全绿 → 启动 → 连库报 `Access denied for user 'root'` →
   > 你去核对密码 —— 而真正的原因是密码压根没填。
   >
   > 2026-09-15 已给两个脚本加了拦截：`service.sh` 的必填校验会把这些值
   > 判为「还是占位符」并拒绝启动；`check-env.sh` 第 9 项在连库之前会点破，
   > 免得那条 `Access denied` 再把人引向数据库。**但脚本拦得住，不如一开始就别用模板。**
2. **换行符必须是 LF。** 用 Windows 工具编辑会引入 CRLF，密码尾部多一个
   不可见的 `\r`，报 `Access denied` 而屏幕上看着完全正确。
   `service.sh` 启动时会检测并拒绝（这是它存在的理由之一）。
   `scp` 不改换行，所以**先传后改**是最安全的顺序。
3. **`chmod 600`**，且这份文件不进 git（仓库外）。

### 天然就支持多机的三样（不用管）

- **登录态**：Sa-Token 存在 Redis，第二台登录、第一台认 ✅
- **文件**：走 OSS，天然共享 ✅

### 2026-09-15 逐项扫过一遍的「跨实例安全性」清单

加机器前把整个项目扫了一遍，找的是「单机没事、两台就出问题」的那类隐患：

| 检查项 | 结论 |
|---|---|
| `@Scheduled` 定时任务 | 全项目**只有 1 个**（`NoticeReminderJob`），已加分布式锁 ✅ |
| 进程内缓存 / 静态可变状态 | **没有**。所有 `static Map` 都是 `Map.of` 只读字典 ✅ |
| 本地磁盘落盘 | **没有**，上传全走 OSS ✅ |
| **单据编号生成** `NumberingRuleServiceImpl#nextCounter` | ✅ **写法是对的**：条件 UPDATE + 判影响行数（CAS）+ 8 次重试，新建分支靠 `DuplicateKeyException` 兜底 —— 而 `sys_numbering_counter` 上确实有唯一索引 `uk_rule_basis(rule_id, basis_key, is_active)`，已连生产库核实 |
| 登录态 / 验证码 | 在 Redis，天然共享 ✅ |

> **编号生成这条值得单独说**：它是集群里最容易出重号的地方（两台同时
> `SELECT MAX(seq)+1` 然后各自写回）。这个项目的实现是 CAS 的，**不用改** ——
> 但以后谁重构它，必须保持「条件 UPDATE + 判影响行数」，退回「先查后写」就会重号。

### ⚠️ 唯一的例外：别在同一台机器上跑两个实例

主键用的是 MyBatis-Plus 雪花（`application.yml:60` 的 `id-type: ASSIGN_ID`），
workerId 由**机器**推导。两台**不同机器** → 各自不同 → 安全；
但**同一台机器上起两个 JVM** 会拿到同样的 workerId，**可能生成重复主键**。

所以：横向扩展请加**机器**，不要在单机上多开实例。滚动发布时也要避免新旧两个
进程长期并存于同一台机器。

## 五、改配置解决不了的：定时任务（**已修**）

`@Scheduled` 是**每个 JVM 各跑各的**，没有任何协调。单机没问题，
两台机器就会同时执行。

`NoticeReminderJob`（每天 03:05 扫描到期未回访的客户并生成提醒）的幂等靠
`noticeExists()` 先查后插 —— **跨实例无效**：两台在各自事务里都查到"不存在"，
然后各插一条。而 `sys_notice` 上只有非唯一索引 `idx_biz(biz_type,biz_id)`，
**数据库也拦不住**。

**→ 每个待回访客户会多出一条重复提醒。**

### 修法

新增 `DistributedJobLock`（`crm-module-crm/.../core/`），
用 `setIfAbsent` + TTL + token 校验 + Lua 释放实现，
`NoticeReminderJob` 外面套上它，抢不到锁的实例直接跳过。

三个不显然的点（都写在类的 javadoc 里）：

1. **必须用 `setIfAbsent`，不能「先 GET 再 SET」** —— 后者是 check-then-act，
   两台可能同时查到"没有锁"然后都认为自己拿到了。与项目里状态流转一律用
   「条件 UPDATE + 判影响行数」是同一个道理。
2. **释放要校验 token** —— 锁带 TTL，A 跑得比 TTL 久时锁会先过期被 B 拿到，
   这时 A 无脑 `DEL` 删掉的是 **B 的锁**，C 又能进来。
3. **「比对 + 删除」要用 Lua 保证原子** —— 写成 Java 两步等于第 2 点白做。

> 以后**新增任何 `@Scheduled` 任务都要套这把锁**。这是集群下最容易忘、
> 且症状最隐蔽的一类问题（数据看着没错，只是多了一份）。

## 六、nginx —— **两台都配了，两个入口都能用**

> ⚠️ **本节 2026-09-15 傍晚重写过。** 早先的版本说「负载均衡只配在前端那台，
> `YOUR_SERVER_IP` 的 nginx 完全不用碰」—— 那个结论**当时是对的，现在作废了**：
> 后来决定让第一台也当入口，于是两台都配了 upstream。

### 现在的实际拓扑

```
        浏览器
          ↓                          ↓
   ┌──────────────────┐      ┌──────────────────┐
   │ YOUR_SERVER_IP    │      │ YOUR_SERVER_IP_2    │
   │  （京东云）        │      │  （阿里云）        │
   │  nginx :80 :443   │      │  nginx :80        │
   │    /      → 前端   │      │    /      → 前端   │
   │    /api/  → 轮询 ──┼──┐   │    /api/  → 轮询 ──┼──┐
   │  :8080 后端        │←─┴───┼───────────────────┘  │
   │  :3306 MySQL       │←─────┼──────────────────────┘
   │  :6379 Redis       │←─────┘
   └──────────────────┘      └──────────────────┘
```

**两个入口完全等价**，随便用哪个。负载均衡的落点在各自的 nginx 上。

### 第一台（`YOUR_SERVER_IP`）这台上配了什么

新增了 `conf.d/aurum-crm.conf` + `snippets/aurum-api.inc`（仓库里
`deploy/nginx/` 有存档），三个 server 块：

| 块 | 作用 |
|---|---|
| 80 + `example.com` | 301 跳 HTTPS |
| 80 + `default_server` | **用 IP 访问时直接给前端内容**（纯 HTTP，无证书警告）|
| 443 + `example.com` | HTTPS 入口，证书 `/etc/nginx/ssl/example.com.{pem,key}` |

外加 `upstream aurum_backend { 127.0.0.1:8080; YOUR_SERVER_IP_2:8080; }`。

> ⚠️ **那台上原来的 `server_name _` 块服务的是「星海智伴」**
> （`/usr/share/nginx/html/dist` + `/root/app/xhzb-admin.jar`，`xhzb` 就是
> 「星海智伴」的拼音首字母 —— 本文早先叫它「中州养老」，名字是错的）。
> 用户 2026-09-15 确认不再需要，所以 80 端口的 `default_server` 让给了 CRM。
> **它的配置和静态文件一个都没删**，要恢复只需去掉 CRM 那份里的
> `default_server` 再 reload。

### 三个必须知道的点

**1. 不需要会话保持（sticky session）。**
登录态（Sa-Token）存在 Redis 里，任何一台后端都能认任何一张令牌 ——
**这是整个集群能成立的前提**。哪天若把会话改成落在 JVM 内存里，集群立刻失效。

**2. nginx 的 upstream 默认没有主动健康检查。**
只有「失败 1 次后摘掉 10 秒」（`max_fails=1 fail_timeout=10s`）。
所以**某台挂掉后，会有少量请求先失败一次**才被摘掉。

> ⚠️ 更阴的一种：如果挂掉的那台是**本机连接被拒**（快失败），
> 每个 30 秒窗口里根本攒不满 `max_fails` 的次数，
> **死节点可能永远摘不掉**，一直分流。
> 增删节点前后都要 `ss -ltnp | grep 8080` 确认对方真的活着。

**3. 前端不用为集群重新构建。**
`VITE_APP_BASE_API` 是 `/api` 这个**相对路径**，具体打到哪台后端由 nginx 决定，
和前端产物无关。（但如果前端代码本身有新提交，那是另一回事 —— 见第十节。）

### 怎么验证「请求到底落到了哪台」

第一台的 `/api/` 里加了这一行：

```nginx
add_header X-Upstream-Addr $upstream_addr always;
```

```bash
for i in $(seq 1 10); do
  curl -s -D- -o /dev/null http://YOUR_SERVER_IP/api/actuator/health \
    | grep -i '^X-Upstream-Addr' | tr -d '\r'
done
```

| 返回值 | 含义 |
|---|---|
| `127.0.0.1:8080` | 落到第一台 |
| `YOUR_SERVER_IP_2:8080` | 落到第二台 |
| `127.0.0.1:8080, YOUR_SERVER_IP_2:8080` | **逗号分隔 = 前者失败过、重试到了后者** |

⚠️ 没有这个头的话，**负载均衡是看不出来的** —— 两台返回的 body 一模一样，
光看 curl 结果分不清是轮询了还是全打到同一台。
（第二台的 nginx 没加这个头，要验那台得先补上。）

### ⚠️ 跨机房的 nginx 有两个坑，都实际踩过（2026-09-15）

集群跑起来之后才发现的两个 bug，**都不是配置写错，而是「看起来对、跑起来一半失败」**。
两个都只在「两台后端在不同云厂商」这个前提下才会出现 —— 单机或同机房**永远不会遇到**。

#### 坑 ①：`proxy_set_header Host $host;` → 一半请求 403

```nginx
location /api/ {
    proxy_set_header Host $host;    # ❌ 把公网域名原样转发给上游
}
```

请求打到**京东云**那台时，京东云的备案核查看到 `Host: abcd.hywweb.me`
（没在它那儿备案）→ 返回它自己的拦截页。

**症状的三层迷惑性：**

1. **阿里云的机器返回了京东云的拦截页** —— 看页面归属根本想不到是转发导致的
2. 因为轮询，表现为**一半 200、一半 403**，看起来像「间歇性故障」
3. **用 IP 访问完全正常** —— 因为 `$host` 这时是 IP 字面量，不触发备案检查

**正确写法：**

```nginx
proxy_set_header Host             $proxy_host;   # upstream 组名，不含点
proxy_set_header X-Forwarded-Host $host;         # 真实域名挪这里保留
```

`$proxy_host` 是 `proxy_pass` 里写的那个名字（upstream 组名），
不含点、不像域名，两家的检查都不触发。**后端不依赖 Host 做路由**，
所以换个值不影响功能；真要拼绝对 URL 的应用可以从 `X-Forwarded-Host` 取。

#### 坑 ②：upstream 名字里有**下划线** → Tomcat 400

改完坑 ① 之后，**一台好了、另一台坏了（400）**：

```
upstream backend-cluster   → 连字符，OK    ✅   （121 上一直是这个）
upstream aurum_backend     → 下划线，400   ❌   （148 上是这个）
```

`$proxy_host` 就是这个**名字本身**，而下划线不是合法的主机名字符（RFC 1123），
**Tomcat 收到 `Host: aurum_backend` 直接回 400 Bad Request**，请求根本到不了应用。

**这个比坑 ① 更难查**：400 是 Tomcat 直接拒的，**应用日志里一条都不留**，
而且**直连后端是好的、只有走这台 nginx 才坏**。

> ✅ **规矩：upstream 名字只用字母、数字、连字符。** 别用下划线。
> 两台的名字统一成 `aurum-backend` / `backend-cluster` 这种形式。

#### 两个坑的共同教训

**「直连后端是好的」不等于「nginx 是好的」。** 这两个 bug 里，后端全程无辜 ——
出问题的都是 nginx 转发出去的那一刻。所以排查这类「一半成功一半失败」时，
第一步不是看后端日志（那里什么都没有），而是：

```bash
# 看这次请求到底落到哪台、有没有重试（逗号分隔 = 前者失败过）
curl -s -D- -o /dev/null http://<入口>/api/actuator/health \
  | grep -i '^X-Upstream-Addr'
```

没有这个响应头，这类问题**完全看不出来** —— 两台返回的 body 一模一样。

### 两台后端起来之后应该做的事（可选，安全加固）

现在两台的 8080 都是 `0.0.0.0` 直接对公网的，登录密码和 Sa-Token 令牌在公网裸奔。
理想状态是只让 nginx 能访问：

1. 安全组：关掉 8080 的公网入站，只放行**两台机器之间的来源 IP**
2. 只对外暴露 nginx 的 80 / 443

> ⚠️ **注意：这里不能把 `server.address` 改成 `127.0.0.1`。**
> 本文早先的版本是这么写的 —— 那是按「nginx 和后端同机」假设写的。
>
> 现在 **`YOUR_SERVER_IP:8080` 是第二台的 `DB_HOST` 吗？不是**，但
> `YOUR_SERVER_IP_2` 的 nginx **要能访问第一台的 8080**（upstream 里有它）。
> 把第一台改成只监听回环，就等于砍掉了集群的一条腿。
>
> ⚠️ 这一条还会让你自己的开发机无法再直连调试。想留后路就先别关，但要知道它一直开着。

### 核心改动：把写死的地址换成 upstream（**已改完**）

> ✅ 这一段是**当时的改法**，两台都已经改好了。仓库里存档在
> `deploy/nginx/aurum-crm.conf` 和 `deploy/nginx/aurum-api.inc`。

原来的写法是写死一台：

```nginx
location /api/ {
    proxy_pass http://YOUR_SERVER_IP:8080/;    # ← 写死了一台
    ...
}
```

改成：

```nginx
# 加在 server 块【外面】（http 块里）
upstream aurum_backend {
    server 127.0.0.1:8080;            # 本机（第一台就是 YOUR_SERVER_IP）
    server YOUR_SERVER_IP_2:8080;       # 第二台

    keepalive 32;                     # 可选：复用长连接
}

server {
    location /api/ {
        # ⚠️ 末尾这个斜杠必须【保留】—— 它负责剥掉 /api 前缀。
        #    前端 VITE_APP_BASE_API=/api，而后端接口本身没有 /api 这一层。
        #    少了斜杠的表现：所有请求 404，且后端日志里一条记录都没有。
        proxy_pass http://aurum_crm_backend/;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;

        # ⚠️ nginx 默认 1M，而 Spring 配的是 multipart 50MB / 100MB。
        #    不放开的话大文件上传被 nginx 挡在门外回 413，后端日志里什么都看不到。
        client_max_body_size 50m;

        # ⚠️ AI 小助手是 SSE 流式返回，缓冲会让它「憋着一句话都不出」
        proxy_buffering off;
        proxy_read_timeout 300s;

        # upstream 里写了 keepalive 就必须清掉 Connection 头，
        # 否则 keepalive 不生效（每个请求照样新建连接）
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

⚠️ **改之前先 `nginx -T` 看现有站点** —— 那台上可能有别的项目，
别覆盖别人的配置。配置里若有 `include`，要改的是被 include 的那个文件。

### 三个必须知道的点

**1. 不需要会话保持（sticky session）。**
登录态（Sa-Token）存在 Redis 里，任何一台后端都能认任何一张令牌 ——
**这是整个集群能成立的前提**。哪天若把会话改成落在 JVM 内存里，集群立刻失效。

**2. nginx 的 upstream 默认没有主动健康检查。**
只有「失败 1 次后摘掉 10 秒」（`max_fails=1 fail_timeout=10s`）。
所以**某台挂掉后，会有少量请求先失败一次**才被摘掉。想让失败更平滑要配
`proxy_next_upstream`，那是另一件事，本次不做。

**3. 前端不用重新构建。**
`VITE_APP_BASE_API` 是 `/api` 这个**相对路径**，具体打到哪台后端由 nginx 决定，
和前端产物无关。（但如果前端代码本身有新提交，那是另一回事 —— 见第十节。）

```bash
./service.sh start
```

**预期**：`status` 运行中；本机 `curl -s 127.0.0.1:8080/actuator/health` 返回 `{"status":"UP"}`。

⚠️ 第二台的 `HEALTH_URL` 探的是**本机**，两台填一样的值，别改成对方的 IP。

---

### 第 7 步 · 确认两台都能独立跑

在**两台各自**执行：

```bash
curl -s http://127.0.0.1:8080/actuator/health
```

**预期**：都是 `{"status":"UP"}`。

再从第二台验证它连的确实是第一台的库（不是连回自己）：

```bash
mysql -hYOUR_SERVER_IP -uroot -p -e "SELECT @@hostname, @@port"
```

**这一步必须先于 nginx。** 两台没各自跑通就上负载均衡，只会让问题变成两份。

---

### 第 8 步 · 给 nginx 加上负载均衡（**两台都做了**）

> ⚠️ **本步早先的版本写的是「只在第二台改，`YOUR_SERVER_IP` 不碰」——
> 那个前提后来变了**：决定让第一台也当入口，于是两台都配了 upstream。

**两台都要改**，各自的 upstream 里都写上对方：

```bash
nginx -T | less        # 看清现有站点，别覆盖别人的
```

把 `location /api/` 里写死的 `proxy_pass` 换成 upstream。
**完整写法、以及必须保留的末尾斜杠等三个坑，见第六节。**

```bash
nginx -t && nginx -s reload     # 先测语法，再热加载 —— 不要 restart
```

**预期**：`nginx -t` 输出 `syntax is ok` + `test is successful`。

验证两个节点都在接流量 —— **别用「返回 200 就算数」**，两台返回的 body
一模一样，看不出来。用 `X-Upstream-Addr` 响应头（第一台已配）：

```bash
for i in $(seq 1 10); do
  curl -s -D- -o /dev/null http://YOUR_SERVER_IP/api/actuator/health \
    | grep -i '^X-Upstream-Addr' | tr -d '\r'
done
# 期望：两个地址交替出现，各 5 次，且【没有逗号】
```

> ℹ️ 只靠 `curl` 看不出"轮询到了哪台"。要确凿证据，看两台后端各自的
> 访问日志，或临时在其中一台的响应里加个标记。

---

### 第 9 步 · 验证分布式锁真的生效

**这是唯一一个无法当场验证的项** —— 要等定时任务跑过一轮。
第二天看两台的日志：

```bash
grep '待办提醒' /root/CRM/aurum-crm/logs/crm-server.log
```

**预期**：**只有一台**打印「生成 N 条到期待回访客户提醒」，
另一台打印「**另一个实例正在执行，本次跳过**」。

> 两台都打印「生成 N 条」= 锁没生效，会造成重复提醒，要回头查。
> 两台都跳过 = 锁没释放干净，查 `crm:job:lock:notice-reminder` 这个 key 的 TTL。

---

# application-prod.yml 的 server.address 改成 127.0.0.1
# 云控制台安全组：关掉 8080 的公网入站，只留 nginx 的 80/443
```

改完两台都要 `./service.sh restart`。

**⚠️ 不要跳过第 2 步。** 在第二台复制一台有问题的第一台，只会让问题变成两份。

> - 两台都「跳过」= 锁**没释放干净**，去 Redis 查 `crm:job:lock:notice-reminder` 的 TTL

### 第 3 项为什么改成看 `ss` 而不是看 `check-env.sh`

`check-env.sh` 打印的「连接目标」是**从 `env` 反推出来的**——
它证明的是「env 里写对了」，**不是「进程真的连过去了」**。

这两者可能不一致：比如 env 改完没重启，或者进程起在改动之前。
直接看进程的 socket 才是硬证据：

```bash
ss -tnp | grep <java的PID> | grep -E "3306|6379"
# 期望看到 -> [::ffff:YOUR_SERVER_IP]:3306 和 :6379
```

> ⚠️ `check-env.sh` 在**没装 `redis-cli`** 的机器上会跳过 Redis 检查，
> 打印一句含糊的「env 里 REDIS_PASSWORD 空着、或没装 redis-cli」——
> 那是提示不是结论，别当成「Redis 没问题」。详见第四节。

### ⚠️ 「服务器上跑的是哪个版本」是个反复踩的坑

2026-09-15 这次就踩到了：第二台上的前端**还是旧版**
（`index-DI0m0SyK.js`），表现为**选择器的组织架构树仍然调 `/dept/tree`** ——
也就是说 **BUG-027 在生产上一直是复现状态**，只是没人注意到。

> 症状很隐蔽：**页面能打开，只是少几个功能/某个入口报错** ——
> 很容易被误判成「后端接口没做」，然后去后端白查一轮。

**判定服务器上是哪个版本，用构建产物的文件名比对**（不是看时间戳）：

```bash
# 本地重新构建后的入口文件名
cd <前端项目目录>\aurum-crm-ui
npm run build
grep -o 'assets/index-[A-Za-z0-9_-]*\.js' dist/index.html

# 服务器上正在跑的那个
curl -s http://<那台的IP>/ | grep -o 'assets/index-[A-Za-z0-9_-]*\.js'
```

**两个哈希一致 = 同一份构建。** 文件名带内容哈希，所以这是可靠的判据。

> ⚠️ 别用「搜 bundle 里有没有某个接口路径」来判断 —— API 路径在
> `api/system.js` 里是模板字符串拼出来的（`` `${DEPT}/options` ``），
> 打包后 `dept/options` 这种整串**根本不会出现**，搜不到不等于没有。
> 那次差点据此误判。

### 重新构建 + 部署

```bash
cd <前端项目目录>\aurum-crm-ui
npm run build          # 产物在 dist/
```

`dist/` 在 `.gitignore` 里，是本地构建产物，不进仓库，要单独传到服务器。
建议打包成 tar 再传（3.2MB → 930KB，且避免几百个小文件逐个传）：

```bash
tar -czf /tmp/aurum-dist.tar.gz -C dist .
scp /tmp/aurum-dist.tar.gz root@<那台IP>:/tmp/
```

```bash
# 服务器上 —— ⚠️ 先清空 assets，否则旧哈希文件会残留
cd /usr/share/nginx/html/<目录>
cp -a <目录> <目录>.bak-$(date +%Y%m%d)      # 备份旧的
rm -rf assets index.html
tar -xzf /tmp/aurum-dist.tar.gz -C .
```
