## 零、需求确认

以下 5 条为**已确认的业务决策**，是本文档全部设计的依据：

| # | 决策 | 影响范围 |
| :--- | :--- | :--- |
| 1 | **销售不应看到他人私海数据**，可以看到自己的客户与公海数据 | 数据权限 |
| 2 | **主管看到自己部门及以下**的数据 | 数据权限 |
| 3 | **财务可以看到客户信息** | 数据权限 + 菜单权限 |
| 4 | **所有人可以看到公海数据** | 数据权限（全局规则） |
| 5 | **需要字段级权限** | 字段权限 |

## 一、权限模型总览

系统权限分为**四层**，从粗到细，逐层收窄：

```
① 菜单权限   能进入哪些页面          ← 控制"看不看得见入口"
     ↓
② 操作权限   能点击哪些按钮          ← 控制"能不能做这个动作"
     ↓
③ 数据权限   能查询到哪些数据行       ← 控制"能看多少条数据"
     ↓
④ 字段权限   能看到行里的哪些字段     ← 控制"能看到哪些列/值"
```

**四层是正交的**，举例说明：

| 场景 | 哪一层在起作用 |
| :--- | :--- |
| 销售看不到「组织架构」菜单 | ① 菜单权限 |
| 销售能进「客户」页，但看不到「删除客户」按钮 | ② 操作权限 |
| 销售进客户页，只看到自己的客户和公海客户 | ③ 数据权限 |
| 销售看到某客户，但联系电话显示 `138****8888` | ④ 字段权限 |
| 财务能看全部客户（数据权限=全部），但进不了「线索」菜单 | ① 与 ③ 分离的体现 |

> **关键原则**：**数据权限 ≠ 功能权限**。财务能"看到"全部客户数据（数据权限放开），
> 但功能上只能进回款/发票/客户三个菜单（菜单权限收紧）。
> 决策 3「财务可以看到客户信息」正是这条原则的应用。

## 三、数据权限设计 ⭐

### 3.1 核心机制

数据权限在 **DAO 层统一拦截**（MyBatis `InnerInterceptor`），
而不是在各个 Service 里手写条件。

**为什么必须在 DAO 层**：

| 方案 | 问题 |
| :--- | :--- |
| Service 层手写 | 靠开发者自觉，**漏一个就是越权漏洞**；无法统一测试 |
| **DAO 层拦截（采用）** | 单点强制，新增接口自动生效；可集中写单元测试 |

### 3.2 公海可见性 —— 决策 4 的实现

决策 4「所有人可以看到公海数据」在 SQL 层面表达为：

```sql
owner_user_id IS NULL     -- 公海：无归属人
```

数据权限拦截器生成的**统一条件模板**：

```sql
AND (
      owner_user_id IS NULL          -- ① 公海数据：所有人可见（决策 4）
   OR <data_scope 条件>              -- ② 私海数据：按角色范围（决策 1、2）
)
```

**这个模板有一个很优雅的性质**：

> 对**没有公海概念**的表（`crm_contract`、`fin_payment` 等），
> 其 `owner_user_id` 是 `NOT NULL` 的，因此 `owner_user_id IS NULL` **恒为 false**，
> 条件自动退化为纯 `<data_scope 条件>`，无需为两类表写两套逻辑。

### 3.3 各 data_scope 的 SQL 生成规则

| data_scope | 生成的 SQL 条件 | 决策依据 |
| :--- | :--- | :--- |
| **1** 全部 | *不追加条件* | 财务、管理员 |
| **2** 自定义 | `AND (owner_user_id IS NULL OR dept_id IN (自定义部门集合))` | — |
| **3** 本部门 | ``AND (owner_user_id IS NULL OR dept_id = ${当前用户部门})`` | — |
| **4** 本部门及以下 | `AND (owner_user_id IS NULL OR dept_id IN (本部门+全部子部门))` | **决策 2** |
| **5** 仅本人 | `AND (owner_user_id IS NULL OR owner_user_id = ${当前用户ID})` | **决策 1 + 4** |

**「本部门及以下」的部门集合怎么算**：用 `sys_dept.ancestors` 做前缀匹配，
避免递归查树。

```sql
-- 查"销售部(3)"及其所有子部门
SELECT dept_id FROM sys_dept
 WHERE del_flag = 0
   AND (dept_id = 3 OR ancestors LIKE '0,1,3,%')
```

> `ancestors` 字段在建表时已设计好，就是为这一场景准备的。

### 3.4 参与数据权限的表

| 表 | 是否有公海概念 | 数据权限条件 |
| :--- | :--- | :--- |
| `crm_lead` | ✅ 有线索池（`owner_user_id` 可空） | `owner_user_id IS NULL OR <scope>` |
| `crm_customer` | ✅ 有公海（`owner_user_id` 可空） | `owner_user_id IS NULL OR <scope>` |
| `crm_opportunity` | ❌ 必有负责人 | `<scope>`（OR 分支恒 false） |
| `crm_quotation` | ❌ 必有负责人 | `<scope>`（OR 分支恒 false） |
| `crm_marketing_campaign` | ❌ | 同上 |
| `crm_sales_target` | ❌ | 同上 |
| `crm_contract` | ❌ | 同上 |
| `fin_payment` | ❌ | 同上 |
| `fin_invoice` | ❌ | 同上 |
| `crm_follow_up` | ❌ | 同上 |
| `crm_ticket` | ❌ | 同上 |

**不参与数据权限的表**（通过表名白名单排除）：

- 系统表：`sys_dept`、`sys_user`、`sys_role`、`sys_menu`、`sys_dict_*` 等
- 只追加流水表：`crm_owner_change_log`、`sys_operation_log`、`sys_login_log`

### 3.5 决策验证 —— 三句 SQL 走查

**场景**：销售专员(ID=100, 部门=销售部)查询客户列表

```sql
SELECT * FROM crm_customer
 WHERE del_flag = 0
   AND (owner_user_id IS NULL OR owner_user_id = 100);
```
✅ 看到自己的客户 + 全部公海客户 → **满足决策 1 和 4**

---

**场景**：销售总监(ID=200, 部门=销售部=3)查询客户列表

```sql
SELECT * FROM crm_customer
 WHERE del_flag = 0
   AND (owner_user_id IS NULL
        OR dept_id IN (SELECT dept_id FROM sys_dept
                        WHERE del_flag=0 AND (dept_id=3 OR ancestors LIKE '0,1,3,%')));
```
✅ 看到本部门及所有子部门的客户 + 公海 → **满足决策 2 和 4**

---

**场景**：财务(ID=300)查询客户列表

```sql
SELECT * FROM crm_customer WHERE del_flag = 0;
```
✅ 无附加条件，看到全部客户 → **满足决策 3**

### 3.6 公海数据可见 ≠ 可领取

**决策 4 说的是"看到"，不是"能拿"。** 这两个必须分开：

| 动作 | 权限层 | 规则 |
| :--- | :--- | :--- |
| 查看公海列表 | 数据权限 | 所有登录用户 ✅（决策 4） |
| **领取**公海数据 | 操作权限 + 业务规则 | 受 `crm_pool_rule.claim_limit` 领取上限约束 |
| **分配**给别人 | 操作权限 | 需要 `crm:customer:assign` 权限（通常仅主管/管理员） |
| 把别人的私海**放入公海** | 操作权限 | 需要 `crm:customer:toPool` 权限 |

**并发风险**：多人同时领取同一条数据 → 必须加锁（Redisson 分布式锁或乐观锁），
否则两个人会领到同一条。

>
> **关键落差**：唯一落地的那一处（看板金额）**并没有用本节设想的方案**，
> 而是照数据权限的老办法按**角色键硬编码**白名单。
> 也就是说本项目目前有**两套并存的思路**，而本节只描述了其中没实现的那一套。
>
> 后续要么补齐注解方案（需新建表 + 写 Jackson 序列化器），
> 要么沿用硬编码并回填本节 —— **别让两者继续各说各话**。
> 这与《07-测试BUG记录》BUG-003 **3.5** 里那段注同源 —— 那边也是「两套依据并存」：
> 超管判断在本项目有**三处、两套依据**（`roleKeys` vs `permissions`），
> 而只有走 Sa-Token 匹配的那条路会踩坑。

### 4.1 需要保护的字段

| 表 | 字段 | 敏感级别 | 建议规则 |
| :--- | :--- | :--- | :--- |
| `crm_product` | `cost_price` 成本价 | 🔴 高 | 仅 `admin` / `sales_director` 可见，其余返回 `null` |
| `crm_customer` | `phone` 联系电话 | 🟠 中 | 非归属人脱敏：`138****8888` |
| `crm_contact` | `phone` 手机号码 | 🟠 中 | 同上 |
| `sys_user` | `phone` 员工手机 | 🟠 中 | 同上 |
| `crm_contract` | `amount` 合同金额 | 🟠 中 | 按角色配置 |
| `fin_payment` | `amount` 回款金额 | 🔴 高 | 仅 `finance` / `admin` 可见 |
| `fin_payment` | `account_no` 收款账号 | 🔴 高 | 仅 `finance` / `admin` 可见 |
| `fin_payment` | `serial_no` 银行流水号 | 🟠 中 | 按角色配置 |

### 4.2 三种处理方式

| 方式 | 效果 | 适用 |
| :--- | :--- | :--- |
| **隐藏** | 字段从响应中完全移除（返回 `null` 或不出现在 JSON） | 成本价、银行账号 |
| **脱敏** | 保留部分字符，其余用 `*` 替换 | 手机号、身份证 |
| **只读** | 能看到但不能修改 | 合同金额（销售能看不能改） |

### 4.3 实现思路（不写代码，说清方案）

**方案：注解声明 + 序列化时按角色过滤**

```
① 在 VO 字段上标注解，声明该字段的可见角色与脱敏规则

   @FieldPermission(visibleRoles = {"admin", "sales_director"})
   private BigDecimal costPrice;

   @FieldPermission(mask = MaskType.PHONE)
   private String phone;

② 自定义 Jackson 序列化器，在对象转 JSON 时：
   ├─ 取当前登录用户的角色（从 LoginUserHolder）
   ├─ 判断字段是否对该角色可见
   ├─ 不可见 → 置为 null / 从输出中剔除
   └─ 需脱敏 → 按规则替换

③ 数据库存配置（可选增强）：
   用 sys_field_permission 表存"哪个角色对哪个表的哪个字段有什么权限"，
   支持不改代码动态调整
```

**为什么要做在序列化层**：

| 位置 | 问题 |
| :--- | :--- |
| 数据库查询时（SELECT 时排除列） | 每个 Mapper 的 SQL 都要改，且前端拿不到字段会报错 |
| **序列化时（采用）** | 一次拦截全部生效；字段名保留（前端结构稳定），只是值为 null |
| 前端隐藏 | **不安全** —— 数据已经传到浏览器，抓包就能看到 |

> ⚠️ **字段权限必须在服务端做**。前端隐藏只是"眼不见"，不构成安全边界。

### 4.4 需要新增的表

当前建表脚本（47 张）**没有字段权限配置表**，需要新增：

```sql
sys_field_permission  字段权限配置表
├── id                 主键
├── role_id            角色ID
├── table_name         表名（如 crm_product）
├── field_name         字段名（如 cost_price）
├── permission_type    处理方式（1隐藏 2脱敏 3只读）
├── mask_rule          脱敏规则（如 保留前3后4）
└── 审计字段
```

### 5.2 操作权限点（从原型按钮反推）

权限标识格式：`模块:资源:操作`

| 模块 | 权限标识 | 说明 |
| :--- | :--- | :--- |
| 线索 | `crm:lead:list` / `:create` / `:update` / `:delete` / `:export` | |
| 线索 | `crm:lead:toPool` | 放入线索池 |
| 线索池 | `crm:leadPool:assign` | **分配**（主管/管理员） |
| 线索池 | `crm:leadPool:claim` | **领取**（销售本人） |
| 客户 | `crm:customer:list` / `:create` / `:update` / `:delete` / `:export` | |
| 客户 | `crm:customer:toPool` | 放入公海 |
| 公海 | `crm:customerPool:assign` | 分配 |
| 公海 | `crm:customerPool:claim` | 领取 |
| 商机 | `crm:opportunity:*` | 含 `:addProduct` 添加产品 |
| 合同 | `crm:contract:*` | 含 `:submit` 提交审核 |
| 合同 | `crm:contract:audit` / `:batchAudit` | **审核**（审批人） |
| 产品 | `crm:product:*` | 含 `:onShelf` / `:offShelf` 上下架 |
| 财务 | `fin:payment:*` / `fin:payment:audit` | 回款登记 / 财务审核 |
| 财务 | `fin:invoice:*` / `fin:invoice:issue` | 发票登记 / 财务开票 |
| 系统 | `system:dept:*` / `system:user:*` / `system:role:*` / `system:dict:*` | 仅 admin |
| 系统 | `system:user:resetPwd` / `:disable` / `:resign` | 重置密码 / 禁用 / 操作离职 |

### 5.3 权限数据来源

```
sys_user ──N:M(sys_user_role)──> sys_role ──N:M(sys_role_menu)──> sys_menu
                                     │
                                     └── data_scope 决定数据范围
                                     └── N:M(sys_role_dept)──> sys_dept（自定义范围）
```

登录时一次性算出并写入 Session：
- `permissions`：权限标识集合（供 `@SaCheckPermission` 使用）
- `dataScope`：数据范围（取该用户所有角色中最宽的一个）
- `deptId` / `dataScopeDeptIds`：供数据权限拦截器使用

#### 超管是特例：权限被「替换」，不是「并集」⚠️

上面「合并所有角色的权限」这条规则**不适用于超级管理员**。
`admin`（`role_key = "admin"`）的权限不是从 `sys_role_menu` 汇总来的，
而是被**整体替换**成通配符：

| | 普通角色 | 超级管理员 |
| :--- | :--- | :--- |
| permissions 来源 | `sys_role_menu` → `sys_menu.perms`（并集） | **合成**，见 `AuthConstants.SUPER_PERMISSIONS` |
| permissions 内容 | 具体权限码，如 `crm:lead:list` | **只有** `["*:*:*"]` 一个值 |
| 菜单树 | 按 `sys_role_menu` 授权 | 取**全量**菜单（同样不看授权表） |

判断依据是 `roleKeys.contains("admin")`（`AuthServiceImpl`）—— **精确等值、大小写敏感**。
全项目共两处特例：`buildLoginUserContext` 合成权限、`buildMenuTree` 取全量菜单，
都是**有意不依赖**「admin 在 `sys_role_menu` 里被授了全部菜单」这条种子数据 ——
所以哪怕授权数据缺失，超管的权限也不受影响。

> ⚠️ **`*:*:*` 不是「匹配一切」的内建语法。**
> 它只是 Sa-Token 的一个普通通配模式（`SaFoxUtil.vagueMatch`），而模式里的 `:` 是**字面量**，
> 因此默认只能命中**三段式**权限码（`crm:lead:list`），命中不了两段式的 `dashboard:view`。
> 「等价于全部权限」这层语义由 `SaTokenConfig#overridePermissionMatching()` **显式**提供 ——
> 少了它，超管会被挡在首页看板门外（`dashboard:view` 恰好是全项目唯一的两段式权限点）。
> 完整分析见 `docs/07-测试BUG记录.md` 的 **BUG-003**。
>
> **推论：权限码一律写成三段式 `模块:资源:操作`。** 两段式不违反任何成文约定，
> 但会让通配符**静默失效** —— 只在超管账号上、只在那个权限点上暴露，极难定位。

## 六、权限判定总流程

```
用户登录
   │
   ├─ 查用户角色
   │     ├─ 普通角色 → 合并所有角色的 permissions（取并集）
   │     └─ admin     → 替换为 ["*:*:*"]，菜单树取全量（见 5.3）
   ├─ 合并 data_scope（取最宽）
   └─ 写入 Sa-Token Session
          │
          ▼
请求进入
   │
   ├─ ① 菜单权限：前端按 permissions 动态生成路由
   ├─ ② 操作权限：后端 @SaCheckPermission("crm:customer:delete")
   ├─ ③ 数据权限：MyBatis 拦截器自动注入 WHERE 条件
   └─ ④ 字段权限：Jackson 序列化时按角色过滤/脱敏
          │
          ▼
       返回结果
```

> ② 的权限匹配由 `SaTokenConfig#overridePermissionMatching()` **覆写**：
> 权限集里含 `*:*:*` 直接放行，其余仍走 Sa-Token 原生通配匹配
> （保留 `crm:lead:*` 这类部分通配的能力）。
> 不覆写的话，超管在**两段式**权限点（`dashboard:view`）上会被拒绝 —— 详见 BUG-003。
