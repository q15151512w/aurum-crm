## 三、① 接口文档 UI 对公网无凭证开放

**实测（修复前，两台都一样、全程不带 token）：**

```bash
curl -o /dev/null -w '%{http_code} %{size_download}\n' http://YOUR_SERVER_IP:8080/doc.html
# 200 1903        ← Knife4j UI 的 HTML 页面
curl -o /dev/null -w '%{http_code} %{size_download}\n' http://YOUR_SERVER_IP:8080/webjars/js/app.c31badf5.js
# 200 395970      ← 约 396KB 的 UI 脚本
```

**根因**是两件各自看都对的事凑在一起：

1. `SaTokenConfig.EXCLUDE_PATHS` 里留着开发期的文档路径白名单；
2. **`knife4j.enable: false` 只关掉了 Knife4j 的自动配置 Bean，
   关不掉 jar 包里的静态资源** —— UI 在 `META-INF/resources/` 下，
   由 Spring Boot 默认的静态资源处理器提供，与 Knife4j 的开关毫无关系。

**危害有限但真实**：接口清单**没有**泄露（`/v3/api-docs` 确实拿不到），
打开的只是空壳 UI。但**只要有人把 `springdoc.api-docs.enabled` 改回 `true`，
清单会立刻从这个口子一起漏出去** —— 一个静默失效的开关不值得留。

**修复**：白名单按 profile 拆分，文档路径只在非 prod 环境放开。
判据写成「prod 未激活」而非「dev 已激活」—— 除 prod 外其余环境行为一个字节不变，
改动影响面和意图完全重合；反过来写会让同事用自定义 profile 起本地环境时
突然看不到文档，而且报的是 **401**，会被当成登录问题去排查。

**已发布并复验**（2026-09-15 17:53）：

| 入口 | 修复前 | 修复后 |
|---|---|---|
| `148:8080/doc.html` | 200 / 1903 | **200 / 77（`code:401`）** |
| `121:8080/doc.html` | 200 / 1903 | **200 / 77（`code:401`）** |
| `.../api/doc.html`（nginx） | 200 / 1903 | **200 / 77（`code:401`）** |
| `.../webjars/js/app.*.js` | 200 / 396KB | **200 / 77（`code:401`）** |

发布后跑回归确认白名单收窄没误伤登录链路（验证码、登录、`/auth/me`、
`/favicon.ico`、`/actuator/health`、看板/客户/用户/发票/AI 会话、
非法路径参数 400、未知路由 404）—— **12 / 12 通过**。

## 四、② 公海领取上限：一条从没被测过的生产路径

`PoolClaimLimiter`（公海/线索池**每日领取上限**，读 `crm_pool_rule`，超限抛 `2601`）
是后加进 `CustomerPoolServiceImpl#claim()` 的依赖，而测试没同步补 mock ——
`claim()` 的**第一行**就调它，于是用例直接 NPE。

> ⚠️ 这个失败方式特别误导：`claim_alreadyOwned_throws2103` 断言的是「抛 2103」，
> 实际抛的是 NPE，终端只说「期望 `ServiceException` 实际 `NullPointerException`」，
> **完全指不到「少声明了一个 mock」这个真因**。

**已补两条用例**：

- `claim_checksLimitBeforeTouchingAnyData` —— 上限校验必须在**碰任何数据之前**
  （含 `inOrder` 顺序断言：若校验被挪到查询之后，已超限的人仍会先把客户读出来，
  结果看起来一样，只有顺序断言挡得住）；
- `claim_limitReached_throws2601AndWritesNothing` —— 超限抛 2601 时
  **一个写操作都不能发生**。

**线上配置实测**（只读查询）：

| rule_id | pool_type | claim_limit | claim_cycle | enabled |
|---|---|---|---|---|
| 1 | 1（线索池） | 50 | 1（今日） | 1 |
| 2 | 2（客户池） | 20 | 1（今日） | 1 |

**规则是启用的**，也就是说这条路径每天都在跑 —— 只是一直没有测试，
也从没真正拦住过人（实测当日该用户线索 6/50、客户 2/20，远未触顶）。
**这正是它长期没被发现的原因。**

> ⏳ **仍未做**：线上实测（需要真去领公海客户，会改真实归属）。
> 想验的话：把 `crm_pool_rule` 客户池限额临时调低 → 领到触顶 → 确认返回 2601
> → 把限额改回。**做之前先想清楚那几条客户的归属怎么恢复。**

## 五、③④ 两处「测试自身」的问题

### 5.1 `SalesOwnerOptionsTest` 断言了会自然变化的数字（BUG-030）

它断言 `hasSize(3)`，而它直连的是**早就有真实业务数据的库** ——
实测返回 12 人。每加一个销售就红一次，**且红得毫无意义**。
这种「狼来了」测试比没有测试更糟：跑红几次之后大家就学会忽略它。

> 📌 排查时先确认过**不是数据漂移**：`sql/crm.sql` 的 `sys_user_role` 种子注释
> 写明「种子只有 4 个角色，非销售岗位暂挂它」—— 结果里的仓管/质检/采购/生产
> 是被**有意**挂在 `sales` 角色上的。库与种子完全一致。

改为断言接口真正该保证的东西（非空、姓名/部门有值、种子销售岗必须查得到）。

> ⚠️ **如实标注了它挡不住什么**：它挡不住「过滤写宽成返回全表」——全表照样包含
> 那几个 id。已在注释里写明，免得后来的人以为它能兜住「下拉混进非销售岗位」。

### 5.2 权限注解被一个 `docs:` 提交删掉（BUG-031）

```bash
$ git show d3bcd8e -- .../UserController.java
  1 file changed, 1 deletion(-)
-    @SaCheckPermission("system:user:list")
```

`d3bcd8e` 的提交信息是 **`docs:修复部分合同 产品bug`**，实际改了
**42 个文件、1024 行**，而对 `UserController` 的唯一改动就是删掉这一行。

**实测后果**：

```
sales01 是否持有 system:user:list : False

GET /system/user?pageNum=1        →  code=403   ← 拦截正常
GET /system/user/simple-list      →  code=0, 返回 10 条人员数据
   样本：{"id":1,"name":"超级管理员","username":"admin",
          "phone":"13800000001","deptId":1,"deptName":"零捌集团"}
```

而且**代码与自己的注释矛盾**：`/options` 的 javadoc 原话是
「**这里保留原端点的严格性**，另开一个语义明确的『选择器端点』」，
可那一行严格性恰恰被同一个提交删掉了。

**影响没有夸大**：`/options` 本就是有意「仅需登录」且返回全部 17 人，
`simple-list` 暴露的是它的**子集**，所以**没有扩大泄露面**。
真正的问题是「权限边界靠另一条路也能走」来兜底 —— 那是巧合，不是设计。

**处置**：恢复注解（与既定设计一致，且前端 `getUserSimpleList` 已无调用方）。

**并加了自动门禁** `UserControllerPermissionTest` —— 因为这类改动是「隐形」的：

| 环节 | 删掉注解后会怎样 |
|---|---|
| 编译 | 不报错 |
| 单测 | **不红**。本项目单测全是纯 Mockito 单测，**不加载 Spring 上下文**，压根不经过 `SaInterceptor`，注解在与不在跑得一模一样 |
| 接口 | 不报错。少一道校验只会让请求**更顺畅**地通过 |

唯一暴露方式是「拿低权限账号真的去调一次」—— 要人工、要记得做。
门禁把这件事变成一次 `mvn test`：

1. `UserController` 每个 `@XxxMapping` 方法都必须带 `@SaCheckPermission`，
   除非在 `LOGIN_ONLY` 白名单（当前只有 `options`，1 条）；
2. 定点回归：`simpleList` 必须要求 `system:user:list`，**连权限码本身都钉死**。

> ✅ **验证过「它在 bug 存在时确实会红」**：临时删掉注解后跑，2 条用例都失败，
> 报错信息直接点名 BUG-031 和该怎么处理；恢复后转绿。
> 不做这一步的话，「新加的测试」和「没有测试」在体感上没区别。

## 八、本轮踩到的三个「验证方法」上的坑（比 bug 本身更值得记）

1. **读到了陈旧的 surefire 报告**。跑门禁测试时漏了 `-am` → 编译失败 →
   Maven 没重新生成报告 → 读到的还是**上一次运行的结果**（`Elapsed` 一模一样）。
   差点当成「验证成功」。
   **规则：断言测试结果前，先确认报告是这次生成的。**

2. **「配置写了」不等于「生效了」**。修复①的根因就是
   「`knife4j.enable: false` 写得明明白白，但没人 curl 一下」。
   **规则：加固措施按实际响应验收，不按配置项验收。**

3. **测试断言了会自然变化的数据**。`hasSize(3)` 对着一个早就不是干净状态的库，
   每次加数据就红一次。
   **规则：断言「契约」，不断言「此刻有几行」。**

> 还有一条不算坑但值得记：**一个标着 `docs:` 的提交删掉了权限注解**。
> 提交信息的前缀是排查时的第一入口，标错了等于指错方向。
