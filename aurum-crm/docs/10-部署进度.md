## 日常管理

```bash
cd /root/CRM/aurum-crm
./service.sh start      # 启动（启动前自动备份当前 jar，内容未变则跳过）
./service.sh stop       # 优雅停机，120 秒等不到才强杀
./service.sh restart    # 重启
./service.sh rollback   # 回滚到上一版 jar 并重启
./service.sh status     # PID / 运行时长 / 端口 / 健康检查 / 磁盘 / 备份列表
./check-env.sh          # 环境体检（只读，不改任何东西）
```

### 发版流程

```cmd
:: 本地
cd /d <项目根目录>
git pull
mvn -DskipTests clean package

:: 上传前【必查】：prod 配置进没进 jar
unzip -l crm-server\target\crm-server.jar | findstr application-

:: 传，先落 /tmp 再就位（scp 中途断线会留截断的 jar）
scp crm-server\target\crm-server.jar root@YOUR_SERVER_IP:/tmp/crm-server.jar.new
```

```bash
# 服务器上
cd /root/CRM/aurum-crm
./service.sh stop                      # ⚠️ 先停再覆盖，别覆盖运行中的 jar
mv -f /tmp/crm-server.jar.new crm-server.jar
./service.sh start                     # 启动时自动备份新 jar
```

出事：`./service.sh rollback`。

### ⚠️ 现在是两台 —— 发版要【滚动】

上面那份流程是单机时写的。**两台之后，千万别同时停** —— 那就是全站不可用，
白白浪费了集群的意义。正确做法是一台一台来：

```
① 停第一台 → 换 jar → 起第一台 → 确认 health UP
   （这期间所有流量由第二台扛，nginx 会把请求都给它）
② 再停第二台 → 换 jar → 起第二台 → 确认 health UP
```

**每台起来确认后再动下一台。** 中间任何一步 health 不 UP 就停下来查，
别继续往下走 —— 那样会从「一半容量」变成「零容量」。

> ⚠️ **两台不能长期跑不同版本的 jar**。数据库 schema 只升不降，
> 新 jar 依赖的列旧 jar 不认识；而且 `sql/` 下的增量脚本是新 jar 的前提。
> 滚动只是把「不一致窗口」压到几分钟，不是允许长期并存。

> ⚠️ **仍然不要在 03:00–03:15 之间发版** —— 那是待办提醒定时任务的窗口。

**`-DskipTests` 不能省**：`crm-server/src/test` 下的两个 `@SpringBootTest`
是 `@ActiveProfiles("dev")`，会连真实数据库跑测试。
但也别用 `-Dmaven.test.skip=true` —— 那样连测试代码都不编译，白丢一次编译期预检。

## 踩过的坑（复用这个部署方案时值得先看一眼）

**① `flock` 锁被子进程继承 → 服务再也停不掉**
并发锁挂在 fd 9 上，而 `nohup java ... &` 拉起的 JVM **默认继承父进程的 fd**。
锁绑定在"打开文件描述"上被父子共享，于是应用只要活着锁就永远不释放，
之后每次 `stop`/`restart` 都报"另一个操作正在进行中"——**而 stop 也走这条路，
等于再也停不掉服务**。修复：`nohup ... 2>&1 9>&- &`。

**② 这台机器 PID 回绕很快（约 25 分钟一轮）**
`kernel.pid_max` 是 32768，而云监控进程 fork 频繁，
PID 会从两万多突然掉回几百。所以**绝不能只信 PID 文件** ——
`service.sh` 用 `/proc/<pid>/cmdline` 校验进程身份，把 PID 回收导致的误杀挡在外面。
这不是理论风险，是这台机器上每天都会发生的事。

**③ `/doc.html` 返回 200 不代表文档开着**
它是打进 jar 的静态 HTML 外壳。判据要看 `/v3/api-docs` 是不是返回 API 清单。

> ⚠️ **但反过来不成立**：不能因为「清单没泄露」就认为这条路径没问题。
> 早期版本的冒烟脚本就是这么判的，把「UI 外壳对公网开放」判成了 PASS ——
> 见坑⑪，那是个**假通过**。

**④ `check-env.sh` 第 4 项在服务运行时曾误报"8080 被占用"**
占用者就是应用自己。已修复：现在会读 `/proc/<pid>/cmdline` 分辨是不是本应用。

**⑤ `sql/crm.sql` 是**全量重建脚本，含 49 条 `DROP TABLE`**
**在生产库上执行等于清库。** 需要补数据时只执行增量部分，别整个文件跑。

**⑧ 未匹配的路由返回 HTTP 500，而不是 404**

2026-09-15 全量测试时发现：请求任何不存在的路径（`GET /no/such/route`），
返回的是 `{"code":500,"message":"服务器内部错误"}`，**并且每次都打一整条 ERROR 堆栈**。

根因是 Spring 6.1（Boot 3.2+）把「找不到路由」统一抛成 `NoResourceFoundException`，
它不在 `GlobalExceptionHandler` 已处理的任何异常链上，直接落到了 `Exception` 兜底分支。

> ⚠️ **为什么这个不能不管**：前端 `src/utils/request.js` 的契约是
> 「HTTP 200 + body.code」，而 **HTTP 500 是它唯一不走 `body.code` 的分支** ——
> 会被当成「服务端崩了」并弹通用错误。实际上只是 URL 拼错，改一处路径就能好，
> 报错方向完全被带偏。
>
> 另一半是日志：公网上任何扫描器乱扫路径都会命中这里，
> ERROR 堆栈被灌满之后，**真正的服务端异常会被淹没在噪音里**。

已修复：`GlobalExceptionHandler` 增加 `NoResourceFoundException` / `NoHandlerFoundException`
处理，返回 HTTP 200 + `body.code=404`（与相邻的 400/403/405 保持一致），
日志降为 WARN 且不打堆栈。日志里的路径做了控制字符清洗（防日志注入）+ 截断。

**⑩ 用户关一次 AI 页面，日志里就多一条 ERROR 堆栈**

和坑⑧同一类毛病。`AsyncRequestNotUsableException`
（`ServletOutputStream failed to flush: Connection reset by peer`）
是**客户端提前断开**，被 `Exception` 兜底分支接住，打成 ERROR + 完整堆栈。

**触发条件是「客户端在服务端正在写响应体时断开」**，实测（2026-09-15，用独立实例开 DEBUG 验证）：

| 场景 | 会不会触发 |
|---|---|
| 导出 / 大列表页，用户没等加载完就切走 | ✅ 触发 |
| 健康检查 `curl -m 6` 超时掐断（线上第一次就是这么出现的） | ✅ 触发 |
| **硬断 AI 小助手的 SSE 流** | ❌ **不触发** |

> ⚠️ 最后一行是实测结论，别想当然。SSE 流的写入是「小段、间歇」的，
> 断开往往落在两次写入之间，压根不产生写失败。
> （一开始我以为「用户关 AI 页面」是主要来源，实测证明不是 —— 已在文档更正。）

> ⚠️ 导出这类还叠加一层副作用：**OSS 上的文件已经传上去了，但客户端没拿到地址** ——
> 于是桶里留下一个没人引用的孤儿文件。见「还没做的」里的 OSS 清理那条。

> 危害：**真正的服务端异常会被 Connection reset 淹没**，
> 排查线上问题时容易误判成网络故障。

已修复：`GlobalExceptionHandler` 增加 `AsyncRequestNotUsableException` 专用处理，
打 **DEBUG** 且无堆栈，返回 `void`（连接已断，写响应体只会在坏连接上再抛一次）。

> 用 DEBUG 而不是 WARN 是有意的：这不是客户端的**错误**，是正常的连接生命周期事件 ——
> 和「参数传错」那种 WARN 不是一回事。生产日志级别是 `info`，所以默认不打。
> 需要看的时候打开 `logging.level.com.aurum.crm.common.exception=debug` 即可。
> 想发现「服务端变慢导致大量客户端超时」，靠的是响应时间指标，不是刷断开日志。

**⑪ 接口文档 UI 对公网无凭证开放（`knife4j.enable: false` 关不掉它）**

2026-09-15 全量测试时实测发现，**两台都一样**：

```bash
curl -o /dev/null -w '%{http_code} %{size_download}\n' http://YOUR_SERVER_IP:8080/doc.html
# 200 1903        ← Knife4j UI 的 HTML 页面
curl -o /dev/null -w '%{http_code} %{size_download}\n' http://YOUR_SERVER_IP:8080/webjars/js/app.c31badf5.js
# 200 395970      ← 约 396KB 的 UI 脚本
```

全程**不带任何 token**，直连 `:8080` 和走 nginx 的 `/api/doc.html` 都能拿到。

**根因**：两件事各自看都对，凑一起才出问题。

1. `SaTokenConfig.EXCLUDE_PATHS` 里留着开发期的文档路径白名单
   （`/doc.html`、`/webjars/**`、`/v3/api-docs/**`、`/swagger-ui/**`、`/swagger-resources/**`）。
2. **`knife4j.enable: false` 只关掉了 Knife4j 的自动配置 Bean，关不掉 jar 包里的静态资源。**
   UI 文件在 `knife4j-openapi3-jakarta-spring-boot-starter` 的
   `META-INF/resources/doc.html` 和 `META-INF/resources/webjars/**`，
   由 **Spring Boot 默认的静态资源处理器**提供 —— 和 Knife4j 的开关一点关系都没有。

> ⚠️ 这是「配置看起来生效了、实际没有」的典型：`knife4j.enable: false` 加上
> `springdoc.api-docs.enabled: false` 一读就觉得万事大吉，但**没人去 curl 一下**。
> 加固措施必须按「实际响应」验收，不能按「配置项写了」验收。

**危害程度**：接口清单**没有**泄露 —— `/v3/api-docs` 确实拿不到，
打开的只是个空壳 UI。但仍不该对公网开着：白送带宽、对外宣告技术栈，
而且**只要哪天有人把 `springdoc.api-docs.enabled` 改回 true，
接口清单会立刻从这个口子一起漏出去** —— 一个静默失效的开关不值得留。

**已修复并已发布**（2026-09-15 17:53，两台滚动重启，包 `cfe69cce`）。

prod 下走 `SaInterceptor` 要求登录。

```java
// SaTokenConfig.java —— 判据是「prod 未激活」而非「dev 已激活」
private String[] excludePaths() {
    boolean prod = Arrays.asList(environment.getActiveProfiles()).contains("prod");
    if (!prod) {
        return Stream.concat(Arrays.stream(BASE_EXCLUDE_PATHS),
                        Arrays.stream(DOC_EXCLUDE_PATHS)).toArray(String[]::new);
    }
    return BASE_EXCLUDE_PATHS;
}
```

> **为什么判据写成「prod 未激活」而不是「dev 已激活」**：除 prod 外其余环境的现有行为
> 一个字节都不变，改动的影响面和意图完全重合。反过来写的话，同事用 `local` 之类自定义
> profile 本地起服务会突然看不到文档，而且报的是 **401** —— 会被当成登录问题去排查。
> 静默锁死的代价比多放开一点更大。

> **`/actuator/**` 目前也在白名单里**，但 `exposure.include` 只有 `health,info`
> （实测 `/actuator/env` 拿到 404 兜底、`info` 返回 `{}`），当前不泄露东西。
> 留个心眼：**这个白名单是 `/actuator/**` 全通配**，哪天有人往
> `exposure.include` 里加 `env`、`heapdump`，会立刻变成公网可读。改 actuator 配置时一并看这里。
