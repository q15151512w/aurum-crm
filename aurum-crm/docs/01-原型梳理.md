# 第一部分：原型梳理

## 1. 总体

| 项 | 内容 |
|---|---|
| 名称 | 【实战项目原型】客户关系管理系统 - CRM |
| 规模 | **107 个页面**，6 个业务模块 + 基础设置（共 7 个模块）|
| 来源 | 商业付费模板，演示页标注「无任何实际功能」 |
| 制作方式 | **Figma 导入 Axure**（图层名全是「矩形 / 形状 / 组合 / 外框 / 线段 / 圆形」，图标资源全是 `uNNNN.svg`） |
| 授权 | 商业模板，直接商用需购买源文件 |

## 2. 全局骨架

所有内页共用一个外壳。

**左侧一级导航（固定 8 项）**

```
首页 · 线索管理 · 客户 · 商机 · 合同 · 产品类型 · 回款登记 · 组织架构
```

**顶栏**：搜索框 + 右侧「个人设置」下拉（个人信息 / 个人资料 / 修改密码 / 退出系统），点击切换可见性，**300ms 渐显**。

**列表页统一结构**：搜索框 → 操作按钮组 → 表格。

**二级导航**（进入模块后出现）：如线索模块下有「线索管理 / 线索池 / 新增线索 / 删除线索 / 放入线索池」；基础设置模块下有「组织架构 / 人员管理 / 角色权限 / 登陆日志 / 编号定义 / 计量单位」。

> 注：原型里模块二级导航用**动态面板状态**切换（`主页` / `选中`），同一页面承载多个视图。

## 3. 业务主线

```
线索 ──转化──> 客户 ──> 商机 ──> 报价单 ──> 合同 ──> 回款 ──> 发票
  │              │                                        │
线索池          公海                                    财务审核
(分配/领取)    (分配/领取)                              (合同审核 / 回款审核 / 开票)
```

典型的 **LTC（Leads to Cash）** 流程。

两条「资源回收」支线贯穿全程：线索进**线索池**、客户进**公海**，均支持两种再分配方式：

- **分配** —— 管理员指派给某负责人
- **领取** —— 员工自取

## 4. 模块清单

| 模块 | 列表 / 主页 | 详情 | 弹窗 / 操作页 |
|---|---|---|---|
| **线索** | 线索管理、线索池 | 线索详情 | 新增线索、删除线索、放入线索池、分配、领取、删除线索池、负责人 |
| **客户** | 客户、公海 | 客户详情 | 新增客户、删除客户、放入公海、分配、领取、负责人 |
| **商机** | 商机 | 商机详情、商机报价单 | 新增商机、删除商机、选择客户、选择商机、添加产品、负责人 |
| **合同** | 合同、合同审核 | 合同详情 | 新增合同、删除合同、选择客户 / 商机 / 报价单、客户签约人、公司签约人、添加产品、合同提交审核、审核、批量审核 |
| **产品** | 产品类型、产品 | — | 新增类型、删除类型、新增产品、删除产品、上架、下架 |

**⚠️ 重要**：原型里的「弹窗」其实是**独立 HTML 页面**——用 `打开 XXX 在当前窗口` 整页跳转实现，不是真弹窗。开发时需自行改为 Modal。

## 5. 详情页 Tab 结构

**客户详情（10 个 Tab）**

```
基础信息 · 联系人 · 开票信息 · 商机报价单 · 商机 · 合同 · 回款 · 发票 · 附件 · 操作记录
```

**合同详情（6 个 Tab）**

```
基础信息 · 产品 · 回款 · 发票 · 附件 · 操作记录
```

这个划分很能说明信息架构：**客户是一切关系的中心**，商机 / 合同 / 回款 / 发票全部挂在客户之下；而合同作为履约主体，又聚合了产品明细与回款 / 发票。

## 6. 字段线索

### 6.1 列表页没有假数据

逐页核实结论：列表页表格**不含任何数据行文本**。表格元件（Axure `table`）的单元格内容只有**头像图片 + 背景色**，例如：

```
tableCell → { 背景色: 0xFFEBECF0, 图片: images/首页/u536.png }
```

全页中文文本仅 124 条，几乎全是交互脚本名与按钮名。

**实践含义**：无法从原型直接提取列表字段的完整定义，需自行设计。

### 6.2 搜索框占位符反推出的关键字段

搜索框的 placeholder 恰好暴露了每张表的关键字段：

| 实体 | 关键字段 |
|---|---|
| 线索 | 线索名称 / 负责人 |
| 客户 | 客户名称 / 负责人 / 联系电话 |
| 商机 | 商机名称 / 负责人 |
| 报价单 | 报价单名称 / 商机名称 |
| 合同 | 合同名称 / 合同编号 / 客户 |
| 发票 | 发票申请编号 / 发票号 |
| 联系人 | 姓名 / 手机号码 / 职务 |
| 人员 | 姓名 / 手机号码 / 部门 |

### 6.3 表单字段（新增客户页，信息最完整）

- 电话号码（placeholder：请输入电话号码）
- 邮箱（placeholder：请输入邮箱）
- 负责人
- 详细地址
- **省市区三级联动**：一级（山东省 / 江西省）→ 二级（潍坊市 / 上饶市）→ 三级（寒亭区 / 信州区）
- **日期选择器**：动态面板「选择日期-1」，向下滑动 100ms 展开

## 7. 通用交互组件

以下 5 个组件在全站反复复用，是原型里最有价值的部分——前端完全可以做成公共组件。

| 组件 | 实现方式 | 复用范围 |
|---|---|---|
| **成功提示条** | `显示 XX成功 向下滑动 200ms` → `等待 1500ms` → `隐藏 向上滑动 200ms` | 全站所有操作反馈 |
| **左侧导航高亮** | 动态面板状态 `主页` / `选中` | 全站 |
| **关注 / 取消关注** | 「星星面板」动态面板 State1 / State2 切换 + 提示条 | 列表页与详情页 |
| **通用下拉选择器** | 动态面板 State1 / State2，默认「请选择」，选中后回填 `[[This.text]]` | 所有负责人 / 选择客户 / 选择商机 / 直属上级 |
| **通用分页选择器** | 独立页面 + 搜索框（如「姓名/手机号码/部门」）+ 表格 | 选择客户 / 选择商机 / 选择报价单 / 选择角色人员 / 负责人 |

> **复用洞察**：「选择客户 / 选择商机 / 选择报价单 / 选择角色人员 / 负责人」这 5 个页面本质是**同一个组件的不同数据源**（后端统一为 `GET /{模块}/{资源}/simple-list`，前端已覆盖 **12 类**，清单见《05-接口文档》第十节）。后端可统一为「按资源类型分页搜索」一个接口模式，前端共用一个选择器组件。

## 8. 实现痕迹与坑

1. **复制粘贴残留**：分配页、领取页、放入公海页的左侧菜单容器名叫「**供应商管理菜单**」——该模板大概率由另一套「供应商管理」原型改造而来。**开发时不要被这些命名误导**。

2. **跨页图片引用**：客户页引用 `images/首页/`，合同页引用 `images/客户详情/`，说明页面间是复制关系。

3. **审核流程只有 UI，没有状态机**：合同审核 / 批量审核 / 财务回款审核都只是点击后弹「审核通过 / 审核拒绝」提示条，没有状态流转、驳回原因、多级审核逻辑。

4. **权限只做了壳**：角色权限页仅有「权限配置 / 角色人员」两个 Tab 和两个角色组（组组合一 / 组组合二），**权限树的具体粒度没做**。

5. **登录页是做得最扎实的一页**，完整实现了：
   - 密码登录 / 验证码登录双模式切换
   - 注册账号、忘记密码
   - 60 秒倒计时（全局变量 `Time`，每 1000ms 递减，归零后重新启用）
   - 手机号校验：`是数字 并且 长度 == 11` 才启用「获取验证码」
   - 聚焦 `onFocus` / 失焦 `onLostFocus` 控制 placeholder 与选中态

6. **细节彩蛋**：编号定义页有 iOS 风格开关——圆点 `移动 到达 (22,)` / `到达 (3,)`，线性 100ms。

## 9. 结论：这套原型能用来做什么

**有价值的**：信息架构、导航结构、详情页 Tab 划分、列表页组件复用模式、线索池 / 公海的双轨机制、LTC 主线的单据串联关系。

**不能直接照搬的**：

| 缺口 | 说明 |
|---|---|
| 列表字段 | 无数据行，只能从搜索框反推，需自行定义 |
| 弹窗 | 是独立页面，需改为真 Modal |
| 状态机 | 审核流、单据状态流转完全没做 |
| 权限模型 | 权限树粒度未定义 |
| 数据模型 | 无字段类型、无约束、无表关系定义 |
| 编号规则 | 有「编号定义」页面，但规则引擎未实现 |

# 第二部分：接口开发优先级

## 10. 优先级排序原则

不按模块平均分配，而按**依赖关系**排：

1. **先解阻塞** —— 被最多模块依赖的基础能力先做
2. **再通主线** —— 让「线索 → 客户 → 商机 → 合同」端到端跑通一条
3. **后补机制** —— 资源池流转、审核流、权限细化
4. **最后辅助** —— 日志、附件、看板统计

> **关键判断**：这个系统的骨架是**数据权限**。「负责人」字段、线索池、公海、角色权限，四件事本质依赖同一套「数据范围」控制（全部 / 自定义 / 本部门 / 本部门及以下 / 仅本人，见《04-权限设计文档》2.2）。**建议在 P0 阶段就把数据权限模型定下来，否则后面积累返工。**

## 11. P0 — 基础支撑层（阻塞项，先做）

> **为什么最先**：负责人选择器、组织架构、权限菜单在所有列表页和表单里都出现；登录是所有页面的前置。

### 11.1 认证鉴权

| 接口 | 说明 |
|---|---|
| `POST /auth/login` | 密码登录 |
| `POST /auth/sms/code` | 发送验证码（**60s 限流**，对应原型的 `Time` 变量倒计时） |
| `POST /auth/login/sms` | 验证码登录 |
| `POST /auth/register` | 注册账号 |
| `POST /auth/password/forgot` | 忘记密码 |
| `PUT /auth/password` | 修改密码（顶栏入口，请求体 `{ oldPassword, newPassword }`） |
| `GET /auth/me` | 当前用户 + 权限 + 菜单树（**前端路由与菜单渲染依赖此接口**） |
| `POST /auth/logout` | 退出系统 |

### 11.2 组织与人员

> 被「负责人 / 直属上级 / 部门负责人 / 客户签约人 / 公司签约人 / 选择角色人员」共 **6 处选择器**依赖，是最高频的底层数据。

| 接口 | 说明 |
|---|---|
| `GET /system/dept/tree` | 部门树（组织架构页 + 选择器） |
| `POST /system/dept`、`PUT /system/dept/{id}`、`DELETE /system/dept/{id}` | 新增 / 编辑 / 删除部门 |
| `PUT /system/dept/{id}/leader` | 部门负责人 |
| `GET /system/user` | 分页 + 关键字搜索（**选择器专用**，需支持按部门过滤） |
| `POST /system/user`、`PUT /system/user/{id}`、`DELETE /system/user/{id}` | 新增 / 编辑 / 删除人员 |
| `PUT /system/user/{id}/superior` | 直属上级 |
| `PUT /system/user/{id}/status` | 激活 / 禁用 / 操作离职（三态合一） |
| `POST /system/user/{id}/reset-password` | 重置密码 |

### 11.3 角色权限

| 接口 | 说明 |
|---|---|
| `GET /system/menu/tree` | 权限树（**依赖菜单结构先定稿**） |
| `GET /system/role`、`POST /system/role`、`PUT /system/role/{id}`、`DELETE /system/role/{id}` | 角色 CRUD |
| `GET /system/role-group`、`POST /system/role-group`、`DELETE /system/role-group/{id}` | 角色组 CRUD |
| `GET /system/role/{id}/permissions`、`PUT /system/role/{id}/permissions` | 权限配置读写 |
| `GET /system/role/{id}/users`、`POST /system/role/{id}/users`、`DELETE /system/role/{id}/users` | 角色人员（选择角色人员弹窗） |

### 11.4 数据字典 / 基础配置

| 接口 | 说明 |
|---|---|
| `GET /system/numbering-rule`、`POST`、`PUT /{id}`、`DELETE /{id}` | 编号定义（含启停开关） |
| `GET /system/unit`、`POST`、`PUT /{id}`、`DELETE /{id}` | 计量单位 |
| `GET /crm/product-category/tree`、`POST`、`PUT /{id}`、`DELETE /{id}` | 产品类型（**虽属产品模块，但被产品 / 商机 / 合同依赖，提前到 P0**） |
| `GET /crm/region/tree`（**可选**）| 省市区三级数据（新增客户表单依赖）。本期前端用本地静态数据，未接接口 |

> **编号规则引擎**属于横切能力：所有单据新增时都要调用它生成编号。建议在 P0 末尾、P1 开始前完成。

## 12. P1 — 主业务线（让一条闭环跑通）

> **为什么这个顺序**：严格按业务流向 线索 → 客户 → 商机 → 报价单 → 合同。前者是后者的数据来源，倒过来做会出现大量空实现。

**每个实体统一一套 7 个接口**（下文不再重复展开）：

```
GET    /{resource}              分页列表（关键字 + 筛选 + 排序 + 分页）
GET    /{resource}/{id}         详情
POST   /{resource}              新增
PUT    /{resource}/{id}         编辑
DELETE /{resource}/{id}         删除
DELETE /{resource}              批量删除
GET    /{resource}/export       导出
```

### 12.1 线索 `leads`

- 上述标准 7 接口
- `POST /leads/{id}/convert` —— **线索转客户**（主线关键节点，打通线索→客户）
- 子资源：附件
- 【扩展】跟进记录（`crm_follow_up`）—— **原型无此页面**，属主动扩展，见《02-建表文档.md》第二节注

### 12.2 客户 `customers`

- 上述标准 7 接口
- 子资源（对应详情页 Tab）：
  - `GET/POST/PUT/DELETE /customers/{id}/contacts` —— 联系人（姓名 / 手机号码 / 职务）
  - `GET/POST/PUT/DELETE /crm/invoice-info`（按 `customerId` 查）—— 开票信息
  - `GET /customers/{id}/timeline` —— 操作记录
- `GET /customers/{id}/related` —— 聚合关联的商机 / 合同 / 回款 / 发票（详情页多个 Tab 可一次拉取）

### 12.3 商机 `opportunities`

- 上述标准 7 接口
- 子资源：产品明细 `opportunity-products`（对应「添加产品」弹窗）
- 关联：`customer_id`（选择客户）

### 12.4 报价单 `quotations`

- 上述标准 7 接口
- 关联：`opportunity_id`（选择商机）、产品明细

### 12.5 合同 `contracts`

- 上述标准 7 接口
- 子资源：产品明细
- 关联：客户 / 商机 / 报价单 / 客户签约人 / 公司签约人
- 编号：调用编号规则引擎生成「合同编号」

## 13. P2 — 资源池机制

> 依赖 P1 的线索与客户实体，且强依赖 P0 的数据权限模型。

### 13.1 线索池

| 接口 | 说明 |
|---|---|
| `GET /lead-pool` | 线索池列表 |
| `POST /leads/{id}/to-pool` | 放入线索池 |
| `POST /lead-pool/{id}/assign` | 分配（管理员指派负责人） |
| `POST /lead-pool/{id}/claim` | 领取（员工自取，**需并发控制防重复领取**） |
| `DELETE /lead-pool/{id}` | 删除 |

### 13.2 公海（客户）

| 接口 | 说明 |
|---|---|
| `GET /customer-pool` | 公海列表 |
| `POST /customers/{id}/to-pool` | 放入公海 |
| `POST /customer-pool/{id}/assign` | 分配 |
| `POST /customer-pool/{id}/claim` | 领取（**同样需并发控制**） |
| `DELETE /customer-pool/{id}` | 删除 |

> ⚠️ **并发陷阱**：「领取」是典型的抢单场景。原型只做了 UI，实际必须加乐观锁或分布式锁，否则两个人会领到同一条。

## 16. 横切关注点（贯穿所有阶段）

这些不是独立阶段，但需要**在 P0 期间就定下规范**：

### 16.1 数据权限 ⭐ 最高优先级

系统里四个看似无关的功能其实共享同一套机制：

| 功能 | 依赖的数据范围 |
|---|---|
| 「负责人」字段 | 只能选到权限范围内的人 |
| 线索池 / 公海 | 只能看到 / 领取范围内的数据 |
| 角色权限 | 决定范围大小 |
| 列表页 | 所有查询自动注入数据范围条件 |

**建议**：P0 阶段定义统一的 `DataScope`（本人 / 本部门 / 本部门及下级 / 全部），做成查询层的强制拦截，避免每个接口各自实现。

### 16.2 其他统一约定

- **分页 / 排序 / 筛选**：统一参数命名与响应结构
- **编号自动生成**：新增单据时统一走编号规则引擎
- **操作日志**：统一 AOP 切面，写入操作记录（供详情页 Tab 与审计使用）
- **软删除**：CRM 数据不建议物理删除，「删除线索 / 删除客户」应为软删除
- **接口返回结构**：统一 `{ code, message, data, success }`（`success` 是 `code == 0` 的便捷布尔值）

## 17. 建议的最小可演示闭环

不要按模块逐个做完，先打通一条**垂直切片**，用来验证架构与前后端联调链路：

```
登录
  → 线索列表（分页）
  → 新增线索
  → 线索转客户
  → 客户列表 / 客户详情（基础信息 Tab）
  → 合同列表
  → 新增合同（含选择客户、添加产品）
  → 提交审核
  → 审核通过
```

走通这条路径，全站骨架（认证、权限、列表页组件、表单组件、选择器组件、编号引擎、审核状态机）就基本立住了，剩余模块多是同构的复制扩展。

**这条闭环覆盖的接口**：P0 全部 + P1 的 leads / customers / contracts 三组 + P3 的合同审核。
