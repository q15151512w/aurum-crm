# 09 - 生产环境部署

> 目标服务器：`YOUR_SERVER_IP`（CentOS 7）
> 部署目录：`/root/CRM/aurum-crm/`
> 本次范围：**只部署后端**。前端和 Nginx 不在此文档内。

> **本文只讲「单台怎么部署」。**
> 要**加第二台 / 做集群**，看 [12-集群部署清单.md](12-集群部署清单.md) ——
> 那份的第七节是逐步命令，第零节写了当前状态、待办和必须先问到的未知量。

## 0. 整体思路

后端在服务器上以 `prod` profile 运行。生产配置 `application-prod.yml` **不含任何明文密钥** ——
所有凭证都写成 `${环境变量}` 占位符，真实值放在服务器上的 `env` 文件（权限 600，不进 git）。

所以配置文件可以安全提交到仓库，密钥只存在于服务器上。

**服务器上的目录结构：**

```
/root/CRM/aurum-crm/
├── service.sh          # 服务管理脚本（start / stop / restart / status）
├── crm-server.jar      # 后端程序
├── env                 # ★ 密钥文件，chmod 600，绝不进 git
├── logs/
│   ├── console.out     # 控制台输出（启动横幅、JVM 级消息）
│   ├── crm-server.log  # 应用日志（100MB 滚动，总量上限 3GB）
│   └── app.pid
└── .service.lock       # 并发锁，运行时自动生成
```

仓库里对应 `deploy/` 目录：

| 文件 | 用途 |
|---|---|
| `service.sh` | 服务管理（start / stop / restart / status） |
| `check-env.sh` | **环境体检（只读）**，部署前和出问题时都先跑它 |
| `env.example` | 密钥模板（全是占位符，可提交） |

## 1. 一次性准备（只做一次）

### 1.1 环境体检：先跑这个

把文件传上去之后（见第 3 节），**先别急着 start**：

```bash
cd /root/CRM/aurum-crm
chmod +x check-env.sh service.sh
./check-env.sh
```

它会逐项检查并直接告诉你缺什么：

```
── 2. JDK 17 ──────────────
  ❌ 找不到 java
     装 JDK 17：
       tar -zxvf /root/jdk-17.0.13_linux-x64_bin.tar.gz -C /usr/local
── 4. 端口 8080 ───────────
  ❌ 8080 已被占用：LISTEN 0 50 *:8080 *:* users:(("java",pid=1234,...))
── 9. 数据库连通性 ─────────
      增量脚本执行情况：
       ✅ 发票多回款改造（payment_id）
       ❌ 公告表补列（sys_notice.update_by）（实际：0）
```

⚠️ **它是只读的** —— 不改任何配置、不建目录、不装软件、不碰数据库数据，
需要动手的地方只打印命令，由你决定要不要执行。

两处特别值得注意的输出：

- **第 3 项时区**：配错的后果是**不报错的** —— 只会让数据悄悄差 8 小时，最难查。
- **第 9 项增量脚本执行情况**：对应 [7.1](#71-️-sql-变更记录必读) 里那张"是否已执行"全是"待确认"的表，
  跑一次体检就能自动填上。

体检要通过（或确认剩余项不影响）再往下走。

### 1.2 安装 JDK 17

⚠️ **CentOS 7 的基础源里没有 `java-17-openjdk`**（7 最高只到 11），所以不能用 `yum install`，要装 tar 包。

包已经在上线资料里：`jdk-17.0.13_linux-x64_bin.tar.gz`。

```bash
# 上传到 /root 后解压（注意 -C 指定到 /usr/local）
tar -zxvf /root/jdk-17.0.13_linux-x64_bin.tar.gz -C /usr/local

# 配置环境变量
vim /etc/profile
# 在文件末尾追加：
#   JAVA_HOME=/usr/local/jdk-17.0.13
#   PATH=$JAVA_HOME/bin:$PATH

source /etc/profile
java -version      # 应该显示 17.0.13
```

> 如果是 Rocky / Alma / Alinux 8+，可以直接 `dnf install -y java-17-openjdk-headless`。

> ⚠️ 不要覆盖系统自带的 `java`。机器上可能有别的东西依赖它。
> `service.sh` 默认就去找 `/usr/local/jdk-17*/bin/java`，不看 `PATH`，
> 所以就算 `/etc/profile` 在非登录 shell 里没生效也不影响启动。

### 1.3 建部署目录

```bash
mkdir -p /root/CRM/aurum-crm/logs
cd /root/CRM/aurum-crm
```

### 1.4 ⚠️ 设置时区（**必做，不是可选项**）

```bash
timedatectl set-timezone Asia/Shanghai
date          # 确认输出的是北京时间
```

**为什么必须做**：`application.yml` 里 Jackson 固定用 `GMT+8`，
定时任务是 cron `0 5 3 * * ?`（凌晨 3:05），`LocalDateTime.now()` 的值会落库。

如果服务器跑在 UTC，后果是：
- 提醒任务会在北京时间 **11:05** 触发，而不是凌晨；
- 所有落库的时间戳差 **8 小时**。

这两个现象看起来都像"应用逻辑有 bug"，排查方向会完全跑偏。

`env` 文件里的 `-Duser.timezone=Asia/Shanghai` 是第二道保险。

### 1.5 防火墙 + 云安全组（**两层都要配**）

```bash
firewall-cmd --permanent --add-port=8080/tcp
firewall-cmd --reload
firewall-cmd --list-all        # 确认 8080/tcp 在里面
```

⚠️ **云控制台的安全组是完全独立的另一套规则**，必须单独去放行 8080。

只配一层、漏掉另一层，现象是「端口显示已开放，但就是连不上，而且任何地方都不报错」——
没有错误信息可查，只能靠两边对照着看。

## 2. 打包

在**本地开发机**的 Maven 项目根目录下执行 —— 注意仓库套了两层 `crm`：

```bash
cd <项目根目录>
mvn -DskipTests clean package
```

⚠️ **`-DskipTests` 是必须的**，不是图省事：

`crm-server/src/test` 下的 `PersistenceLayerTest` 和 `SalesOwnerOptionsTest` 是
`@SpringBootTest @ActiveProfiles("dev")`，**会去连 `YOUR_SERVER_IP` 的真实数据库**。
不跳过的话，打包就会对着生产数据跑测试。

> 但**不要**用 `-Dmaven.test.skip=true`。`-DskipTests` 仍然会编译测试代码，
> 等于白送一次编译期检查；后者连编译都跳过。

产物固定在：`crm-server/target/crm-server.jar`

**上传前先自检**（这一步能在构建机上就发现"配置文件没打进包"这类问题）：

```bash
# ① 确认两个配置文件都在 jar 里
unzip -l crm-server/target/crm-server.jar | grep 'application-.*\.yml'
# 期望看到 application.yml 和 application-prod.yml 两行

# ② 确认 yml 里用到的环境变量，env 模板里都有
unzip -p crm-server/target/crm-server.jar BOOT-INF/classes/application-prod.yml \
  | grep -o '\${[A-Z_]*' | tr -d '${' | sort -u
```

第 ② 步输出的每个名字，都必须能在 `deploy/env.example` 里找到。
**少一个就是一次必然的启动失败** —— 不用部署就能查出来。

## 3. 上传

⚠️ **路径都是相对 Maven 项目根 `aurum-crm/` 的，先 cd 过去。**
仓库层级是 `crm/crm/aurum-crm/`（外层 `crm/` 是仓库，里面还有一层 `crm/` 才是 git 根），
不 cd 直接粘命令会找不到文件。

```bash
# ① 服务器上先建目录
ssh root@YOUR_SERVER_IP "mkdir -p /root/CRM/aurum-crm/logs"

# ② 本地：先切到 Maven 项目根
cd <项目根目录>

# ③ 脚本和模板传过去
scp deploy/service.sh deploy/check-env.sh deploy/env.example \
    root@YOUR_SERVER_IP:/root/CRM/aurum-crm/

# ④ jar 先传 /tmp 中转
scp crm-server/target/crm-server.jar root@YOUR_SERVER_IP:/tmp/
```

> PowerShell / CMD 里同样可以，但要在上面那个目录下执行，
> 或者把源路径换成绝对路径：
> `scp <项目根目录>/deploy/service.sh root@YOUR_SERVER_IP:/root/CRM/aurum-crm/`

⚠️ jar 先传到 `/tmp` 中转，**不要直接覆盖正在运行的 jar** ——
传输中途失败会留下一个截断的 jar，服务就再也起不来了。

服务器上再落位：

```bash
cd /root/CRM/aurum-crm

# 先备份旧包（按日期，和你原来的习惯一致）
[ -f crm-server.jar ] && cp crm-server.jar crm-server.jar.$(date +%Y%m%d)

# 再落位新包
install -m 644 /tmp/crm-server.jar ./crm-server.jar

chmod +x service.sh check-env.sh
```

⚠️ **`chmod +x` 不能忘。** 从 Windows 传过去的文件会丢掉可执行位，
现象是 `Permission denied`，而文件看起来一切正常。

落位完成后，**先跑一次环境体检**（第 1.1 节），再往下走。

## 4. 配置密钥

```bash
cd /root/CRM/aurum-crm

# ⚠️ 先 umask 再创建，避免出现"先建成全局可读、之后再补救"的窗口
umask 077
cp env.example env
vim env
chmod 600 env
```

**逐项填写**（值可以从本仓库的 `application-dev.yml` 里对照抄）：

| 变量 | 必填 | 说明 |
|---|:---:|---|
| `SPRING_PROFILES_ACTIVE` | ✅ | 固定 `prod` |
| `DB_HOST` / `DB_PORT` | ⬜ | MySQL 地址与端口，**不填默认 `127.0.0.1:3306`**（同机回环）。2026-09-15 起可配 |
| `DB_USERNAME` / `DB_PASSWORD` | ✅ | MySQL 账号密码 |
| `REDIS_HOST` / `REDIS_PORT` | ⬜ | Redis 地址与端口，不填默认 `127.0.0.1:6379`。2026-09-15 起可配 |
| `REDIS_PASSWORD` | ✅ | Redis 密码 |
| `REDIS_USERNAME` | ⬜ | 默认 `default` |
| `MAIL_USERNAME` / `MAIL_PASSWORD` | ✅ | 完整邮箱 + **SMTP 授权码**（不是登录密码） |
| `OSS_ENDPOINT` / `OSS_ACCESS_KEY_ID` / `OSS_ACCESS_KEY_SECRET` / `OSS_BUCKET_NAME` | ✅ | **缺一即启动失败** |
| `AI_MODEL` | ✅ | 必须是真实存在的模型 ID，见下方注意事项 |
| `DEEPSEEK_API_KEY` | ⬜ | 留空则 AI 降级（接口返回 5006），**不影响启动** |
| `OSS_DIR` / `OSS_URL_PREFIX` | ⬜ | 默认 `crm/` / 空 |
| `JAVA_OPTS` / `STOP_TIMEOUT` 等 | ⬜ | 脚本参数，见 env.example 里的说明 |

### ⚠️ 编辑 env 文件的三个坑

**① 每个值都要用单引号包起来。**

这个文件是被 bash `source` 执行的，不是被解析的。裸值里含 `$`、反引号、空格、`#` 会被展开甚至执行：

```bash
DB_PASSWORD='abc$123'    # ✅ 正确，值是 abc$123
DB_PASSWORD=abc$123      # ❌ 值是 abc23 —— $1 被当成变量展开成了空
```

**② 不要用会写 CRLF 的 Windows 工具编辑。**

尾部的 `\r` 会让 `DB_PASSWORD` 实际变成 `"xxxx\r"`，
数据库报 `Access denied`，而你在编辑器里怎么看那个密码都是对的 ——
排查方向会完全跑偏到"密码是不是被改了"上去。

`service.sh` 启动时会检测并拒绝启动，报错里直接给出 `dos2unix` 命令。

**③ `AI_MODEL` 先确认是真实模型 ID。**

`application-dev.yml` 里写的是 `deepseek-flash`，但 DeepSeek 公开的模型名是
`deepseek-chat` / `deepseek-reasoner`。写错了不会影响启动，
但会在**调用 AI 功能时**失败。所以 `application-prod.yml` 里这项**故意不给默认值**，逼你显式确认一次。

## 5. 启动

```bash
cd /root/CRM/aurum-crm
./service.sh start
```

脚本会：校验环境变量 → 拉起进程 → 轮询健康检查（最多 180 秒，正常 15~40 秒）→ 报告结果。

**失败时会直接打印现场**：控制台日志尾部 40 行，外加对常见原因的定向提示
（占位符没解析 / 数据库拒绝 / Redis 连不上 / OSS 配置缺失）。

⚠️ 脚本**故意不做自动重启、自动回滚**：重启循环会把第 1 个错误淹没在第 5 个里，
反复起停的进程也让人没法看日志。失败就停下来，让人来看。

## 7. 发版与回滚

**发版**：

```bash
cd /root/CRM/aurum-crm
cp crm-server.jar crm-server.jar.$(date +%Y%m%d)     # 备份
# 上传新包、落位、chmod +x service.sh
./service.sh restart
./service.sh status
```

**回滚**：

```bash
cd /root/CRM/aurum-crm
cp crm-server.jar.20260915 crm-server.jar
./service.sh restart
```

⚠️ **回滚救不了数据库改动。** 项目没有迁移工具，`sql/*.sql` 是手工执行的。
如果新版本依赖某个新增的列，回滚 jar 也没用。
所以每次发版要记录**执行了哪些 SQL**，并且 `service.sh` **绝不自动执行 SQL**。

⚠️ **不要在 03:00 ~ 03:15 之间发版** —— 那是提醒任务（cron `0 5 3 * * ?`）的执行窗口。

### 7.1 ⚠️ SQL 变更记录（必读）

**为什么需要这张表**：项目没有 Flyway / Liquibase 之类的迁移工具，`sql/*.sql` 全靠手工执行。
而 `sql/upgrade/` 目录里**已经有 10 个增量脚本**，且大多**不是重复执行安全**的 ——
（`sql/` 下只有 `crm.sql` 一份全量初始化脚本，增量脚本全在 `sql/upgrade/`）
光看文件名和 git 历史，**无法判断某个库到底跑过哪些**。

典型事故：接手的人不确定 `sys-notice` 那个脚本跑过没有，
凭感觉再跑一遍，报 `Duplicate column 'update_by'`，于是以为"脚本有问题"，
转头去改 SQL —— 而实际上脚本早就执行过了，什么都没坏。

**⚠️ 先说一个容易忽略的前提**：目前 **dev 和 prod 是同一个数据库**。
`application-dev.yml` 连的是 `YOUR_SERVER_IP:3306/crm`，
prod 的地址由服务器 `env` 里的 `DB_HOST` 决定 —— **2026-09-15 起它填的也是
`YOUR_SERVER_IP`**，而在此之前是 `127.0.0.1`。两种写法指向的是**同一个库**，
因为 MySQL 就装在这台机器上。

> 换句话说：`DB_HOST` 填 `127.0.0.1` 还是填这台机器的 IP，**连的都是同一个库**，
> 差别只在网络路径。同机场景下回环更快、且不依赖安全组与 NAT 回环。

所以：**本地对这些 SQL 的任何操作，改的都是生产库。** 这条记录只需要维护一份。

#### 脚本清单与执行状态

> 「重复执行」列的含义：按项目既有约定，多数脚本重跑会报**可忽略**的错误码
> （1060 列已存在 / 1091 索引不存在 / 1062 主键重复），脚本头部都有说明。
> 这里标的是**重跑会不会造成数据损坏**，不是会不会报错。

| 脚本 | 做了什么 | 重复执行 | 是否已执行 |
|---|---|---|---|
| `sql/crm.sql` | 全量建库（49 张表） | ☠️ **含 49 条 `DROP TABLE`，对已有库执行 = 清库** | 生产库**已执行过**（库是好的），⚠️ **绝不可再跑** |
| `sql/upgrade/alter-2026-09-14-invoice-allocation.sql` | `fin_invoice` 加六个开票信息快照列；`payment_id` 改可空；删 `uk_payment_active` | ⚠️ 报 1060/1091/1062，忽略即可 | ✅ 已执行 <br>（`payment_id` / `invoice_title` 均在） |
| `sql/upgrade/alter-2026-09-14-fin-invoice-rebuild.sql` | 一次性修复：把停留在旧 schema 的 `fin_invoice` 拉齐 | ❌ **有条件的一次性修复**，执行前必须先诊断 `SHOW COLUMNS FROM fin_invoice` | ☐ 未核对（结构已拉齐，是否需要跑由诊断决定） |
| `sql/upgrade/alter-2026-09-14-numbering-rule-items.sql` | 新增 `sys_numbering_rule_item`、`sys_numbering_counter` 两表 + 菜单权限 | ⚠️ 建表有 `IF NOT EXISTS`，菜单 INSERT 可能重复 | ✅ 已执行 <br>（两张表都在） |
| `sql/upgrade/alter-2026-09-14-numbering-menu.sql` | 「编号定义」菜单归到「组织架构」下 | ✅ 纯 UPDATE，可重跑 | ☐ 未核对（只影响菜单归属，不影响功能） |
| `sql/upgrade/alter-2026-09-14-sys-menu-detail.sql` | 补两条详情页隐藏菜单（`menu_id` 34 / 53） | ✅ `INSERT IGNORE`，可重跑 | ✅ 已执行 <br>（两条详情菜单在） |
| `sql/upgrade/alter-2026-09-14-sys-notice.sql` | `sys_notice` 加 `update_by` / `update_time`；`receiver_id` 改可空 | ⚠️ 报 `Duplicate column`，忽略即可 | ✅ 已执行 <br>（`update_by` 在） |
| `sql/upgrade/alter-2026-09-15-invoice-detail-menu.sql` | 补发票详情页隐藏菜单（`menu_id` 66） | ✅ `INSERT IGNORE`，可重跑 | ✅ 已执行 <br>（`menu_id` 66 在） |
| `sql/upgrade/alter-2026-09-15-sys-notice-handle.sql` | `sys_notice` 加 `handle_status` / `handle_time`（「已处理」功能） | ⚠️ 报 `Duplicate column`，忽略即可 | ✅ 已执行 <br>（两列均在） |
| `sql/upgrade/alter-2026-09-15-contract-audit-finance-menu.sql` | **修断链**：把合同审批流的角色审批人（财务）补上 `crm:contract:auditList / :audit / :batchAudit` 三个菜单权限 | ✅ `INSERT IGNORE`，幂等（已实测：重跑后 `sys_role_menu` 行数不变） | ✅ **已执行**（2026-09-15） |
| `sql/upgrade/seed-2026-09-14-invoice-snapshot-backfill.sql` | 演示数据回填（发票快照、客户开票信息） | ✅ `INSERT IGNORE` + UPDATE，可重跑 | ☐ 未核对（只影响演示数据，不影响功能） |

> 上表的「是否已执行」于 **2026-09-15 直接连库核对**（`information_schema` +
> `sys_menu` / `sys_role_menu` 实查），不是凭印象填的。核对方法见下一节。
> 标 ☐ 的三条是**刻意没核对**的：它们要么只影响菜单归属 / 演示数据（跑没跑都不影响功能），
> 要么是「先诊断再决定要不要跑」的一次性修复 —— 对这三条，核对结果不改变任何行动。

#### 怎么判断某个脚本跑过没有

不靠记录也能查 —— **直接看库里的结构有没有变**。这是最可靠的依据：

```sql
-- invoice-allocation 跑过没？有 payment_id 就是跑过了
SHOW COLUMNS FROM `fin_invoice` LIKE 'payment_id';
SHOW COLUMNS FROM `fin_invoice` LIKE 'invoice_title';

-- sys-notice 跑过没？
SHOW COLUMNS FROM `sys_notice` LIKE 'update_by';

-- numbering-rule-items 跑过没？
SHOW TABLES LIKE 'sys_numbering_rule_item';
SHOW TABLES LIKE 'sys_numbering_counter';

-- sys-menu-detail 跑过没？（应该返回 2 行）
SELECT menu_id, path FROM `sys_menu`
 WHERE path IN ('/crm/quotation/:id', '/crm/product/:id');

-- invoice-detail-menu 跑过没？（应该返回 1 行）
SELECT menu_id, path FROM `sys_menu` WHERE path = '/finance/invoice/:id';
```

**这些检查为什么重要**：前 4 项对应的正是代码里 `DO` 对象存在、而表里列不存在的经典故障 ——

```
ERROR 1054 (42S22): Unknown column 'payment_id' in 'field list'
```

只要 `InvoiceDO` 里有 `paymentId`，任何一次列表查询都会带上它，
于是**整个模块直接 500**，而不是某个字段取不到值。

⚠️ 另外注意：`sql/crm.sql` 头部标的是 `V1.0 / 2026-09-12`，
但测试代码注释里引用的是一个**并不存在**的文件名 `crm-schema-V1.1.sql`。
看到这个引用不要去找它，就是 `sql/crm.sql`。

## 9. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `bad interpreter: /bin/bash^M` | `service.sh` 带了 CRLF | `dos2unix service.sh` |
| 数据库 `Access denied`，但密码看着对 | `env` 文件带了 CRLF，密码尾部多个 `\r` | `dos2unix env`，或 `sed -i 's/\r$//' env` |
| 启动报 `Could not resolve placeholder` | `env` 里缺变量 | 对照 `env.example` 补齐，脚本启动时会先列出来 |
| 启动报 `缺少 OSS 配置项 xxx` | OSS 四项必填项有缺失 | 这是**有意设计**的 fail-fast，补齐即可 |
| 163 报 `535 authentication failed`，授权码没问题 | 163 网页版的 SMTP 服务没开启 | 去 163 网页版开：设置 → POP3/SMTP/IMAP |
| `Permission denied` 执行脚本 | 从 Windows 传过来丢了可执行位 | `chmod +x service.sh` |
| 连不上 8080 | 防火墙和云安全组只配了一层 | 两层都查：`firewall-cmd --list-all` + 云控制台 |
| `Address already in use` | 上一个进程还没完全退出 | `./service.sh status` 确认，再 `restart` |
| 中文日志乱码 | 服务器 locale 不是 UTF-8 | `LANG=en_US.UTF-8`，`env` 里已有 `-Dfile.encoding=UTF-8` |

## 10. ⚠️ 已知风险与注意事项

### 10.1 生产与开发共用同一个数据库

`application-dev.yml` 里的 MySQL 和 Redis 指向的就是 `YOUR_SERVER_IP`，
也就是说**本地开发连的就是生产数据**。

- Redis 已经用 `database 2`（生产）和 `database 0`（开发）做了隔离，
  避免登录 token 和验证码互相串；
- **但 MySQL 没有隔离**，本地调试写的就是生产数据。

⚠️ 尤其注意：本地跑 `PersistenceLayerTest` / `SalesOwnerOptionsTest` 这两个集成测试，
**操作的就是生产库**。

⚠️⚠️ **最危险的一条**：`sql/crm.sql` 里有 **49 条 `DROP TABLE`**，是对已有库执行就会清库的全量脚本。
因为是同一个库，**在本地"重新导一下数据库"就等于把生产数据清空**。
每次动 SQL 之前先确认一遍目标库（`SELECT DATABASE();`），细节见 [7.1 SQL 变更记录](#71-️-sql-变更记录必读)。

### 10.2 8080 是明文暴露的

后端目前**没有配 TLS**，直接绑 `0.0.0.0` 对外。这意味着
**登录密码和 Sa-Token 令牌是以明文走公网的**。

**（2026-09-15 更正）** 这里原本写的是「Nginx 装在本机反代 `127.0.0.1:8080`，
`server.address` 改回 `127.0.0.1`」—— 那是按「nginx 与后端同机」假设写的。

实际情况是：**前端和它的 nginx 部署在另一台云服务器上**，通过 `/api` 反代到
`YOUR_SERVER_IP:8080`。所以：

- ⚠️ **不要**把 `server.address` 改成 `127.0.0.1` —— 那会让另一台机器上的
  nginx 连不上，**直接把已经跑通的前端打挂**
- 要做的是：安全组只放行**前端服务器**的来源 IP 访问 8080，
  而不是关掉 8080 或绑回环

要加第二台后端时看 [12-集群部署清单.md](12-集群部署清单.md)。

### 10.3 数据库和 Redis 当前对公网开放

`3306` 和 `6379` 目前可从外网访问（本地 dev 就是这么连的），
而相关密码**已经明文提交进了 git 历史**。

本文档范围内未做处理。后续建议：
把 MySQL 和 Redis 都改成只监听 `127.0.0.1`，关掉这两个端口的防火墙规则，
并轮换全部凭证。应用在同一台机器上，走回环访问，从外部访问这两个端口没有任何正当需求。

### 10.4 日志磁盘占用

应用日志由 Spring Boot 按 `100MB × 30 份`、总量上限 `3GB` 滚动。
`console.out` 每次启动重命名保留一代。

`service.sh status` 会打印磁盘余量，建议偶尔看一眼。

### 10.5 堆转储含客户数据

`JAVA_OPTS` 里配了 `-XX:+HeapDumpOnOutOfMemoryError`，
OOM 时会落一个堆转储文件。**里面含客户姓名、电话、金额**，分析完记得删掉。
（`umask 027` 保证日志和转储目录不会被同机其他用户读到。）
